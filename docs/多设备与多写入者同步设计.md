| 问题 | 决定 | 由此推出的东西 |

## 2. 四条骨架规则

### R1 身份以凭证为准，`device_id` 降级为「写者标识」

- `Authorization: Bearer <token>` → `account_id`（后台侧持久映射，不由客户端声明）。
- 无凭证时 `account_id = "anon"` —— **整实例共享的那一个匿名账号**。为什么不按 `device_id` 切：`GET /favorites` 没有请求体，服务端拿不到 `device_id`，按设备切的结果是写入者下一次 GET 就看不见自己刚写的行；而「多设备共用一个账号」本来就是需求本身，共享匿名恰好直接满足它。代价同一张决策表：同一实例上不同人的匿名数据互相可见，真实后台要么强制登录，要么接受这一点。
- 第三方服务由运维发**独立 provider 凭证**，通过 `provider_accounts` 授权映射绑定到用户已有的 `account_id` —— 这就是「同一账号、可见可合并」的实现方式：不是给它开一个新账号，而是让它的 credential 指向同一个 `account_id`。映射表与授权流程见接入文档 §1，本文只管账号维度这一层。
- 每个 op 落库前校验「这行属于本账号」。**删除侧**不属于就归入 `unknown_ops`，与「不存在」同一个出口，**不回**「存在但无权限」这类可被枚举他人数据的信息。**写侧（UPSERT）2026-11-19 裁决落地同一口径，但换桶**：被拒的写进 `op_errors`，原因用中性文案（不透露归属），该行一字不改、不计 `applied`。为什么不能也跟 `unknown_ops` —— App 把 `unknown_ops` 计入「已确认」，那条 op 会**出队并标 SYNCED**，等于本机改动被静默丢掉而后台根本没存；`op_errors` 才是「后台答了、但拒了」那一档，App 现成判据会把它标红留在队列（[SyncWorker.kt:112](../app/src/main/java/com/favkit/tablet/sync/SyncWorker.kt#L112)），App 侧不需要任何改动。**参考实现已落地（2026-11-19）**：归属校验挪到每个 UPSERT op 的最前面（[server.mjs:624-634](../mock-server/server.mjs#L624-L634)），他账号的行直接进 `op_errors` 并 `continue`，新建行分支与目标行分支都不再出现「照抄别人归属」的分支；删除侧维持 `notMine` → `unknown_ops`（[server.mjs:762](../mock-server/server.mjs#L762)）。早前那句「写内容、不换主人」是当时的现状，已随这次改动下线，常驻断言见 `mock-server/test/cross-account.test.mjs` 的 M1-c 与 `mock-server/test/server.test.mjs` 的「跨账号 id 撞车的 UPSERT 被拦」。

### R2 账号内的自然键是 URL，id 只是临时句柄

UPSERT 的处理顺序（这就是「后台只需要做个判断」的完整展开）：

1. `id` 命中本账号某行 → 视为对已有行的编辑，按字段合并。
2. `id` 未命中、`url` 命中本账号某行 → **不建新行**，把这次 op 携带的字段合并进那一行；回执用 `merged_into: [{op_index, from_id, to_id}]` 告诉调用方归到了哪个 id。
3. 两者都未命中 → 插入新行。

配套约束：

- 同一 `id` 带不同 `url` 重传 → 该 op 拒绝，`op_errors` 给原因。url 是自然键，改它等于换一条收藏；本地缓存、媒体清单、播放进度都会跟内容错位。
- 合并时 `favorite_at` **取较老的那个**。它同时是 keyset 游标，把一条旧收藏的时间推到未来会让游标跳条（§3 末）。
- 删除仍只按 `id` 生效。判重只发生在写侧，所以第三方拿自己的 id 删不到东西时进 `unknown_ops`，是正确结果。
- **这条对第三方最反直觉**：它不能拿自己的 id 当持久标识，要么读 `merged_into`，要么自己维护「外部 id → 后台 id」映射表。文档必须显式写（§6）。
- App 侧这条**已实现**（2026-11-19，App 轮次 2d）：悬浮面板保存时 url 命中本机墓碑行 → 复用那一行的**原 id** 恢复（`deletedAt` 清空、写这次的备注/来源/标签整套覆盖、badge 回 QUEUED、HLC 成对新戳），不再新建一个 id 等后台归并回执来对账。两个后果要写清：① `favorite_at` **取较旧的那个**，所以重新收藏的那条**不会回到列表顶部**，而是回到它上次的排序位置 —— 这是游标稳定的直接代价，界面是否要「保存后定位到那条」是一个单独的界面决定，目前不做；② 队列里那条没上传的 DELETE 由 `SyncManager.queue()` 现成的「同 id 旧 op 先删再入」就地换成 UPSERT，不需要新逻辑，两笔互斥的 op 不会都跑。后台的归并 + 复活仍然是最后一道防线（老版本 App 靠它）。

### R3 ~~一个请求只有一个 op~~（已作废）

原本这条是为「第三方直接批量调 `/sync`」设的公开契约。第三方改走独立 ingest 面之后它失去了存在理由，现在只是 **App 面的内部实现事实**：客户端每次发 1 条（`OPS_PER_REQUEST = 1`，[SyncWorker.kt:110](../app/src/main/java/com/favkit/tablet/sync/SyncWorker.kt#L110)），后台不必对 `ops.length != 1` 回 400，也不必实现「请求内多 op 的行内合并 + 顺序无关性」那一套。

要保留的只有一句：**服务端不得假设 `ops` 长度恒为 1**（老版本 App、手动 curl、未来的批量优化都会发多条），等式 `applied + len(unknown_ops) + len(op_errors) == len(ops)` 对任意长度都得成立（不下发 `op_errors` 的老后台是它的退化形 `applied + len(unknown_ops) == len(ops)`）。批量需求由 ingest 面承接（接入文档 §3）。

### R4 客户端必须声明改了哪些字段

这条不是可选的细节，而是「字段级 LWW」能不能成立的前提：

客户端上传的是**整条 favorite**（接口说明 §2.4），里面 `url`、`source_app`、`favorite_at`、`tags` 大多是从后台抄回来的、这次并没有改动。如果服务端把整行都记成「这次写的」，那么：

> A 离线改备注（带着后台某天返回的旧标签），B 之后改了标签。A 上线上传，这次写入的 HLC 比 B 那次新 → **A 携带的旧标签赢，B 的标签改动被吞掉。**

所以 op 里加 `changed_fields`，服务端**只对列出的字段**做字段级合并，其余一律不动：

- App：`create` 传 `["url","note","tags","source_app","favorite_at"]`；`updateNote` 传 `["note"]`；`updateTags` 传 `["tags"]`；`markDeleted` 走 DELETE 不涉及。
- 缺省（不带该键）= 全字段覆盖 = 今天的语义。这一档留着纯为防御（老客户端、手动 curl）；ingest 面不需要它，每个 item 的字段集天然就是 `changed_fields`（接入文档 §6）。

**标签的固有代价要写明白**：`tags` 是一个字段，整体 LWW。A 删一个标签、B 加另一个标签 → B 的集合赢，A 的删除丢失。这是「字段级粒度」这个选择的直接后果，不是 bug。要根治得把 tags 做成 per-tag 墓碑集合（§10 列为后续）。

## 3. 时间与决胜键

先把三件事分开，它们常被混为一谈：

| 问题 | 影响 | 处置 |
|---|---|---|
| **时区** | 只影响**显示**，不影响任何比较 | 协议永远是 epoch 毫秒（与时区无关）；App 的 `formatDate`/`formatClock` 继续按设备本地时区渲染，不动 |
| **格式与单位** | 会静默错位（把本地时间当 UTC 写 = 偏 8 小时；秒/毫秒混用 = 差 1000 倍） | 协议**只接受整数 epoch 毫秒**。出现日期字符串（`"2026-11-19 03:10:00"`，无偏移，无法判定）、浮点、或明显是秒的量级 → 400 + `op_errors` 给原因 |
| **偏移与漂移** | 直接决定**胜负**，是真正危险的那个 | 不让任何客户端墙钟单独拥有决定权：HLC + 服务端夹紧 + 三档兜底 |

### HLC（混合逻辑时钟）

每个写者维护 `(wall_ms, seq)`：

- `wall_ms = max(本地墙钟, 已知下界)`；
- 每次本地写：`seq += 1`；
- **收到任何响应**：把 `server_time` 吸收成新下界（`wall_ms = max(wall_ms, server_time)`，`seq = 0` 当 `wall_ms` 被抬高时）。

比较序：`wall_ms` → `seq` → 写者标识（请求顶层 `device_id` 的字典序）。平局规则固定，因此结果可复现、可写测试。

写者标识**相同**时后到的那一笔赢（内部用 `>=`，不是严格大于）：同一台设备走 `server_time` 兜底路径的两次编辑可以撞进同一毫秒、`seq` 又同为 0，严格大于会把第二次改动判输 —— 用户改完抬头看到的还是旧值，而这正是平局规则要避免的那件事。

决胜戳存在服务端内部列 `field_hlc`（逐字段一份 `[wall_ms, seq, writer]`），**不上协议**：响应发出前剥掉，历史行没有它时从 `updated_at` 派生（writer 退化成 `account_id` 这种粗粒度值），不做迁移。

关键收益：`wall_ms` 的绝对值可以被时区或错误时钟随意平移，但**因果顺序不会反转** —— B 在知道 A 的写入之后才写，它的下界就 ≥ A，无论 B 的表上写着几点。`seq` 保证同一写者内的多次编辑严格有序，这正是墙钟在快速连改（毫秒并列）时给不了的。

现成的下界来源：`server_time` 在每个响应里都已经有（[Dto.kt:127/171/193/224](../app/src/main/java/com/favkit/tablet/net/Dto.kt#L127)）。HLC 让这个字段第一次有职责，**且不需要新增任何请求** —— 这一半 App 侧也已经落实（2026-11-19，App 轮次 1）：出站口五个收到 `server_time` 的地方全部走 `SyncClock.absorbServerTime`（[SyncApi.kt:69/78/114/145/179](../app/src/main/java/com/favkit/tablet/net/SyncApi.kt#L69)），吸收后进的是 DataStore 而不是 Room，因为 destructive migration 会把时钟的下界一起清掉。

### 服务端三档兜底

协议字段全部可选，服务端按可得信息降级，并把每档语义写成「定义」而非「未定义行为」。第三方走 ingest 面时**根本不参与这件事** —— 它的 HLC 由服务端代发（接入文档 §7）；下面这张表现在只服务两类非协作写者：老版本 App，以及手搓 curl 的联调者。

| 请求携带 | 服务端用作字段最后写入时间 | 语义 |
|---|---|---|
| `write_hlc{wall_ms,seq}` | HLC 原值，超前（`> now+5min`）则**夹到 `now+5min`**，`seq` 与档位不变 | 参与因果排序 —— 本 App |
| 仅 `updated_at_ms` | 合法则用原值（负数夹 0）；超前则**退回 `server_time`**，不是 `now+5min` | 物理时间 LWW，无因果保证 |
| 都没有 | `server_time` | 到达顺序赢 |

第二档为什么不用 `min(updated_at_ms, server_time + 5min)`：那等于给一个跑快的钟发一张「未来 5 分钟内谁都赢不了你」的票，而这一档本来就没有因果保证；退回 `server_time` 才是「你的表不可信，就按到达顺序算」。两档由此真的不同档，可以写测试。

**这张表参考实现已完整落地（③-3a，2026-11-19）**：三档取值、两键同带按第一档不混算、两处「夹紧不拒」。下面两条也在同一轮接完（③-3b，2026-11-19）：复合分页游标与 `clock_skew_ms` 计数，验收见接口说明 §3.2 与 §3.4。

### 其余时间字段

- `favorite_at`：仍由写者提供（它是「用户什么时候收藏的」这个事实，不是决胜键）。服务端夹紧到 `[now − 10 年, now + 5 min]`，超出即夹紧并记日志，不拒绝请求。
- 分页游标从 `favorite_at` 改为 **`(favorite_at, id)` 复合 keyset**（**已落地**：游标串是不透明的 `<favorite_at>.<id 的 URL 编码>`，`/meta.cursor_style` 同步改为 `keyset:favorite_at_desc,id_asc`）。两个写者给出同一毫秒时，单列游标翻页会既漏条又重复，且结果不可复现。③-3a 的夹紧把这件事从「理论可能」变成了「必然撞」：所有早于 `now − 10 年` 的 `favorite_at` 会被压成**同一个值**，而归并取较旧也会把两行对齐 —— 并列组一出现，单列游标就整段跳过同值的那几条。并列值现在实测会撞（同一毫秒收藏四条，`limit=3` 翻页拿到 `1795036401412.skew-c` 这种游标，续页不重不漏）。**游标不合法一律明确 400，不退回第一页**：退第一页会让 App 陷入「同一页 → 游标不变 → 同一页」的死循环。
- 服务端可观测：每个 op 记下「客户端声称的时间 vs 接收时间」的差（`clock_skew_ms`）到日志与账号级统计（超前/滞后各计数），用于发现「某台设备时区写错」「某个容器时钟没同步」。**不下发**该值 —— 客户端不该依赖它做决策。**已落地**，并补了三件当时没说清的事：只记第一、二档（第三档的戳就是服务端 `now`，偏移恒 0，记了是稀释）、记的是**夹紧前**客户端声称的戳（记夹紧后的值等于把问题本身抹掉）、阈值取超前 > `now+5min`（复用夹紧窗口）与滞后 24 h，只在进程内累计、重启清零。

## 4. 服务端数据模型

```
accounts(id, kind[anon|user], created_at)
credentials(token_hash → account_id, rate_limit, created_at)
    -- App 面：一个用户设备一个账号。provider 凭证与 provider→account 授权映射另建两张表，
    -- 见接入文档 §1/§2（favorite_aliases 也在那边），本面不为此加列。

favorites(account_id, id, url, note, source_app, favorite_at,
          rev,                     -- 账号内单调递增，服务端发号，每次落库 +1
          deleted_at,              -- 墓碑：非空=已删，仍保留行
          media_rev,               -- 内容信息最后一次被写入时的 rev
          PRIMARY KEY (account_id, id),
          UNIQUE (account_id, url))

favorite_writes(favorite_id, field, value, hlc_wall, hlc_seq, writer, rev)
    -- 每个可改字段一行；合并时按 HLC 取胜后写回 favorites 的列。
    -- 也可做成 favorites 上的列级 *_hlc/*_rev 冗余列，量小反而更快，实现时按查询计划选。

tags(account_id, name) / favorite_tags(account_id, favorite_id, tag_id)

revision_log(account_id, rev, favorite_id, kind[upsert|delete], payload_json, written_at)
    -- /changes 的唯一来源。按账号 GC，保留窗口默认 30 天 + 至少 N 万条
```

服务端还必须有：

1. **解析结果缓存 + 解析队列**：按 `hash(normalized_url)` 存 `media` + `resolved_at`。写 `note`/`tags` **永不触发重解析**，重传同一 url 也不重爬。App 面仍在同一次调用里返回内容（已有缓存直接给，无缓存时同步解析一条通常很快）；**ingest 面走异步解析队列**，批量写入不等解析（接入文档 §9）。这条同时解决 §1 第 6 点和批量回灌打爆解析层的问题。
2. **墓碑**：DELETE 改成写 `deleted_at`，物理清理交给 GC（窗口见 `revision_log`）。/changes 与全量拉取都以 `deleted_at` 为空过滤。
3. **按凭证限流**：429 + `Retry-After` + **响应体 `next_wait_ms`**（App 读后者、不读头 —— 接口说明 §5 已确立这条口径）。Ingest 面没有待推的队列，只回 `retry_after_ms`。
4. `GET /meta`（App 面）：`{cursor_format, changes_retention_days, resolver: {…}, rate_limit}`。免鉴权，联调第一步就查它。第三方看的是另一个 `GET /ingest/meta`，两者内容不同，不要合成一个 —— 合成之后服务方会读到一堆与它无关的 App 同步参数。

不模拟升级前的全局表：`favorites` 里每一行都必须带 `account_id`，没有「未认领」这一态。

## 5. 协议变更清单

「加字段安全、改语义危险」是接口说明 §10 定的口径，这里照它分类。

| 位置 | 字段 | 性质 | 缺省行为（老客户端/老后台） |
|---|---|---|---|
| `op` | `base_rev` (number) | 新增，可选 | 不带 = 不做版本冲突判定；**带了而落后于行上现值，同样不改判据**（裁决见下面那段） |
| `op.favorite` | `write_hlc: {wall_ms, seq}` | 新增，可选 | 走三档兜底（§3） |
| `op.favorite` | `updated_at_ms` (number) | §3 三档兜底**第二档的载体**，不是本 App 用的键 | 本 App 从不发（有戳就发 `write_hlc`，没戳就两个都不发）。谁发了它，这一笔就按物理时间参与决胜：服务端夹紧到 `min(updated_at_ms, server_time + 5min)`，超前得离谱就退回 `server_time` |
| `op` | `changed_fields` (string[]) | 新增，可选 | 视为全字段覆盖（= 今天语义） |
| `favorite` | `rev` (number) | 新增，仅响应 | App 存下来作为下次 `base_rev`；老后台不下发则 `base_rev` 永远不带，功能退化为纯 HLC 合并 |
| `SyncResponse` | `op_errors: [{op_index, id, reason}]` | 新增，可选 | 不下发时 App 仍按现有 `applied + unknown_ops` 判据 |
| `SyncResponse` | `merged_into: [{op_index, from_id, to_id}]` | 新增，可选 | 只有真发生归并才下发 |
| `SyncResponse` | `rev` (number) | 新增，可选 | 账号当前最新 rev，供 App 记录对账起点 |
| `POST /sync` | 语义变更：`applied + len(unknown_ops) == len(ops)` 扩展为 `applied + len(unknown_ops) == len(ops) − len(op_errors)`，且 `op_errors` 非空时该 op **不得**计成 applied | **危险类** | App 判据要同版本更新，否则拒绝型错误会被算成假成功并触发「条数不符」标红 |
| `GET /favorites` | `next_cursor` 改为复合游标（不透明字符串 `<favorite_at>.<id>`） | 语义变更 | **参考实现已改完（③-3b）**。App 侧代码不用动：它一直把游标当不透明串原样回传。真正需要同步的是反过来那半 —— 还发单列纯数字游标的老 App 打新后台会收到 400 而取不到页，所以这一条必须跟后台同批上线，不做双向兼容 |
| 新 `GET /favorites/changes?since_rev=&limit=` | `{ok, server_time, items: [{rev, favorite_id, deleted, favorite?}], next_rev, truncated}` | 新增 | 404/未实现 → App 退回全量翻页，功能降级但不报错 |
| 新 `GET /meta` | 见 §4（App 面专用，不含 ingest 参数） | 新增 | 404 → App 用内置默认节奏 |
| `media` 缺失 | **语义澄清**：在异步解析之后，它明确表示「后台还在解析」，而不再只是「老后台没返回」 | 安全类（App 早就为这条写了显示分支，`VideoCard.kt:388`） | 只改文案，不加字段、不加状态枚举 |

**`base_rev` 只做情报，不做冲突拒写（③-2 定为不做）。** 落后于行上当前 `rev` 的 `base_rev` 不改变落库判据：每一列的归属仍由那一列的 `write_hlc` 逐字段决胜决定，后台照常落库，只把该行最新 `rev` 放进响应，App 存下来当下次编辑的起点。理由：这套协议里 `base_rev` 唯一真正要防的事——「整行覆盖把另一台设备刚改的列吞掉」——已经被 §2 R4 的 `changed_fields` + 逐字段 LWW 堵住了；再往下判只剩两种做法，一是拒写（离线攒下的编辑一回到网上就全弹成 FAILED，等用户自己处理），二是新增一个冲突回执键（本表之外的字段，要多占一个 App 与后台的同版本窗口）。两种代价换的都只是「LWW 已经给出的同一个结果」，所以判据保持一条：**每一列由谁拥有，只看那一列的 HLC**。App 侧继续如实发 `base_rev`，服务端把它当排障线索（日志/未来的冲突面板），不参与胜负。

本表只覆盖 **App 面**。第三方走的是另一套接口（`POST /ingest/favorites`、`GET /ingest/meta`、`GET /ingest/status`），字段、结果码、幂等规则全在 [第三方采集服务接入接口.md](第三方采集服务接入接口.md)，不与本表交叉 —— 两个面唯一的耦合点是共用同一张 `favorites`、同一个 `rev` 序列和同一份 `revision_log`。

`items[].deleted = true` 时不带 `favorite`，App 收到即**物理删除本地行**（连播放进度一起，符合「进度只在本机」的决定）。`truncated = true` 表示 `since_rev` 已被 GC 掉，App 丢弃游标改走全量。

**这条接口只发四个字段，翻页靠它们判**（不额外加 `has_more`）：`items` 为空就是这一段对完了，直接停在 `next_rev`；`items` 满一页且 `next_rev` 比这一批最大 `rev` 还大才继续拉下一批；`truncated` 为真则丢弃游标走全量。契约里不列 `has_more` 是有意的 —— 它和「整页长度」说的是同一件事，两处给就有一处会说不清。

## 6. 两个 API 面

写入者形态最终定为：**App 面不动，第三方给独立的 ingest 面**。原本为「第三方直接调 `/sync`」设计的那些约束就地迁走：

| 迁到接入文档 | 迁走的原因 |
|---|---|
| R3 单 op 公开契约（已作废） | ingest 面本来就是批量形态，App 面不必再对外承诺长度 |
| L0/L1/L2 能力分档 | 不再需要「同一份协议按客户端能力降级」这件事，两个面各自只有一种客户端 |
| 第三方 9 条硬要求 | 换成 ingest 面自己的 10 条自查清单（更短，因为它不必理解队列、`next_wait_ms`、`merged_into`、HLC） |
| `changed_fields` 对第三方必填 | item 的字段集天然就是它，写权由凭证的 `writable_fields` 判定 |
| 「客户端传的 `media` 一律忽略」 | 放宽成 `media_hint` 兜底规则（仅在解析失败时补标题/封面），权威仍然在解析器 |
| 全有或全无的校验回滚 | 逐 item 独立应用 —— 批量场景一条脏 url 让整批回滚，服务方只能二分重发 |
| 协议字段的时钟兜底档位 | 服务方不碰时钟，由服务端代生成 HLC |

**留在本文不变的东西**：R1 账号维度（只是多了一层 provider→account 授权映射）、R2 url 是账号内自然键（`merged_into` 仍然保留给 App 面，因为 App 自生成的 id 也可能撞上 ingest 先建的那行）、R4 `changed_fields`（App 面仍然必填，理由一个字没变）、§3 全部时间与 HLC 决胜规则、§4 表结构与 `revision_log`、`/changes` 对账通道。

两面共用同一套数据这一条是整套方案的支点：ingest 每次落库同样 `rev += 1` 并写 `revision_log`，所以 App 看见第三方写入**不需要任何新接口、新字段或新代码路径**。反过来说，任何「为了第三方」想给 App 面加的东西，都要先问一句「能不能只在 ingest 面解决」—— 事后看，答案是全部能。

## 10. 明确不做的与残余风险

1. **`tags` 集合级合并**。今天按字段 LWW，代价见 §2 R4（并发加/删标签会丢一边）。要做对需要 per-tag 墓碑 + 并集语义，改动面在后台合并层与 App 的本地标签库，收益是「少丢标签」。留作灰度 ④ 之后的独立决策，不要顺手加进 ③。
2. **不做冲突提示 UI**。字段级合并后不存在「整条冲突」可展示了；给用户看「这条有冲突，请选择保留哪个备注」在实践中只会变成噪音。失败信息只出现在「失败 N」与 `lastError`。
3. **同字段并发仍然会丢内容**。HLC 保证的是**因果顺序**，不是「两边都改同一个字段时都保留」。那是 CRDT/文合并的范畴，与「收藏列表」这个场景的收益不匹配 —— 明确按 LWW 丢弃，写进文档以免日后被当成 bug。
4. ~~匿名账号无法自行升级绑定~~ **已定：不做认领，也不做迁移**。填了 token 就是换到令牌账号那个视图，匿名期写的行留在 `anon` 账号里不再出现；界面上不为这件事加提示，也不加「迁到当前账号」的动作。`writer_device` 那一列因此不需要 —— 它唯一的用途就是把认领范围收窄到「这台设备写过的」，而认领本身已经取消。
5. **HLC 状态丢失 = 因果链断裂**。所以它必须在 DataStore（`fallbackToDestructiveMigration` 清不到）。清 DataStore（清数据/换机）等同新写者，可接受。
6. **时钟夹紧窗口是拍的**（超前 5min、滞后 10 年）。后台上线后按 `clock_skew_ms` 分布调，不要一开始就写复杂自适应。
7. **第三方数据质量**。同账号合并意味着别人灌的垃圾 url 会出现在用户墙上，账号隔离与写权校验都挡不住「有权限写但写得烂」。现在的缓解是四条：凭证 `writable_fields` 收窄（默认连 `note` 都写不了）、`provider_accounts` 授权映射要求逐账号绑定、按 provider 出 `merged`/`unchanged`/`reason_code` 指标给运维看谁在灌垃圾、解析失败仍只在那条卡片上显示一行字。**仍然没有**用户侧的「屏蔽某个来源」入口 —— 用户想清掉某服务写的所有收藏，目前只能逐条删，或走内部批量 tombstone 脚本。要不要在界面上给一个「按来源筛选/清理」，是个独立的产品决定。
8. **异步解析的长尾**。解析队列积压时，「内容信息还在后台解析」会变成事实上的长期状态，卡片上就是一片文字块没有封面。兜底必须是后台侧的：条目在队列里超过 N 天就以 `failed_reason` 落一个终态（「后台没能取到这条的内容，可以手动重新解析」），让卡片回到「解析失败 + 原因」那条已有的显示分支，而不是永远停在「还在解析」。App 侧不需要为此加任何东西 —— 终态用的就是现有那个字段。
