# 架构与性能验证

这份文档说明「为什么这样实现」以及**每一项硬指标怎么自己量出来**，避免只能靠嘴说。

---

## 1. 分层与依赖

```
UI（Compose）→ ViewModel → Repository → Room / DataStore
                                  ↘ 同步层（SyncApi → OkHttp，纯明文 JSON）
                                  ↘ 后台层（SyncManager → WorkManager → SyncWorker）
播放器（Media3 ExoPlayer + SimpleCache）独立一层，被 ViewModel 与悬浮层共用
悬浮层（Service + WindowManager + ComposeView 宿主）复用同一套 Repository / 面板 UI
```

- 依赖容器 `di/AppGraph` 用 `by lazy`，`Application.onCreate` 只做两件事：装容器、建通知渠道。
  Room 首次建库、WorkManager 初始化、DataStore 首读都被推到真正用到那一刻。
- `androidx.startup` 里的 `WorkManagerInitializer` 已从 Manifest 移除，WorkManager 由
  `Configuration.Provider` 按需初始化，避免启动期额外一次磁盘写。
- 无第三方 DI（Hilt/Koin）、无 Startup 多初始化器、无 Compose 预览依赖进入 release。

## 2. 三项硬指标怎么测

### 2.1 冷启动 ≤ 2s

```bash
adb shell am force-stop com.favkit.tablet
adb shell am start -W -n com.favkit.tablet/.ui.MainActivity
# 看 TotalTime（首次冷启动）；重复测 5 次取中位数
```

工程侧的保证：
- `App.onCreate` 不读写磁盘、不建线程池、不联网；
- 播放器和缓存目录在首次点播放时才创建；
- 标签播种（`ensurePresets`）放到 MainViewModel 初始化后的协程里，不占用启动路径；
- 列表首屏只渲染 Room 一次性查出的行 + 标签引用计数，没有 N+1 查询。

### 2.2 悬浮助手常驻内存 ≤ 80MB

```bash
# 开启悬浮助手，面板关闭（只留悬浮球）
adb shell dumpsys meminfo com.favkit.tablet
# 关注 TOTAL PSS 与 Java Heap / Native Heap；也可用
adb shell am dumpheap com.favkit.tablet /data/local/tmp/favkit.hprof
```

工程侧的保证：
- 悬浮球窗口只有一个 `ComposeView`（约几 KB 视图树），面板窗口**用完即移除**，常驻期不保留；
- 球上的同步角标只多两条 Room 的 COUNT 订阅（`pending_ops` 总数与 `attempts >= 3` 条数）加一个联网回调，
  全是写触发/事件驱动，没有新增定时器；代价是服务启动会把数据库拉起来（与主 App 共用同一个 `AppGraph` 单例，不叠加）。
  设置里关掉「悬浮球显示同步角标」就取消这三条订阅，回到「只为设置而订阅 DataStore」的最小常驻；
- 全局只有**一个** `ExoPlayer` 实例，切条目复用同一实例（`setMediaItem` 而不是重建），
  解码器与 Surface 不会重复分配；面板收起时不会残留 `PlayerView`；
- 播放器的释放只在 `MainViewModel.onCleared()` 里做一次，界面切换/进出遮罩层期间不重建实例；
  遮罩层自己就是全屏，画面只有这一处 `PlayerView`，不再有「内嵌 + 全屏」两套形态去抢同一个实例；
- 封面图用 Coil（`AsyncImage`）。它是本轮为了「主界面以视频列表为主」新引入的唯一位图开销：
  `AsyncImage` 会按测量到的卡片尺寸降采样，16:9 小卡解码出来的就是小位图，不会把原图按全屏尺寸驻留；
  悬浮助手常驻期（只留悬浮球窗口）不加载任何封面，也就不会触发位图缓存；
- 遮罩层换条那个 `VerticalPager` **只组合当前那一页**：相邻页那张封面只在拖动过程中存在、松手就随离焦销毁，
  所以整屏滑动既不会同时挂两条内容，也不会多出一个播放器实例（内容区仍然全局一个 ExoPlayer）；
  抖音式排版常见的「同时准备 3 个播放器实例的播放器池」在这里**刻意不做**：三个 ExoPlayer 就是三份解码器与缓冲，
  80MB 常驻预算撑不住，换来的是少零点几秒的起播；本项目用「非当前页只渲染封面、落定才装载」把同一件事做掉了；
- 未引入图片以外的重型 UI 库（无 Glide/Picasso、无第三方案例库）；
- 无 Handler 轮询、无定时器；唯一的循环是聚焦遮罩层可见时 500ms 一次的进度同步（纯内存读，无 IO）。

### 2.3 后台静默同步不额外耗电

```bash
adb shell dumpsys deviceidle whitelist -com.favkit.tablet   # 不加白名单，模拟真实待机
# 断网 -> 收藏 20 条 -> 恢复网络，观察
adb shell dumpsys batterystats --charged com.favkit.tablet
# 关注 wakelock 时长、network callback 注册数、AlarmManager 任务数（应为 0 个自建的周期性任务）
adb shell job list          # 只应在联网/改动时出现一个短任务
```

工程侧的保证：
- 网络状态只注册 `ConnectivityManager.NetworkCallback`，**没有任何轮询线程 / 没有周期任务**；
- 同步任务由 `WorkManager` 一次性任务承载，带 `NetworkType.CONNECTED` 约束，
  系统会把它与其它 App 的任务合并到合适窗口执行；
- 同一时刻只有一个唯一任务链（`APPEND_OR_REPLACE`），改动再密集也不会排出一串任务；
- 失败退避为线性 4s 起、最多 3 次，之后停 in 本地队列，等联网回调再动，不做后台定时器。

## 3. 平板尺寸适配的实现理由

需求写的是**物理长度**（≥10mm、≥20mm），不是 dp：

```kotlin
val physicalDpi = if (horizontal) dm.xdpi else dm.ydpi   // 真实物理 DPI
val px  = mm / 25.4f * physicalDpi                      // mm → px
val dp  = px / dm.density                               // px → dp（Compose 用）
```

- 不能用 `densityDpi`：那是厂商声明的「软件像素比」，同一块物理屏在不同 ROM 上可能给出 240/320/400dpi，
  按它换算出来的 10mm 可能是 7mm 也可能是 14mm。
- 个别驱动上报的 `xdpi` 明显异常（常见 0 或 160 假值），因此：
  1) `xdpi/ydpi` 只在 120~800 区间才采用，否则回退 `densityDpi`；
  2) 结果再夹取在 `[mm*1.2f, mm*6f]` dp 的安全区间内，
     10mm 一定落在 12~60dp，既不会退化到手指点不准，也不会顶穿视频墙布局。
- 间距：手机端推荐 8dp 基线 × 1.5 = 12dp 起（`gap_sm`），四档间距直接写在 `values/dimens.xml`
  的 `gap_xs/gap_sm/gap_md/gap_lg` 里，Compose 侧的 `TabletScale` 读的就是它们。
- 断点：`smallestScreenWidthDp` 由系统资源限定符直接命中 `values-sw600dp` / `values-sw720dp`，
  悬浮面板/抽屉宽（460/560/600dp）与四档间距、边距都在 dimens 里分档，
  每个尺寸最终取「物理 mm 下限」与「断点基线」的较大值。
- **视频墙自己按窗口宽度排布**：`VideoWall` 用 `BoxWithConstraints` 按
  `列数 = (可用宽度 - 间距) / (卡片最小宽 + 间距)` 取 2~5 列（卡片最小宽 240dp，窄屏 200dp），
  所以同一套代码在竖屏平板、横屏平板和分屏小窗里都不会出现「一屏两张大卡」或「挤成一条缝」；
  窗口宽度不再决定「几栏」——主界面只有墙 + 遮罩两层。
- **遮罩层自己就是全屏，尺寸只切「详情用哪个容器」**：`BoxWithConstraints` 里
  `sideDetails = maxWidth >= 840dp && maxWidth > maxHeight`，成立就从右侧拉出抽屉（宽 = `maxWidth × 45%`，夹在 320~560dp），
  否则用底部三档 `ModalBottomSheet`。画面本身不参与这个判断：整屏铺满、一律 `RESIZE_MODE_FIT`，横竖屏同一档显示。
  判定用的是**窗口**尺寸而非 `LocalConfiguration` 的屏幕尺寸，所以分屏、折叠屏半开这类「窗口又窄又高」的场景
  自动落回底部抽屉，不会在 700dp 宽的窗口里硬塞一条抽屉把画面挡住。
  两种容器都是模态的：开着时 `userScrollEnabled=false` 让竖向手势归抽屉，因此不再需要常驻栏，也不再需要额外的换条手势带。
- **横竖屏都可用**：`MainActivity` 用 `fullSensor`，横竖屏共用同一套遮罩层代码（只有 `sideDetails` 这一个布尔在切容器），
  悬浮窗面板用 `LAYOUT_IN_SCREEN` 按当前窗口实际宽度排版。

## 4. 状态为什么在旋转时一定不丢

三重保证，缺一都可能出问题：

1. `configChanges="orientation|screenSize|smallestScreenSize|screenLayout|keyboardHidden|navigation|density|fontScale|keyboard|uiMode|layoutDirection"`
   —— Activity **不重建**，Compose 侧的 `remember`（搜索草稿、编辑中的备注、勾选集合）与 `LazyGridState` 原样活着；
2. `rememberLazyGridState()` + 各 ViewModel 持有筛选/选择状态 —— 进程被系统回收后重建也能恢复。
   这里不能用 `rememberSaveable { LazyGridState() }`（`LazyListState` 同理）：foundation 1.7 的这些 State 没有实现 `Saveable`，
   自动 Saver 会把对象本身交给 Bundle，注册时直接抛 `IllegalArgumentException`（首帧就闪退，本项目踩过）；
3. 悬浮面板的草稿放在**进程级单例** `FloatingDraftStore`，面板窗口重建（包括服务被 `START_STICKY` 重启、
   `ACTION_CONFIGURATION_CHANGED` 重新排版）都不会清空输入；保存成功后只清链接与备注，保留标签选择习惯。

服务侧还监听 `ACTION_CONFIGURATION_CHANGED`，转屏时按新的物理尺寸重新计算悬浮球直径、边距与面板宽度并 `updateViewLayout`。

## 5. 同步协议与节奏

| 环节 | 做法 |
| --- | --- |
| 传输 | 纯明文 JSON。协议结构是 `{device_id, sent_at, ops:[…]}`，`ops` 虽是数组，但**实现里每次只放 1 条**（见下面「上传节奏」），这样 `next_wait_ms` 才能精确对应单条。**没有信封加密**：出网的只有链接、备注、标签名和来源，没有需要密文传输的数据，加一层 RSA+AES 只会让「后台解不开却回 200」这类静默丢数据的问题更难排查。完整字段与状态码语义见 `docs/同步后台接口说明.md` |
| 一条主脑 | **后台保存与解析在同一次调用里完成**，`POST /sync` 的回执直接带回调用的收藏（含 `media`）。因此协议里没有 `pending`/`status`，App 里没有「等内容」的中间态，也没有取解析结果的轮询接口。这是 v4 定下来的口径，任何改动都要先看 `docs/同步后台接口说明.md` §10 |
| 出站内容 | `UPSERT` 带 `favorite{ id, url, note, tags[], source_app, favorite_at }` 六项，`DELETE` 只带 `favorite_id`。内容信息（标题/作者/站点/说明/素材清单）永不出站，只从响应往回写。观看进度也不出栈：段号与逐段位置只存本地 |
| 成功判据 | **只认服务端明确确认的条数**：`applied + unknown_ops.size == 本次送出条数` 才算成功并出队。数量对不上就重新排队并标 FAILED，绝不清空队列 |
| 失败分级 | 4xx → `Rejected`（重试无意义，保留在队列里等用户处理，原因直接显示）；429/5xx/IO → `Retryable`（静默退避 `attempts × 8s`，3 次用尽后留在队列靠联网回调补传）；400/413 的响应体不含 `favorites/next_wait_ms`，客户端不会因此清队列 |
| 上传节奏 | 每次 worker 循环只取 **1 条**（`OPS_PER_REQUEST = 1`）。真正的「下一条什么时候能发」不在 worker 里 sleep，而是由 `SyncGate` 在出站口统一把关：三个数据接口（`POST /sync`、`GET /favorites` 分页、`POST /resolve`，含失败重试）都排队通过，上一条响应完全结束后再等 `wait` 才放下一条。`wait = 响应里的 next_wait_ms ?: 设置里的上传间隔（默认 3000ms）`，服务端因此可以按自己的解析负载动态限速。`UPSERT` 与 `DELETE` 走同一条队列、同一个闸门：批量删除确实会一条一条按间隔传，这是把节奏交给后台限速的代价，换来的是后台不会被一次几百条删除打爆；想立刻传完就把设置里的上传间隔调成 0（不限速）。 |
| 分页拉取 | 服务端是收藏的事实来源，本地 `favorites` 表只是分页缓存。冷启动发现缓存空着自动取第一页，墙离底还有两屏静默补一页，手动入口在空状态与筛选抽屉。一页 50 条，游标是上一页最后一条的 `favorite_at`（keyset，不用 OFFSET：八千条数据翻到后面每页都要重扫前八千行，且中途新增会让老条目被跳过或重复）。每页都回带 `total`（后台总数），界面靠它区分「一共就这些」和「只取回了前几页」——缺这个字段时宁可只说本地条数，也不拿已取回的页数冒充总数。**这行分数式文案只在 `has_more` 为真时说**：`total` 只在翻页时刷新，页取全了本地就是后台的镜像，还拿它跟本地条数比就会把刚删掉的那条说成「还没取回」（实测：删一条之后顶栏说出「共 20 条 · 已取回 19 条」）。取全之后一律只报本地条数 |
| 单次运行上限 | `MAX_RUN_MS = 3 分钟`，超时就交还给 WorkManager，避免长驻后台耗电 |
| 认证 | `Authorization: Bearer <token>`（设置页可填，不填则不带）；token 存 DataStore 私有目录 |
| 传输通道 | `network_security_config.xml` 放开明文，同步地址由用户自填（本机/局域网 `http://` 或公网 `https://`）。填 https 时仍走系统证书校验 |
| 备份/迁移 | `allowBackup=false` + `dataExtractionRules` 排除数据库与设置，避免收藏内容随云备份外流 |
| 悬浮层 | 只用 `SYSTEM_ALERT_WINDOW` + 静音通知；**不使用无障碍服务、不使用前台 App 查询、不申请存储权限**（缓存写在应用专属外部缓存目录，卸载即清理） |
| 备份与分享 | 系统分享入口只接收 `text/plain`，且只挑出其中的 http(s) 视频链接，其它文本丢弃 |

接口清单（与 `mock-server/server.mjs` 一一对应，字段命名改一边必须同步改另一边）：

```
POST /api/v1/sync       {device_id, sent_at, ops:[...]} -> {ok, server_time, applied, unknown_ops, favorites, next_wait_ms, error}
                                                                    favorites 每条都已内联 media{...}，直接落库渲染
GET  /api/v1/favorites?limit=&cursor=                   -> {ok, server_time, favorites, total, next_cursor, has_more}
POST /api/v1/resolve    {favorite_ids:[...]}            -> {ok, server_time, favorites, unknown_ids}   丢弃旧结果重算，favorite_at 不变
GET  /api/v1/health                                     -> 免 token，用于排查连通性
```

三条数据接口都可选带 `next_wait_ms`（`/resolve` 想控制手动重算的频率时就下发，mock 没带）；未知字段一律被 App 忽略，所以后台可以往 favorite 上多加自己的列（`device_id`、`updated_at` 就是这么来的）。

## 6. 数据模型要点

- **一条收藏 = 一行**。`favorites` 这张表同时装用户产生的四项（`url`/`note`/`sourceApp`/`favoriteAt`，也是上传载荷的全部）
  和后台解析回来的内容信息（`title`/`author`/`site`/`summary`/`segmentsJson`/`failedReason`/`resolvedAt`，只能由响应写入，本地一律不猜）。
  早期版本把它拆成 `favorites` + `video_info` 两张、内容表还带一个 `status` 列，那是「解析是异步的」这个错误前提的残留：
  两侧各一套状态、各一套计数，加上一条轮询接口，结果就是添加删除之后数字对不上、界面上「待同步」和「待解析」同时出现。
  v4 合成一张表之后，渲染不用 join，计数只剩队列一个来源。
- **没有「解析中」这个态**。只有三种情况，全部从行内字段直接读出来：`segmentsJson` 为空且 `failedReason` 为空 = 内容信息还没取回来（占位块说这句话）；
  `failedReason` 非空 = 解析失败，卡片与遮罩层显示后台给的那句原因；其余就是正常渲染。**解析失败不进任何全局计数**——
  上传成没成和内容有没有解出来是两件事，混成一个状态用户就不知道该点「重试上传」还是该改链接。
- 列表/详情/播放读的仍是本地 `favorites` 表 —— 但它的定位是「后台的分页缓存」：
  冷启动空表自动取第一页，墙离底两屏静默补页，离线能翻的就是已取回的那几页。
  软删除列 `deletedAt` 让「删除」也能进同步队列，后台确认后才物理清除（外键 `CASCADE` 顺带清理标签关联）。
- 播放走 `segments[]` 里那个 `kind=video` 段的 `url`，而不是收藏的原始链接：收藏的往往是分享页，能播的地址只有后台知道。
  顶层不再镜像 `play_url`/`cover_url`/`duration_ms` —— 镜像会和清单对不上，而清单才是正文。
- 观看进度（`segmentProgress` 逐段「段号:毫秒」+ `lastSegmentIndex`）**只在本地**，协议里没有对应字段。
  多设备同步进度要引入冲突裁决，而这条链路唯一有价值的是「接着看」，代价和收益不匹配。
- `pending_ops` 是待上传队列：载荷存**单个** op 的最终 JSON，`attempts` 记重试次数，
  `nextRetryAt` 只表示「这条什么时候才允许被取走」（退避时间）—— 两条之间隔多久已经写不到这里了，
  节奏统一由 `SyncGate` 在出站口把控，否则失败分支和翻页拉取的旁路会绕过限速；
  同一条目在未发出前被连续修改时**覆盖旧载荷**，只把最新版本传上去。
- Room `version = 4`，四张表（`favorites`/`tags`/`favorite_tags`/`pending_ops`）。开发阶段不写 Migration，直接
  `fallbackToDestructiveMigration()`：清的是本地缓存，收藏本身与内容信息都在后台，冷启动看见空表会自动向后端取回第一页，
  不是「收藏没了」。写迁移反而要猜中 Room 自己生成的 DDL，而云端 CI 只编译、从不执行迁移，猜错就是装机即崩。
- Room 不导出 schema 快照（`exportSchema = false`）：debug 与 release 两条链共用同一个 `app/schemas/` 输出目录，
  云端并行构建时会写出半截空文件，Room 读取它直接失败。真要升数据库版本时，本地临时打开导出并 review migration 即可。
- **journal 模式用 TRUNCATE，不用 WAL**。设备实测（设置页「测量存储占用」，见 §6.1）：0 条收藏、缓存也清干净之后，
  内部目录还剩 1,220,608 字节，其中 `favorites.db-wal` 420,272 + `-shm` 34,384 = 454,656，占 37%，
  而真正的 `favorites.db` 骨架只有 69,632。wal 是还没 checkpoint 的写历史，跟内容量无关，空库也占这么大。
  WAL 换来的是「写的时候还能读」，但本应用只有一个进程（manifest 里没有 `android:process`），
  写又都被 `SyncGate` 串行化，这个并发用不上；TRUNCATE 每次提交把回滚日志截干，那两个文件根本不再出现。

### 6.1 本地字节的口径与回收（一轮实测之后）

数字都来自设置页的只读探针在同一台设备上的读数，不是推算：

- **报数一律按磁盘真相**。`MediaCache.totalCachedBytes()` 原来是遍历 SimpleCache 索引（`keys` + `getCachedSpans`）求和，
  但 ROM 的「清除缓存」直接删 blob 文件、不删索引，于是出现过「磁盘上什么都没有，设置里还显示一堆」，
  而且只有重启才换数。现在改为遍历 `media-v1` 目录求文件长度；图片那侧同口径走 `cache/image_cache`，不用 `DiskCache.size`
  （它是 Coil journal 里的自报值，journal 被动过就跟磁盘对不上）。
- **打开设置就重新取一遍两个占用数**，不靠别的回调时机。在线边播边存没有总量变更通知，等它自己刷新就是「要重启才对」。
- **清空视频缓存连索引一起删**：`SimpleCache.delete(dir, StandaloneDatabaseProvider)` 之后再 `deleteRecursively`，
  否则会留下 `databases/exoplayer_internal.db` 指向已经不存在的文件。这里要说清收益是**正确性不是字节**：
  实测索引 + journal 恒为 86,016 字节，12MB 的 blob 存进去它一个字节没涨，所以别指望这条省空间。
- **删收藏即回收该条留下的字节**：图片按 URL 精确 `DiskCache.remove`（Coil 2 的磁盘键就是请求里的 data，也就是 URL；
  `size` 那只影响内存键，所以传收藏行里的原 URL 就删得到），视频段按 URI 键 `removeResource`。
  回收失败只影响字节，不能挡住删除本身，所以整段包在 `runCatching` 里、排在删除提示之后执行。
- **图片缓存上限可选，默认 32MB**（32/64/128/256/512MB，键 `image_cache_limit_mb`）。Coil 2 的默认策略是「分区剩余空间的 2%，夹在 10~250MB」，平板上基本就是 250MB 天花板，
  而实测每加一条收藏涨 ~248KB、删收藏一字节不掉 —— 这是唯一无上限增长的一项。设到 32MB 到量自动淘汰，
  另留「清空图片缓存」按钮处理老版本已经攒下的孤儿图。`DiskCache.maxSize` 是 `val`、没有运行期改容量的接口，
  所以改上限走整体重建 ImageLoader（同 MediaCache 的换档套路），目录不变、已缓存的图不丢。协议里没有小图地址，`thumb_url` 是另一件事，本轮没动。
- **「清空视频缓存」连 `locallyCached` 一起复位**（一条 `UPDATE favorites SET locallyCached = 0`）。卡片右下角那个绿点和
  遮罩信息栏那句「已缓存，离线可直接播放」读的都是这一列，它由预取成功时逐条写 true；只删 SimpleCache 不动标记，
  实测就是「缓存明明清干净了，界面还说这条能离线播」。标记是本地列，永不出站，复位它不影响任何协议字段。
- **收藏表的行数不是问题**：20 行实测 +20,480 字节，即 1,024 字节/行（含索引与空页），一千条约 1MB 加骨架。
  反复增删后 `favorites.db` 从 77,824 缩回 69,632，freelist 自己复用，**VACUUM 不需要**。
- **本轮不动的一项**：`no_backup/androidx.work.workdb` 三件 602,112 字节，占内部目录 49%，是 WorkManager 的库，
  框架没暴露它的 journal 模式；每个待传操作另加约 1.2KB。要么换掉 WorkManager，要么接受，目前按接受处理。
