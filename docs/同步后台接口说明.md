# 同步后台接口说明

这份文档是 App、另一个采集 App（下称 **B**）与收藏后台之间的**唯一**协议口径，内容与两处实现一一对应：

- App 侧：[net/Dto.kt](../app/src/main/java/com/favkit/tablet/net/Dto.kt)（数据结构）、[net/SyncApi.kt](../app/src/main/java/com/favkit/tablet/net/SyncApi.kt)（收发）、[sync/SyncManager.kt](../app/src/main/java/com/favkit/tablet/sync/SyncManager.kt)（对账与节奏）、[sync/SyncWorker.kt](../app/src/main/java/com/favkit/tablet/sync/SyncWorker.kt)（上传队列）
- 参考实现：[mock-server/server.mjs](../mock-server/server.mjs)，测试在 [mock-server/test/](../mock-server/test/)

**改任何一边都必须同步改另一边与本文。**

---

## 0. 这是什么，以及刻意不是什么

这个后台是**一个人**的收藏库：一个实例、一个令牌、一份数据。收藏的同步身份就是**链接本身（`url`）**，所以协议里没有账号、没有版本号、没有字段戳、没有冲突裁决。

写成「一个 URL 一行」之后，几件原本很复杂的事直接消失了：

- 同一链接在两处被收藏 → 天然同一行，不需要归并、不需要改主键；
- 「删了又收藏」→ 那一行本来就还在，恢复即可；
- 两台设备同时改同一条的不同字段 → 后到的那次整行赢。**这是明写的代价**，不是漏实现。个人使用场景里它意味着「我改了备注，把你刚在另一台上加的标签带回去了」，概率很低，代价是补一下标签；换来的是整个协议不需要时钟。

两条 API 面共用同一张表：App 走 `/sync`（能改能删），B 走回调（只增不改）。所以 App 看见 B 推的东西**不需要任何新接口**。

**内容的产生是异步的**：后台收到链接后先解析（每个视频选一档，长视频可选调用远程切片服务，切成一组独立可播的 mp4），**解析成功即就绪**；随后异步做上传：视频片/整片、图片、封面逐条上传存储、拿回 id。上传失败只影响备份，不影响可播可看。所以每条收藏带一个 `media_state`：

| `media_state` | 含义 | 界面表现 |
|---|---|---|
| `pending` | 后台正在解析 / 切片 | 「内容还在后台准备」 |
| `ready` | 解析完成，`media` 可用（地址由后台代理，源失效时自动回落备份） | 正常渲染 |
| `failed` | 解析失败，原因在 `failed_reason` | 「解析失败」+ 原因 |

`pending` **不是一个全局状态**：它不进顶栏、不进筛选抽屉、不进悬浮球角标，只是那条卡片/遮罩层里的一行字。全局计数只数上传队列。

## 1. 基础约定

| 项目 | 约定 |
|---|---|
| 传输 | HTTP/1.1 或 HTTP/2，`Content-Type: application/json; charset=utf-8` |
| 寻址 | App 把设置页里的接口地址当 base，直接拼接 `/sync` 等路径；地址要含前缀（如 `http://192.168.1.20:8787/api/v1`），结尾多余的 `/` 会去掉，不以 `http(s)://` 开头直接判「地址无效」不发请求 |
| 字段命名 | 全部 `snake_case` |
| 时间 | 一律 **Unix epoch 毫秒**整数（见 §1.1） |
| 认证 | 设置页填了令牌就带 `Authorization: Bearer <token>`；参考实现用 `SYNC_TOKEN` 控制，非空时数据接口校验，不匹配回 401。`/health` 与 `/meta` 永远免鉴权 |
| 媒体流 | `GET /media/<key>.<ext>` **免鉴权**：ExoPlayer 与 Coil 都不带 header，虚拟地址里的不可猜 key 就是凭据。令牌只保护数据接口 |
| 未知字段 | App 侧 `ignoreUnknownKeys = true`：后台可以多返回字段 |
| 未填字段 | App 侧 `encodeDefaults = true`、`explicitNulls = false`：非空字段都会显式出现，`null` 会被整个省略 |
| 超时 | 连接 10s、读 20s、整次调用 40s；连接失败 OkHttp 自行重试一次 |
| 体积 | 请求体上限 4MB，超出 413 |

### 1.1 `favorite_at` 与其他时间

- `favorite_at`：**用户什么时候收藏的**，客户端给，标识符是 epoch 毫秒。App 用本机墙钟（`System.currentTimeMillis()`）；B 不传时间，后台一律按**收到时刻**记。
- 后台把它夹在 `[now − 10 年, now + 5 分钟]`，非数字或 0 一律当作 `now`，**夹紧不拒**。
- 它只用于**排序与分页游标**，不参与任何胜负判断。显示按设备本地时区渲染。
- `updated_at`：**后台**这一行最后一次变化的时刻（用户字段或内容），由服务端写。对账靠它判断「这条要不要重新取内容」，客户端不写、不比较大小以外的任何东西。
- App 从不上传 `updated_at`。

### 1.2 出站节奏

所有出站请求排在同一条闸门（[net/SyncGate.kt](../app/src/main/java/com/favkit/tablet/net/SyncGate.kt)）上：

- **上传与重建内容**按设置里的「上传间隔」（默认 3000ms）占时隙，服务端可以用响应里的 `next_wait_ms` 覆盖；
- **读请求**（清单、lookup）只串行、不等待 —— 对账一次要翻十几页，让每页等 3 秒是没法用的。

## 2. 数据结构

### 2.1 `favorite`

| 字段 | 类型 | 谁写 | 说明 |
|---|---|---|---|
| `url` | string | 客户端 | **同步身份**。同一 url 在这个后台只有一行 |
| `note` | string | 客户端 | 备注，默认 `""` |
| `tags` | string[] | 客户端 | 标签**名称**，服务端自行维护名称→ID |
| `source_app` | string | 客户端 | 来源标识，如 `chrome`、`share`、`manual`；B 回调进来的固定写「第三方」 |
| `favorite_at` | number | 客户端 | 收藏时间（epoch 毫秒），见 §1.1 |
| `updated_at` | number | **服务端** | 这一行最后一次变化的时刻，对账用 |
| `media_state` | string | **服务端** | `pending` / `ready` / `failed` |
| `failed_reason` | string | **服务端** | 非空表示内容没做出来，这句原因直接给用户看 |
| `media` | object / null | **服务端** | 内容信息，见 §2.2；`pending` 时为 null |

App 的本地 `id`（UUID）**不出站**：它只是本机句柄，标签外键、播放队列、列表都靠它。

### 2.2 `media`

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | string | 内容标题。App 不用链接猜标题，标题只来自这里 |
| `author` / `site` | string | 作者 / 站点显示名 |
| `summary` | string | 一句话说明，卡片上两行、遮罩层里全文 |
| `segments` | object[] | 素材清单，见 §2.3 |
| `failed_reason` | string | 非空表示内容没做出来，此时 `segments` 必为空 |
| `resolved_at` | number | 内容就绪的时刻 |

### 2.3 `segments[]` 元素

| 字段 | 类型 | 说明 |
|---|---|---|
| `index` | number | 段序号；App 先按它排序再重编号，跳号也不乱 |
| `kind` | string | `image` / `video`，其它值一律按 video 处理 |
| `title` | string | 段自己的标题 |
| `cover_url` | string | 视频段封面的**相对虚拟地址**；图片段留空 |
| `url` | string | 视频段/图片段的**相对虚拟地址**（`/media/<key>.mp4`、`.jpg`），由后台代理；真实地址不出后台 |
| `duration_ms` | number | 视频时长；图片 0 |
| `quality` | string | 清晰度，如 `1080P`；图片留空 |
| `store_id` | string | 该段的存储备份 id（App 不读，排障用）；上传完成前为空 |

顺序即展示顺序：卡片首图取 `segments[0]`，所以有视频段时把它排前面。

素材地址是**相对路径**，相对的是 App 设置里的接口地址（含 `/api/v1`）：App 把它拼成绝对地址后再交给播放器/Coil。长视频被切成多个独立 mp4，**每片就是一个段**；播完一片会自动接下一段，「整片缓存」等于逐片预取。旧后台留下的 `.m3u8` 地址仍按「切片视频」处理，不给整片缓存。

## 3. 接口清单

### 3.1 `POST /sync` —— App 上传（一次一条）

```json
{
  "device_id": "tab-3f2a9c1d7b40",
  "sent_at": 1763122500000,
  "slice_rule": { "mode": "size", "bytes": 2000000, "align": "keyframe" },
  "ops": [
    { "type": "UPSERT",
      "favorite": { "url": "https://www.bilibili.com/video/BV1xx411c7mD",
                    "note": "周末看", "tags": ["待看"], "source_app": "chrome",
                    "favorite_at": 1763122400000 } }
  ]
}
```

`slice_rule` 可省略；带了就按条落库，只影响这条的新解析。只收 `{mode:"size",bytes}`（App 设置页按 1–1024MB 输入；mock 仍按切片服务的 64KB–1GB 校验），切点固定按关键帧对齐。`bytes` 同时是「长视频」的判定阈值与每片大小。B 回调等没有规则的入口用后台默认值。

```json
{ "type": "DELETE", "url": "https://www.bilibili.com/video/BV1xx411c7mD" }
```

写入语义：

- **UPSERT**：按 `url` 命中就覆盖那四列（url 不可变），不命中就新建并排一次解析；内容四列与状态一概以后台为准。
- **DELETE**：按 `url` 删行。**不存在也算成功**（目标状态已达成）。
- **一次只接受一条 op**，多于一条回 400。
- `slice_rule` 只在新行落库，改已存在条目的规则不会自动重切；要重切请用 `/resolve`。

成功响应：

```json
{
  "ok": true,
  "server_time": 1763122500123,
  "applied": 1,
  "favorites": [ { "url": "…", "note": "周末看", "tags": ["待看"], "source_app": "chrome",
                   "favorite_at": 1763122400000, "updated_at": 1763122500100,
                   "media_state": "pending", "failed_reason": "", "media": null } ],
  "next_wait_ms": 3000,
  "error": ""
}
```

- `applied`：确实落库的条数。App 的成功判据是 **`applied == 1`**，对不上就留在队列并标红——早期版本在这一步删过队列条目，导致静默丢数据。
- `favorites`：这条的最新状态。新建/改备注之后通常是 `pending`，解析完成才 `ready`（不再等备份）。
- `next_wait_ms`：服务端建议的下一条等待时间（缺省用本地设置）。
- 4xx：整请求拒绝，`error` 是给人看的中文原因（会显示在 App 里）。

### 3.2 `GET /favorites` —— 两档列表

```
GET /favorites?limit=50&cursor=…             # 整行档：每条带 media
GET /favorites?fields=min&limit=300&cursor=… # 清单档：只有 url / favorite_at / updated_at / media_state
```

响应：

```json
{ "ok": true, "server_time": 1763122500123,
  "favorites": [ … ], "total": 1280,
  "next_cursor": "1763120000000.https%3A%2F%2F…", "has_more": true }
```

- 顺序是 `favorite_at` 降序、并列时 `url` 升序；游标是不透明串 `<favorite_at>.<url 编码>`，客户端原样回传。
- 游标不合法 **明确 400**，不退回第一页（退第一页会让翻页方每轮拿到同一页）。
- `limit` 上限 1000。
- **清单档只占整行档约 14% 的字节**（实测 22 条样本：整行 1132 B/条，清单 160 B/条）。一万条翻一遍约 1.5MB / 10 个请求，整行档是 10.8MB / 50 个请求 —— 对账因此永远先翻清单。

### 3.3 `POST /favorites/lookup` —— 批量取内容

```json
{ "urls": ["https://…", "https://…"] }     // 一次最多 200 个
```

```json
{ "ok": true, "server_time": …, "favorites": [ … 带 media … ] }
```

只回真实存在的那些。差集算完之后，App 只为「新增 + 变更」的链接发这一请求。

### 3.4 `POST /resolve` —— 重新准备内容

```json
{ "urls": ["https://…"], "slice_rule": { "mode": "size", "bytes": 60000000 } }
```

`slice_rule` 可省略：带了就按新规则重切，不带沿用这条收藏当初的规则。后台丢弃旧结果、重排一次解析，**立刻返回**（这条回到 `pending`，旧内容保留到新内容就绪），未知 url 进 `unknown_urls`。这是全站唯一主动重建内容的入口，只由用户在遮罩层里点。

### 3.5 `GET /health` / `GET /meta`

- `/health`：免鉴权存活检查，报 `favorites / pending / failed / jobs` 计数。
- `/meta`：免鉴权能力自述（游标样式、清单字段、lookup 上限、状态取值、节奏参数）。App 不调用，联调第一步用。

### 3.6 `GET /media/<key>.<ext>` —— 媒体代理（免鉴权）

App/ExoPlayer/Coil 直接请求「设置里的接口地址 + 段/封面的相对路径」。后台按 key 取出一条 asset：

1. 解析虚拟 key（key 里带内容版本），取出这条 asset 的源地址、切片区间或整片、存储 id；
2. 校验源地址：HEAD 比对解析时的 `etag` 与文件大小，结果按源地址缓存 60 秒（HEAD 不被支持时用 `Range: 0-0`）；
3. 源可用 → 按客户端 `Range` 代理回源；视频单片 = `init` 段 + 源文件字节区间；整片/图片/封面直接透传；
4. 源失效、取源失败或 `etag/大小` 不一致 → 读该 asset 的 `store_id` 备份（同一份 `init+区间` 或整文件）；
5. 两边都没有 → 502。

换片大小/换源/换切片后内容版本变化，地址随之变化，App 不会继续命中旧片；同样的解析结果重放时地址稳定。

支持 `Range` / `206`、`HEAD`，透传 `Content-Type`、`Content-Length`、`Content-Range`，固定 `Cache-Control: no-store`。只服务已登记的 key，不是任意 URL 转发；公网部署建议配置 `MEDIA_KEY_SECRET`，让 key 不可猜且可轮换。

### 3.7 `POST /ingest/callback` —— B 的回调入口

B 的接口与数据格式是**对方定死的**，我们只做适配。链路是：

```
后台部署时 ──一次人工注册（回调地址）──▶ B
B 侧产生收藏 ──POST 固定格式──▶ 我们的回调 ──▶ 落库（url 判重、只增不改）+ 排解析
                                           └──▶ 回 2xx
```

规则：

1. **只增不改**：url 已存在就一个字都不动（你的备注、标签不会被它覆盖）；不存在就新建。
2. **不收时间**：B 不传时间，收藏时间 = 后台收到它的时刻。
3. **来源固定**写 `第三方`（`INGEST_SOURCE_APP` 可改）。
4. **逐条独立**：一个请求里 N 条，逐条处理；非法链接只跳过那一条（记一行日志），**不连累同批**。
5. **应答**：处理完就 2xx，`{"ok":true,"received":N,"created":..,"existed":..,"invalid":..}`。坏数据也算「处理过了」——对方只看结果，报错只会让它重发同一条坏数据。只有我们自己落库出错才回 5xx。
6. **删掉之后再推会复活**：后台不存墓碑，删就是真删，B 再推一次等于又收藏了一次。
7. 载荷形状的适配点在 [server.mjs](../mock-server/server.mjs) 的 `extractIngestItems`：目前认 `{links:[…]}`、`{items:[{url}]}`、直接一个数组三种。**接上 B 的真实格式时只改这一个函数**，别把形状判断散进业务代码。

## 4. 内容解析、上传与代理

后台收到链接后不等内容：它立刻落库，并把这条放进 `jobs` 队列。

- **parse（解析）**：单线程跑一遍「选档 → 探体积 → 可选切片」。每个视频选一档：高度不超过 `UPLOAD_MAX_HEIGHT`（默认 1080）的最高可达档；范围内都不可达时取最小的范围外档；全不可达仍保留整片一段，不丢内容。选中视频体积 > `slice_rule.bytes`（默认 2MB）才调远程切片服务，拿回每片的 `init` 段、源文件区间与时长；否则整片；切片失败降级整片。解析成功即写 `media`、置 `ready`，不再等上传。
- **一条 asset = 一个段**：视频片/整片、图片、封面都各是一条 asset；App 展示、上传、代理读同一份记录。视频段用 `cover_key` 引用自己的封面 asset。
- **upload（上传）**：解析成功后再排一次上传任务，遍历这条收藏的全部 asset（含封面）：
  - 每片/每个整片/每张图/每张封面各拿一个存储 id；`store_id` 写回 asset；
  - 上传是本地目录模拟（`STORE_DIR`），真实后台只替换存储适配层；
  - 单条失败重试 `UPLOAD_MAX_ATTEMPTS`（默认 3）次、间隔 `UPLOAD_RETRY_MS`；用尽后行上 `upload_state` 记 `partial` / `failed`，**收藏本身仍是 `ready`**。
- **内容版本**：虚拟 key 带整条收藏的内容指纹（源身份 + 切片区间/init + 图片/封面地址）。切片边界、分辨率档、源、解析结果一变，地址就变；同样的解析结果重放时地址稳定。
- **代理**：App 只拿相对虚拟地址。请求时先校验源地址，可用就代理回源，失效就读该 asset 的存储备份，见 §3.6。
- **不做解析缓存**：收藏以 url 为主键，重复收藏/删后重藏会重新解析一次；换来的是少一套缓存状态与失效逻辑。
- **解析失败重试** `TRANSFER_MAX_ATTEMPTS`（默认 3）次、间隔 `TRANSFER_RETRY_MS × 次数`，用尽后落 `failed` + 原因，之后只能靠用户点「重新准备」。
- **重启续跑**：`jobs` 随数据落盘，进程重启后接着跑；`upload_state=pending` 的行会补排上传。
- 就绪时 `updated_at` 会变，所以 App 下一次对账一定能看见它。

## 5. 校验与错误

`POST /sync` 是**全有或全无**（一次一条，拒绝就是整请求失败），错误消息带定位：

| 情况 | HTTP | `error` |
|---|---|---|
| 请求体不是 JSON / 不是对象 | 400 | `请求体不是合法 JSON` / `请求体必须是 JSON 对象` |
| 缺 `device_id` | 400 | `缺少 device_id` |
| `ops` 不是数组 / 不是 1 条 | 400 | `ops 必须是数组` / `这个后台一次只接受一条操作` |
| `type` 不是 UPSERT/DELETE | 400 | `…的 type 只支持 UPSERT / DELETE` |
| UPSERT 缺 `favorite` / `favorite.url` | 400 | `…缺少 favorite 对象` / `…缺少 favorite.url` |
| `url` 不是合法 http(s) | 400 | `…的 favorite.url 不是合法的 http(s) 地址` |
| `tags` 不是字符串数组、`note` 类型不对 | 400 | `…必须是字符串数组` / `…必须是字符串` |
| `slice_rule` 形状/范围不合法 | 400 | `slice_rule 只支持 {mode:"duration",seconds} 或 {mode:"size",bytes}`（App 只发 size） |
| DELETE 缺 `url` | 400 | `…（DELETE）缺少 url` |
| 请求体 > 4MB | 413 | `请求体超过 4MB 上限` |

App 侧对状态码的处置（[SyncWorker.kt](../app/src/main/java/com/favkit/tablet/sync/SyncWorker.kt)）：

| 服务端表现 | App 行为 |
|---|---|
| 200 且 `applied==1` | 出队、标绿；回执里的行回填（内容多半还是 pending） |
| 200 但 `applied!=1` | **留在队列**、标红 FAILED，原因写「后台确认条数不符」 |
| 4xx | 留在队列、标红 FAILED，显示后台那句中文；不自动重试 |
| 429 / 5xx / IO | 静默退避（`attempts × 8s`），用尽后留队列等下次触发 |
| 落库失败 | 不销账、标红，`lastError` 写明哪个计数没对上 |

## 6. App 侧：同步怎么跑

### 6.1 上传

本地改动先写 Room（离线立刻可见），再入 `pending_ops`，`SyncWorker` 串行逐条发：

- 一次一条（`OPS_PER_REQUEST = 1`），两条之间由闸门控节奏；
- 同一链接只留最后一次动作（改备注后又删，队列里只剩 DELETE）；
- 单轮最多跑 3 分钟，跑不完交回 WorkManager 线性退避，**无常驻定时器、无轮询**；
- 开头有一次兜底扫尾：`badge=QUEUED` 却没有对应 op 的行（进程在两笔事务之间被杀）补进队列。

### 6.2 对账：翻清单做差集

触发点只有两个：**worker 把队列跑到空**、**进前台**（`MainActivity.onResume`）。联网回调只补传，不对账。

一轮的步骤：

1. 翻完整的清单（300/页，最多 40 页）；
2. 本地没有的、或 `updated_at` 与本地存的不一样的 → 收进「要取内容」；
3. 分批 `lookup`（200/批）把这些内容取回来落库；
4. **最后**才判删除：本地有、远端没有、而且这行没有未上传改动（badge 不是 SYNCED 的都算脏）→ 物理删除（连段进度一起）。

三条硬规则：

- **中途任何一页失败 → 直接结束，什么都不删。** 拉不全就当成「后台把剩下的都删了」是这套方案唯一可能丢数据的路。
- **脏行永远不删**：它的收敛归上传链路管。
- 失败会在屏幕底部的悬浮提示条上说一句，带「重试」；下一次对账成功自动消失。

> 为什么不做增量游标：这个后台没有墓碑表，增量一旦跳过没变的行，就再也发现不了「别的设备删了这条」——除非把墓碑表加回来，而那正是这次砍掉的东西。清单档足够便宜，全量差值就够了。

### 6.3 内容没就绪时

- 卡片与遮罩层显示「内容还在后台准备」，**不给转圈**（这条链路没有轮询，转圈是兑不了的承诺）。
- **打开**一条还没就绪的收藏时，App 单独问一次（`lookup` 单条）。失败只在提示条上说「刷新失败」，**库里那行一个字不动**，继续停在原来的状态。
- 失败的行显示「解析失败」+ 后台原因，出口是详情里的「重新准备」。

### 6.4 状态口径

- 全局只有三枚词：**离线 / 待同步 N / 失败 N**，且**只数上传队列**。
- 它们统一显示在**屏幕底部居中的悬浮提示条**上，优先级：临时回执（3.5 秒）> 对账失败 > 单条刷新失败 > 离线 > 上传失败 > 待同步。
- 顶栏只剩「待同步 N」与转圈——那是进度，不是问题。

## 7. App 本地存储（Room v6）

`favorites` 一张表：用户四列 + 内容列 + 两列后台状态 + 本地状态。

| 列组 | 列 | 归属 |
|---|---|---|
| 上传的 | `url`、`note`、`sourceApp`、`favoriteAt` | App 产生，`POST /sync` 送出 |
| 后台的内容 | `title`、`author`、`site`、`summary`、`segmentsJson`、`failedReason`、`resolvedAt` | 只从响应写回 |
| 后台的状态 | `serverUpdatedAt`、`mediaState` | 只读，对账与占位态用 |
| 本地状态 | `id`（本地句柄，不出站）、`badge`、`locallyCached`、`deletedAt` | 只在 App |
| 旧列 | `segmentProgress`、`lastSegmentIndex` | 旧版本记录过播放进度；现在不写不读，列保留以免动数据库版本 |

- `url` 上建唯一索引：同一链接只能有一行，这是「url 即身份」在本机的落点。
- `pending_ops.favoriteId` 存的是**本机行 id**（句柄），出站身份在载荷的 `url` 里。
- 开发阶段不写迁移，`fallbackToDestructiveMigration()`：清的是本地缓存，收藏与内容都在后台。

## 9. 手工联调

```bash
BASE=http://127.0.0.1:8787/api/v1
TOK='-H authorization:Bearer\ <token>'   # 未设 SYNC_TOKEN 时省略

# 1) 存活与能力
curl -s "$BASE/health"; curl -s "$BASE/meta"

# 2) 上传一条：applied=1，回执 media_state 应为 pending
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' $TOK -d '{
  "device_id":"tab-debug","sent_at":1763122500000,
  "ops":[{"type":"UPSERT","favorite":{
    "url":"https://www.bilibili.com/video/BV1xx411c7mD",
    "note":"调试","tags":["算法"],"source_app":"manual","favorite_at":1763122400000}}]}'

# 3) 清单：看 updated_at 变化表示解析完成
curl -s "$BASE/favorites?fields=min&limit=10" $TOK

# 4) 取内容
curl -s -X POST "$BASE/favorites/lookup" -H 'content-type: application/json' $TOK \
  -d '{"urls":["https://www.bilibili.com/video/BV1xx411c7mD"]}'

# 5) 代理取素材：段地址是相对路径（/media/...），直接接在 $BASE 后面
#    curl -s -D - -H 'Range: bytes=0-1023' "$BASE/media/<key>.mp4" -o /tmp/slice.bin

# 6) 重新准备（可带新的切片规则）
curl -s -X POST "$BASE/resolve" -H 'content-type: application/json' $TOK \
  -d '{"urls":["https://www.bilibili.com/video/BV1xx411c7mD"],"slice_rule":{"mode":"size","bytes":60000000}}'

# 7) 删除（不存在也回 applied=1）
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' $TOK \
  -d '{"device_id":"tab-debug","sent_at":1763122501000,"ops":[{"type":"DELETE","url":"https://example.com/x"}]}'

# 8) B 回调：只增不改 + 非法链接单独计数
curl -s -X POST "$BASE/ingest/callback" -H 'content-type: application/json' \
  -d '{"links":["https://example.com/a","not-a-url"]}'
```

App 侧验收：保存后卡片立即出现（黄点）→ 传完变绿 → 内容由「还在准备」变成可看；拔网线保存仍可见，恢复后不点任何按钮自动补传；另一台设备删一条，本机回前台后那张卡自己消失。

## 10. 明确的边界

1. **不做多账号**。一个实例 = 一个人的库。要给家人另开，就再起一个实例。
2. **不做字段级合并**。两台设备同时改同一条的不同字段，后到的整行赢（§0）。
3. **不做墓碑表 / 增量游标**。删除靠「清单里没有」判定，见 §6.2 的三条硬规则。
4. **不记录播放进度**。App 不保存看到哪儿，也不上传；每次打开都从头开始。
5. **不做 B 的异步解析队列**。B 推一条就解析一条，个人量级足够；解析结果同样落 `media`，App 看到的是同一条链路。
6. **不做客户端时钟参与决胜**。时间只用于排序与显示。
7. **切片视频用独立 mp4，不用 HLS**。每片是一段可独立播放的 mp4，App 播完自动接下一段；「整片缓存」= 逐片预取。旧后台留下的 `.m3u8` 仍不给整片缓存。
8. **媒体代理免鉴权**。令牌只保护数据接口；媒体流靠虚拟地址里的不可猜 key，公网部署请配置 `MEDIA_KEY_SECRET`。
