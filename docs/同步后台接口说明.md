# 同步后台接口说明

本文是 App 与收藏后台之间**唯一**的协议文档，内容与两处实现一一对应：

- App 侧：[net/Dto.kt](../app/src/main/java/com/favkit/tablet/net/Dto.kt)（数据结构）、[net/SyncApi.kt](../app/src/main/java/com/favkit/tablet/net/SyncApi.kt)（收发与状态码判定）、[sync/SyncWorker.kt](../app/src/main/java/com/favkit/tablet/sync/SyncWorker.kt)（成功判据与节奏）
- 参考实现：[mock-server/server.mjs](../mock-server/server.mjs)（可直接跑起来当联调靶子）

**改任何一边都必须同步改另一边，并更新本文。** 协议刻意是纯明文 JSON：出网的只有链接、备注、标签名、归档桶和播放进度，没有需要密文传输的数据；上一版加过 RSA+AES 信封，结果是「后台解不开却回 200」变成静默丢数据，排查代价远大于收益。传输加密交给部署环境的 TLS（后台换成 `https://` 即可，App 无需改动）。

---

## 1. 基础约定

| 项目 | 约定 |
|---|---|
| 传输 | HTTP/1.1 或 HTTP/2，`Content-Type: application/json; charset=utf-8` |
| 寻址 | App 把「设置页里的接口地址」当作 base，直接拼接 `/sync`、`/favorites` 等路径。因此地址要**填到包含前缀的完整 base**，例如 `http://192.168.1.20:8787/api/v1`；结尾多余的 `/` 会被去掉；不以 `http://`/`https://` 开头会被判为「同步地址无效」，请求根本不发 |
| 字段命名 | 全部 `snake_case`（`device_id`、`favorite_at`、`next_wait_ms`…） |
| 时间 | 一律 Unix 毫秒时间戳。`sent_at` 是客户端本地时间，**服务端不要拿它做排序或去重依据** |
| 认证 | 设置页填了令牌时，App 每个请求都带 `Authorization: Bearer <token>`；未填则不带该头。参考实现用环境变量 `SYNC_TOKEN` 控制：非空时数据接口校验，不匹配回 401 |
| 附加请求头 | `X-Device-Platform: android-tablet`（服务端可忽略，仅便于排查） |
| 未知字段 | App 的 JSON 解析器 `ignoreUnknownKeys = true`：**服务端可以多返回字段**（如 `updated_at`、`device_id`），App 会忽略，不会报错 |
| App 发出的字段 | `encodeDefaults = true`、`explicitNulls = false`：所有非空字段都会显式出现，值为 `null` 的字段会被整个省略 |
| 超时 | 连接 10s、读 20s、整次调用 40s；连接失败由 OkHttp 自行重试一次 |
| 体积 | 参考实现对请求体设 4MB 上限，超出回 413（App 视为永久失败，见 §5） |

免令牌的两个接口（`/health`、`/stats`）是给人在浏览器/curl 里自查用的，App 不会调用它们。

## 2. 数据结构

### 2.1 `favorite` —— 用户产生的数据（客户端生成 ID）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 收藏的唯一标识，由 App 生成（UUID 字符串）。服务端以它为幂等键 |
| `url` | string | 是 | 用户收藏的**原始链接**。注意它不等于可播放地址：一条链接可能解析出多个素材，可播地址在 `video.media[]` 的各段 `url`（顶层 `play_url` 只镜像第一个可播段） |
| `note` | string | 否（默认 `""`） | 用户备注（含手写转成的文字） |
| `tags` | string[] | 否（默认 `[]`） | 标签**名称**数组，不带标签 ID；服务端自行维护名称→ID |
| `source_app` | string | 否（默认 `""`） | 来源应用标识，如 `chrome`、`share`、`manual` |
| `favorite_at` | number | 否（默认 0） | 收藏时间（毫秒）。App 缺省时参考实现按 `Date.now()` 补 |
| `bucket` | string | 否（默认 `INBOX`） | 归档桶枚举：`INBOX`（待看）/ `ARCHIVED`（已归档）/ `STARRED`（精选）。当前 App 已去掉归档功能，**一律上传 `INBOX`**；字段保留是为了不改表结构、不破坏已有后台 |
| `last_position_ms` | number | 否（默认 0） | 上次看到的进度。多设备间以「更靠前的位置」为准，App 本地不会被后台覆盖。注意它只是**最后看的那一段**的进度：段序号（`media` 里的第几段）与逐段进度只存在 App 本地（Room v3 的 `segmentProgress`/`lastSegmentIndex`），本协议不上传，所以换设备后是「同进度、从头一段开始」 |

服务端在返回 `favorite` 时可以附加自己的字段（参考实现会加 `device_id`、`updated_at`）。

### 2.2 `video` —— 后台解析出来的内容信息（**不要**由客户端提供）

一条收藏链接解析回来的**不一定是单个视频**：可能是「图＋视频」「纯图集（1~N 张）」或「多段视频」。
所以内容清单在 `media[]`，另有一句给人看的 `summary`。

| 字段 | 类型 | 说明 |
|---|---|---|
| `favorite_id` | string | 归属的收藏 ID。留空时 App 用请求上下文里的那个 ID 兜底 |
| `title` | string | 内容标题。App 不再用链接猜标题，标题**只能**来自这里 |
| `cover_url` | string | 首图地址（http/https），App 用 Coil 异步加载并磁盘缓存 |
| `author` | string | 作者/UP 主 |
| `site` | string | 站点显示名 |
| `duration_ms` | number | **所有视频段时长之和**；未知填 0（填 0 时 App 的进度条不可拖动） |
| `play_url` | string | **首个视频段的可播地址**（mp4 或 m3u8）。纯图集时为空；为空或 `status != ready` 时 App 拒绝播放 |
| `quality` | string | 清晰度标签，如 `1080P`（取首个视频段） |
| `resolved_at` | number | 解析完成时间（毫秒） |
| `status` | string | `pending` / `ready` / `failed`。**其它值一律按 `pending` 处理** |
| `error` | string | `failed` 时给用户的中文原因 |
| `is_mock_source` | boolean | 参考实现恒为 `true`，用来提醒自己「这条数据是假的」；真实后台可省略（默认 `false`） |
| `summary` | string | **一句话说明文案**：后台读懂内容后写给用户看的「这条链接里有什么、建议怎么看」。App 把它当内容主体 —— 卡片上两行，聚焦层里全文 |
| `media` | object[] | 素材清单，见 §2.3。缺省或空数组时 App 用上面的 `title/cover_url/play_url/duration_ms` 兜底成「单个视频段」，所以**老后台不给 `media` 也照常能播** |

### 2.3 `media` 元素 —— 一个可独立浏览或播放的素材段

| 字段 | 类型 | 说明 |
|---|---|---|
| `index` | number | 段序号。App 先按它排序，再重新编号成 `0..n-1`，所以**跳号或从 1 起算都不会打乱顺序** |
| `kind` | string | `image` / `video`。大小写不敏感；**其它值一律按 `video` 处理**（宁可给一个播不了的段，也不把图片当视频播） |
| `title` | string | 该段自己的标题，如 `图 2`、`哔哩哔哩视频 1` |
| `cover_url` | string | 视频段的封面图；图片段留空（它自己就是要看的那张图） |
| `url` | string | `video` 段是可播地址，`image` 段就是图片本身。**同一个字段两种用途**，App 靠 `kind` 区分 |
| `duration_ms` | number | 视频段时长；图片段填 0 |
| `quality` | string | 视频段清晰度；图片段留空 |

顺序即展示顺序：App 的视频墙卡片拿 `media[0]` 当首图，所以**有可播段时请把视频段排在前面**，纯图集按阅读动线排（第一张最抓人）。参考实现就是这么做的。

### 2.4 `op` —— 一次变更

```jsonc
{ "type": "UPSERT", "favorite": { "id": "...", "url": "...", /* ... */ } }
{ "type": "DELETE", "favorite_id": "..." }
```

- `type` 只支持 `UPSERT` / `DELETE`，其它值 → 400。
- `UPSERT` 必须带完整 `favorite` 对象（整条覆盖，不是增量 patch）。
- `DELETE` 必须带非空 `favorite_id`。
- App 用 `explicitNulls=false` 序列化，所以 UPSERT 请求里**不会**出现 `favorite_id: null` 这种键。

## 3. 接口清单

### 3.1 `POST /sync` —— 上传变更（App 唯一的写接口）

请求：

```json
{
  "device_id": "tab-3f2a9c1d7b40",
  "sent_at": 1763122500000,
  "ops": [
    {
      "type": "UPSERT",
      "favorite": {
        "id": "9f1c0a5e-2b7d-4c8a-9f3e-6d0a1b2c3d4e",
        "url": "https://www.bilibili.com/video/BV1xx411c7mD",
        "note": "周末看",
        "tags": ["待看", "算法"],
        "source_app": "chrome",
        "favorite_at": 1763122400000,
        "bucket": "INBOX",
        "last_position_ms": 0
      }
    }
  ]
}
```

成功响应（200）：

```json
{
  "ok": true,
  "server_time": 1763122500123,
  "applied": 1,
  "unknown_ops": [],
  "favorites": [ { "id": "...", "url": "...", "device_id": "tab-3f2a9c1d7b40", "updated_at": 1763122500100 } ],
  "videos": [ {
    "favorite_id": "...", "title": "哔哩哔哩视频 · a3f19c", "status": "ready",
    "summary": "UP 主实测 3 款降噪耳机，先看 8 分钟对比视频，再对照 4 张频谱图。",
    "play_url": "https://.../x36xhzz.m3u8", "cover_url": "https://picsum.photos/seed/a3f19c2d/640/360",
    "duration_ms": 1140000, "quality": "1080P",
    "media": [
      { "index": 0, "kind": "video", "title": "耳机对比实测", "cover_url": "https://picsum.photos/seed/a3f19c2d/640/360", "url": "https://.../x36xhzz.m3u8", "duration_ms": 480000, "quality": "1080P" },
      { "index": 1, "kind": "video", "title": "佩戴舒适度", "cover_url": "https://picsum.photos/seed/a3f19c2d-1/640/360", "url": "https://.../BigBuckBunny.mp4", "duration_ms": 660000, "quality": "720P" },
      { "index": 2, "kind": "image", "title": "低频频谱", "cover_url": "", "url": "https://picsum.photos/seed/a3f19c2d-2/1280/720", "duration_ms": 0, "quality": "" }
    ]
  } ],
  "next_wait_ms": 3000,
  "error": ""
}
```

字段语义：

- `applied`：**服务端确实落库的条数**。UPSERT 成功计 1，删除已有条目计 1。
- `unknown_ops`：要删但服务端没有这个 ID 的 `favorite_id` 列表。**这不是错误**：多设备场景下别的设备已经删过，属正常收敛，App 一样会清掉本地数据。
- `favorites` / `videos`：本次涉及条目的最新状态，其中 `videos` 是「后台对这批链接的解析结果」。App 会直接落库，所以后台没解析完就回 `status: "pending"`，别凭空造 `ready`。列表卡片与遮罩层展示的内容以 `summary` + `media[]` 为准，顶层的 `title/cover_url/play_url/duration_ms/quality` 只是 `media[0]`（第一个可播段）的镜像，供老版本 App 和只有一条视频时使用。
- `next_wait_ms`：**服务端建议「下一条上传前等多久」**。App 每次请求只带一条 op，这个值因此精确对应单条的节奏。缺省（不下发该字段或为 null）时 App 退回设置页的「上传间隔」（默认 3000ms，填 0 表示不限速）。参考实现默认固定 3000ms，可用 `UPLOAD_WAIT_JITTER_MS` 按下发序号抖动，验证 App 是否真的读服务端的建议而不是只用自己的配置。
- `error`：失败原因（中文，会直接显示在 App 列表/设置里）。

失败响应示例（400，`Content-Type` 仍是 JSON）：

```json
{ "ok": false, "error": "第 1 条操作（UPSERT）缺少 favorite.id", "applied": 0, "unknown_ops": [] }
```

**服务端实现必须守住的不变式：`applied + len(unknown_ops) == len(ops)`。** App 的成功判据就是这个等式；不等时条目留在队列并标红（详见 §5）。参考实现在内部也做了同一断言，对不上宁可抛 500，也不回一个「看起来成功」的空响应。

### 3.2 `GET /favorites?limit=&cursor=` —— 分页拉取收藏

服务端是收藏的事实来源，App 本地那张表只是**分页缓存**：

- 冷启动发现本地缓存为空（换机、清数据、破坏性迁移）→ 自动取第一页，不用用户点；
- 视频墙滚到离底还有两屏 → 静默取下一页；
- 空列表/抽屉里的「从后台加载我的收藏」是同一件事的手动入口。

请求：`GET /favorites?limit=50`，续页时带上 `&cursor=<上一页返回的 next_cursor>`（App 会对游标做 URL 编码）。

响应：

```json
{
  "ok": true,
  "server_time": 1763122500123,
  "favorites": [ /* favorite 对象数组，最多 limit 条 */ ],
  "videos": [ /* video 对象数组，只含本页 favorites 里存在的 favorite_id */ ],
  "total": 1280,
  "next_cursor": "1763120000000",
  "has_more": true
}
```

- 请按 `favorite_at` **倒序**返回，游标建议就用上一页最后一条的 `favorite_at`（键集分页）。用偏移量的话，翻页途中新收藏一条就会把下一页顶掉一条；键集不会，重复取到的那条 App 按 `id` 去掉。
- `total`：**这个账号下的收藏总数**（不含已删除），每页都带同一个值。App 拿它区分「一共就这些」和「本地只取回了前几页」：顶栏说「后台共 1280 条 · 已取回 50 条」，墙头说「已取回 50 / 1280 条」。不下发或为 0 时 App 退回只显示本地条数，不会编出一个总数。
- `next_cursor` 为空或 `has_more=false` 都表示到底了，App 就不再补页（列表尾部显示「到底了」）。
- `has_more=true` 却返回 0 条，App 按到底处理，避免无休止地滚动补页。
- `videos` 允许缺失或不包含某条（该条在 App 里显示「待解析」，条目级仍能看到，全局只计入「待同步」一项）。
- 4xx → 手动入口提示「从后台加载失败：后台拒绝：HTTP xxx」；网络层失败 → 提示「从后台加载失败：<IO 原因>」。自动补页失败不弹提示，只把尾部的加载位收回去。这两个请求都只读，不会污染上传队列。

### 3.3 `GET /videos?ids=` —— 取解析结果（把 `pending` 变 `ready`）

后台解析是异步的，App 靠这个接口取结果。请求形如 `GET /videos?ids=aaa,bbb,ccc`（逗号分隔，**不做 URL 编码**，因为 ID 是 UUID 字符集；真实后台若要支持上千条 ID，请保证容忍长查询串或与 App 侧约定分批）。

App 调用时机：主界面初始化时、以及「队列排空但还有条目停在 pending」这一状态刚出现时（事件驱动，不轮询也不定时），快速收藏保存成功后另走一次。每次只把 `status != READY` 的条目组成 ID 列表带上。

响应：

```json
{ "ok": true, "server_time": 1763122500123, "videos": [ /* video 数组 */ ], "unknown_ids": [] }
```

- 参考实现对**认识的 ID 返回其现状，不认识的 ID 返回一条 `status:"pending"` 的占位 video**（`unknown_ids` 为空）。
- 也可以只返回认识的 video，把不认识的放进 `unknown_ids`；App 两种写法都支持。
- `next_wait_ms` 此接口也会带（若服务端想控制轮询频率）；参考实现没有下发。

### 3.4 `POST /videos/resolve` —— 强制重新解析

App 侧入口：聚焦遮罩层里的「重新解析」按钮（每次只传 1 个 ID）。

请求：`{ "ids": ["9f1c0a5e-..."] }`

响应：`{ "ok": true, "server_time": ..., "videos": [ /* 重新算出的 video */ ], "unknown_ids": [ /* 后台没有这条收藏 */ ] }`

语义：让服务端**丢弃旧结果重算**（例如换了解析器、之前解析失败）。ID 去重由服务端负责；参考实现会跳过空白与重复 ID，落库后再返回。

### 3.5 `GET /health` —— 免鉴权自查

```json
{ "ok": true, "server_time": 1763122500123, "host": "0.0.0.0", "port": 8787,
  "favorites": 20, "videos": 20, "resolver": "mock" }
```

用途：平板浏览器先打这个，确认网络可达再调数据接口。App 不调用。

### 3.6 `GET /stats` —— 免鉴权的调试视图

```json
{ "ok": true, "favorites": 20, "videos": 20,
  "devices": { "tab-3f2a9c1d7b40": { "last_sync_at": 1763122500100, "favorites": 20 } } }
```

`devices` 按 `device_id` 汇总最近同步时间，用来确认「同一账号下不同平板」是否都连上了。App 不调用。

## 4. 上传节奏：一次一条

`SyncWorker` 是队列的执行体，行为如下（这些决定了服务端会看到什么样的流量）：

1. 每次 `nextDue(now)` 只取**一条**到期 op，`ops` 数组长度恒为 1（`OPS_PER_REQUEST = 1`）。串行是为了让 `next_wait_ms` 精确对应单条，失败时也能定位到具体条目。
2. 成功后：`wait = next_wait_ms ?? 设置里的上传间隔`，把队列里其余条目的 `nextRetryAt` 统一排到 `now + wait`，然后 `delay(wait)` 再取下一条。`wait <= 0` 时不等待。
3. 单次 `doWork()` 最多跑 3 分钟（`MAX_RUN_MS`）；时间片用完但队列非空 → `Result.retry()`，由 WorkManager 线性退避 4s 后继续。**无常驻定时器、不轮询**。
4. 载荷无法解析（极端情况，如升级后字段变更）→ 丢弃该 op 继续跑，避免整条队列被一条坏数据永久堵住。
5. 队列在 App 里**先落 Room 再入队**，所以「保存即生效」不依赖网络；同一条目短时间反复编辑只发最新版本（入队时会覆盖该条目尚未上传的旧载荷）。

## 5. 状态码 → App 行为对照表

| 服务端表现 | App 归类 | App 行为 |
|---|---|---|
| 2xx，`ok=true`，`applied + unknown_ops == 送出条数` | 成功 | 出队该条、标绿（SYNCED）、落库返回的 `videos`；`DELETE` 则物理删除本地条目；按 `next_wait_ms` 节奏继续 |
| 2xx，`ok=true`，但确认条数不足（典型：`applied=0`） | **假成功** | **条目留在队列**，`nextRetryAt` 排到遥远将来，标红 FAILED，原因写「后台确认条数不符（applied=0）」。需要用户在设置页「立即重试」。**这是最早那版静默丢数据的根因，绝不允许** |
| 2xx，`ok=false` | 拒绝 | 同上（标红、留在队列），显示服务端 `error` 文本 |
| 400 / 404 / 413 等 4xx | 拒绝 | 同上；优先展示响应体里的中文 `error`，没有则「后台拒绝：HTTP xxx」 |
| 401 | 拒绝 | 同上 —— 令牌不匹配不会自动重试，请让用户在设置页改令牌后点「立即重试」 |
| 429 | 可重试 | 按 `attempts × 8s` 退避（**App 读的是响应体 `next_wait_ms`，不看 `Retry-After` 头**，限速时请把等待时间放进 JSON） |
| 5xx | 可重试 | 按 `attempts × 8s` 退避 |
| 连接失败 / 超时 / 响应不是合法 JSON | 可重试 | 同上，原因显示「网络不可用」「后台响应格式不符：…」 |

重试上限 `MAX_ATTEMPTS = 3`。用尽后条目**仍留在队列**（`nextRetryAt=0`，随时可跑）并标红：联网回调、下次改动、或用户点「立即重试」都会自动补传 —— 与原始需求里「静默重试 3 次后转本地待上传队列，之后自动补传」一致。

WorkManager 侧另有约束：没有网络时任务不会被调度（`NetworkType.CONNECTED`），网络恢复由 `Connectivity` 回调触发一次 `flush()`。

## 6. 校验规则（参考实现逐条对应，真实后台建议照抄）

`POST /sync` 的校验是**全有或全无**：任何一条不合法就整批 400，绝不部分应用。错误消息都带「第 N 条操作」定位。

| 情况 | HTTP | `error` 文本 |
|---|---|---|
| 请求体不是 JSON | 400 | `请求体不是合法 JSON` |
| 请求体不是对象 | 400 | `请求体必须是 JSON 对象` |
| 缺 `device_id` 或为空白 | 400 | `缺少 device_id` |
| `ops` 不是数组 | 400 | `ops 必须是数组` |
| `type` 不是 UPSERT/DELETE | 400 | `第 N 条操作的 type 只支持 UPSERT / DELETE` |
| UPSERT 缺 `favorite` | 400 | `第 N 条操作（UPSERT）缺少 favorite 对象` |
| UPSERT 缺/空 `favorite.id` | 400 | `第 N 条操作（UPSERT）缺少 favorite.id` |
| `favorite.url` 不是字符串 | 400 | `第 N 条操作（UPSERT）的 favorite.url 必须是字符串` |
| `favorite.tags` 不是字符串数组 | 400 | `第 N 条操作的 favorite.tags 必须是字符串数组` |
| `note`/`source_app`/`bucket` 类型不对 | 400 | `…的 favorite.xxx 必须是字符串` |
| `favorite_at`/`last_position_ms` 不是有限数 | 400 | `…的 favorite.xxx 必须是数字` |
| DELETE 缺 `favorite_id` | 400 | `第 N 条操作（DELETE）缺少 favorite_id` |
| 请求体 > 4MB | 413 | `请求体超过 4MB 上限` |
| 路径不认识 | 404 | `not found` |
| 服务端内部异常 | 500 | `服务端内部错误` / `服务端处理失败：<原因>` |

其它实现要求：

- **UPSERT 必须幂等**（按 `favorite.id` 覆盖）；App 会重发同一条，服务端不能产生副本。
- **删除不存在的 ID 要进 `unknown_ops`**，不能 404 也不能静默计成 `applied`。
- `GET /videos/resolve` 的 `ids` 里出现后台没有的收藏 → 放进 `unknown_ids`，整体仍回 200。
- 落盘时机：解析结果一旦生成就应持久化，别只在内存里 —— App 重启后靠 `GET /videos` 补状态。

## 7. mock 参考实现：跑起来与可调项

```bash
node mock-server/server.mjs
```

只用 Node 内置模块，**不需要 `npm install`**。启动时会打印每个网卡的 IPv4 地址，形如 `平板可填: http://192.168.1.20:8787/api/v1`，直接抄进 App 设置页。

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `HOST` | `0.0.0.0` | 监听全部网卡，平板才能局域网直连；改成 `127.0.0.1` 只本机可访问 |
| `PORT` | `8787` | 端口 |
| `BASE_PATH` | `/api/v1` | 路由前缀，**必须与 App 里 base 地址的后缀一致** |
| `SYNC_TOKEN` | 空 | 非空则数据接口要求 `Authorization: Bearer <token>`，否则 401 |
| `DATA_FILE` | `mock-server/data.json` | 数据落盘位置（已在 `.gitignore` 里，不要提交） |
| `UPLOAD_WAIT_MS` | `3000` | `next_wait_ms` 基准值 |
| `UPLOAD_WAIT_JITTER_MS` | `0` | 正数则按请求序号抖动 `基准 + (序号 % 3) × 该值`，用来验证 App 真读了服务端建议 |

Windows 上真机直连还要放行防火墙（一次性，管理员执行）：

```
netsh advfirewall firewall add rule name="favkit-mock" dir=in action=allow protocol=TCP localport=8787 profile=private
```

假解析器：**同一个 url 永远得到同一份结果**（对 url 取 sha1，用 `hash[6:10]` 当槽位），存在的意义是把「一条链接 → 多个素材」的展示链路在本地完整跑一遍。`slot % 10` 决定素材构成，四类链接都会均匀出现：

| 桶 | 构成 | 段数 |
|---|---|---|
| 0–3 | 图 + 视频混合 | 1–2 段视频 + 1–4 张图 |
| 4–6 | 纯图集 | 1–12 张图 |
| 7–8 | 多段视频 | 2–4 段 |
| 9 | 单个视频（最贴近真实） | 1 段 |

`media` 里视频段排在前面（卡片首图取 `media[0]`，能播的先给封面）：视频段的 `cover_url` 是 `picsum.photos/seed/<hash8>-v<i>/640/360`、`duration_ms` 60s~30min、`quality` 从 720P/1080P/480P 取、播放地址从 4 个业界常用的公开测试流里选；图片段 `cover_url` 留空（它自己就是要看的那张图），`url` 是 `picsum.photos/seed/<hash8>-i<i>/1280/720`。`summary` 由同一份 `media` 现场统计（`共 3 张图 + 2 段视频（合计约 9 分钟）：…`／`共 7 张图：…`／`1 段视频，约 6 分钟：…`），所以卡片上的文字永远不会和图对不上。顶层字段是兼容镜像：`title` 为 `<站点>视频 · <hash6>`（纯图集是 `<站点>图集 · <hash6>`），`play_url`/`quality` 取第一段可播视频，`cover_url` 取 `media[0]`，`duration_ms` 是所有视频段之和；`is_mock_source` 恒为 `true`。链接不是合法 http(s) 时回 `status:"failed"` + `error:"收藏链接不是合法的 http(s) 地址"`，`media` 为空数组。

## 8. 手工联调脚本

把 `$BASE` 换成实际地址（例如 `http://127.0.0.1:8787/api/v1`），带令牌时再加 `-H "Authorization: Bearer $TOKEN"`。

```bash
BASE=http://127.0.0.1:8787/api/v1

# 1) 存活
curl -s "$BASE/health"

# 2) 上传一条收藏：期望 applied=1、videos[0].status=ready、next_wait_ms 有值
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' -d '{
  "device_id":"tab-debug","sent_at":1763122500000,
  "ops":[{"type":"UPSERT","favorite":{
    "id":"11111111-1111-1111-1111-111111111111",
    "url":"https://www.bilibili.com/video/BV1xx411c7mD",
    "note":"调试","tags":["算法"],"source_app":"manual",
    "favorite_at":1763122400000,"bucket":"INBOX","last_position_ms":0}}]}'

# 3) 取解析结果（已知 ID 给现状，未知 ID 给 pending 占位）
curl -s "$BASE/videos?ids=11111111-1111-1111-1111-111111111111,does-not-exist"

# 4) 强制重算
curl -s -X POST "$BASE/videos/resolve" -H 'content-type: application/json' \
  -d '{"ids":["11111111-1111-1111-1111-111111111111"]}'

# 5) 分页拉取（第一页 / 续页）
curl -s "$BASE/favorites?limit=50"
curl -s "$BASE/favorites?limit=50&cursor=1763120000000"

# 6) 删除已有 / 删除不存在：后者应进 unknown_ops，applied=0，但 ok 仍为 true
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' \
  -d '{"device_id":"tab-debug","sent_at":1763122501000,"ops":[{"type":"DELETE","favorite_id":"11111111-1111-1111-1111-111111111111"}]}'
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' \
  -d '{"device_id":"tab-debug","sent_at":1763122502000,"ops":[{"type":"DELETE","favorite_id":"nope"}]}'

# 7) 校验负例：应 400 且 error 指出「第 1 条操作（UPSERT）缺少 favorite.id」
curl -s -i -X POST "$BASE/sync" -H 'content-type: application/json' \
  -d '{"device_id":"tab-debug","sent_at":1763122503000,"ops":[{"type":"UPSERT","favorite":{"url":"x"}}]}'

# 8) 设了 SYNC_TOKEN 却带错令牌：应 401
curl -s -i -X POST "$BASE/sync" -H 'content-type: application/json' -H 'Authorization: Bearer wrong' \
  -d '{"device_id":"tab-debug","sent_at":1763122504000,"ops":[]}'
```

App 侧的对应验收：列表小圆点 黄(QUEUED) → 绿(SYNCED)；拔网线保存 → 黄/红且条目仍在；恢复网络后不点任何按钮应自动补传转绿；`GET /stats` 里 `devices.<device_id>.last_sync_at` 应随之更新。

## 9. 兼容与演进

- App 端配置项：接口地址与令牌在设置页可改，持久化在 DataStore；打包默认值来自 `gradle.properties` 的 `SYNC_ENDPOINT` 或 CI 的 `SYNC_ENDPOINT` 变量（缺省 `http://10.0.2.2:8787/api/v1`，即模拟器访问宿主机）。设备标识 `device_id` 形如 `tab-` + 12 位 UUID 片段，首次使用时生成并固定。
- 本协议没有版本号字段，版本靠 `BASE_PATH`（`/api/v1`）体现。
- **加字段安全**（App 忽略未知键），**改语义/删字段危险**：改任一边都要同时改 `Dto.kt`、`server.mjs` 与本文。
- 枚举扩展需 App 先发版：`bucket` 未知值在 App 侧会落到默认展示，`video.status` 未知值按 `pending` 处理。
- Room 已到 v3（v2 拆出收藏/视频两张表，v3 给 `video_info` 加 `summary`+`mediaJson`、给 `favorites` 加 `segmentProgress`+`lastSegmentIndex`）。v2→v3 走的是真 `MIGRATION_2_3`（四条 `ALTER TABLE ADD COLUMN`，新列全部可空所以不用写 DEFAULT），**升级旧包不会清库**；只有版本落差没有迁移路径时才落回 `fallbackToDestructiveMigration()`。因此联调时看到「收藏全没了」要先确认是清库还是后台丢数据 —— 前者是本地缓存空了，冷启动会自动去后台取第一页，也可以点「从后台加载我的收藏」。
