# 同步后台接口说明

本文是 App 与收藏后台之间**唯一**的协议文档，内容与两处实现一一对应：

- App 侧：[net/Dto.kt](../app/src/main/java/com/favkit/tablet/net/Dto.kt)（数据结构）、[net/SyncApi.kt](../app/src/main/java/com/favkit/tablet/net/SyncApi.kt)（收发与状态码判定）、[sync/SyncWorker.kt](../app/src/main/java/com/favkit/tablet/sync/SyncWorker.kt)（成功判据与节奏）
- 参考实现：[mock-server/server.mjs](../mock-server/server.mjs)（可直接跑起来当联调靶子）

**改任何一边都必须同步改另一边，并更新本文。**

协议只有一条主脑：**后台保存与解析在同一次调用里完成**。App 发一条链接回来就带着这条链接的内容信息，所以协议里没有「已上传、等内容」这种中间态，没有 `pending` 状态，也没有专门取解析结果的轮询接口。数据接口一共三个，加上一个免鉴权的 `GET /health`。

协议刻意是纯明文 JSON：出网的只有链接、备注、标签名和播放不了才需要解释的那点元信息，没有需要密文传输的数据。上一版加过 RSA+AES 信封，结果是「后台解不开却回 200」变成静默丢数据，排查代价远大于收益。传输加密交给部署环境的 TLS（后台换成 `https://` 即可，App 无需改动）。

## 1. 基础约定

| 项目 | 约定 |
|---|---|
| 传输 | HTTP/1.1 或 HTTP/2，`Content-Type: application/json; charset=utf-8` |
| 寻址 | App 把「设置页里的接口地址」当作 base，直接拼接 `/sync`、`/favorites`、`/resolve`、`/health`。因此地址要**填到包含前缀的完整 base**，例如 `http://192.168.1.20:8787/api/v1`；结尾多余的 `/` 会被去掉；不以 `http://`/`https://` 开头会被判为「同步地址无效」，请求根本不发 |
| 字段命名 | 全部 `snake_case`（`device_id`、`favorite_at`、`next_wait_ms`…） |
| 时间 | 一律 Unix 毫秒时间戳。`sent_at` 是客户端本地时间，**服务端不要拿它做排序或去重依据** |
| 认证 | 设置页填了令牌时，App 每个请求都带 `Authorization: Bearer <token>`；未填则不带该头。参考实现用环境变量 `SYNC_TOKEN` 控制：非空时数据接口校验，不匹配回 401（`/health` 不校验） |
| 附加请求头 | `X-Device-Platform: android-tablet`（服务端可忽略，仅便于排查） |
| 未知字段 | App 的 JSON 解析器 `ignoreUnknownKeys = true`：**服务端可以多返回字段**（如 `updated_at`、`device_id`），App 会忽略，不会报错 |
| App 发出的字段 | `encodeDefaults = true`、`explicitNulls = false`：所有非空字段都会显式出现，值为 `null` 的字段会被整个省略 |
| 超时 | 连接 10s、读 20s、整次调用 40s；连接失败由 OkHttp 自行重试一次 |
| 体积 | 参考实现对请求体设 4MB 上限，超出回 413（App 视为永久失败，见 §5） |

`GET /health` 是给人在浏览器/curl 里自查用的，App 不会调用它。

**出站节奏只有一个闸门**（`net/SyncGate.kt`）。三个数据接口共用它：上一条请求完成后要等到下一个时隙才发下一条，等待时长由响应里的 `next_wait_ms` 决定。所以后台看到的是一个串行的、自己可以调速的流量，不会并发打过来。

## 2. 数据结构

### 2.1 `favorite` —— 一条收藏

用户产生的数据由客户端提供，内容信息由服务端解析。**同名字段客户端传了也不算数**，服务端一律以自己解析出来的为准。

| 字段 | 类型 | 谁写 | 说明 |
|---|---|---|---|
| `id` | string | 客户端 | 收藏的唯一标识，App 生成（UUID 字符串）。服务端以它为幂等键 |
| `url` | string | 客户端 | 用户收藏的**原始链接**。它不等于可播放地址：一条链接可能解析出多个素材，可播地址在 `media.segments[]` 的各段 `url` |
| `note` | string | 客户端 | 用户备注（含手写转成的文字），默认 `""` |
| `tags` | string[] | 客户端 | 标签**名称**数组，不带标签 ID；服务端自行维护名称→ID |
| `source_app` | string | 客户端 | 来源应用标识，如 `chrome`、`share`、`manual`，默认 `""` |
| `favorite_at` | number | 客户端 | 收藏时间（毫秒）。App 缺省时参考实现按 `Date.now()` 补；分页游标就是它 |
| `media` | object 或 null | **服务端** | 这条链接的解析结果，见 §2.2。请求里永远是 `null`（App 直接省略这个键），只有响应里才带 |

上传一条收藏时要送的就是前六项；`media` 只出现在服务端 → App 的方向。

### 2.2 `media` —— 后台解析出来的内容信息

一条链接解析回来的**不一定是单个视频**：可能是「图＋视频」「纯图集（1~N 张）」或「多段视频」。所以内容清单在 `segments[]`，另有一句给人看的 `summary`。

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | string | 内容标题。App 不再用链接猜标题，标题**只能**来自这里 |
| `author` | string | 作者/UP 主 |
| `site` | string | 站点显示名 |
| `summary` | string | **一句话说明文案**：后台读懂内容后写给用户看的「这条链接里有什么、建议怎么看」。App 把它当内容主体 —— 卡片上两行，遮罩层里全文 |
| `segments` | object[] | 素材清单，见 §2.3。空数组 + 非空 `failed_reason` 表示解析失败 |
| `failed_reason` | string | 非空表示**解析失败**，此时 `segments` 必为空。App 把这句话原样显示在那条卡片上（卡片和遮罩层各一处），没有全局计数 |
| `resolved_at` | number | 解析完成时间（毫秒），遮罩层的元信息行展示 |

没有 `status` 字段。只有三种情况，各自都能从上面直接读出来：

- `media` 缺失（老数据或后台没解析）→ App 显示「内容信息还没取回来」，条目照常出现在墙上；
- `failed_reason` 非空 → 显示「解析失败」+ 原因；
- 其余 → 用 `summary` + `segments` 渲染。

### 2.3 `segments` 元素 —— 一个可独立浏览或播放的素材

| 字段 | 类型 | 说明 |
|---|---|---|
| `index` | number | 段序号。App 先按它排序，再重新编号成 `0..n-1`，所以**跳号或从 1 起算都不会打乱顺序** |
| `kind` | string | `image` / `video`。大小写不敏感；**其它值一律按 `video` 处理**（宁可给一个播不了的段，也不把图片当视频播） |
| `title` | string | 该段自己的标题，如 `图 2`、`哔哩哔哩视频 1` |
| `cover_url` | string | 视频段的封面图；图片段留空（它自己就是要看的那张图） |
| `url` | string | `video` 段是可播地址（mp4 或 m3u8），`image` 段就是图片本身。**同一个字段两种用途**，App 靠 `kind` 区分 |
| `duration_ms` | number | 视频段时长；图片段填 0。填 0 时 App 的进度条不可拖动 |
| `quality` | string | 视频段清晰度，如 `1080P`；图片段留空 |

顺序即展示顺序：App 的视频墙卡片拿 `segments[0]` 当首图，所以**有可播段时请把视频段排在前面**，纯图集按阅读动线排（第一张最抓人）。参考实现就是这么做的。

顶层不再有 `play_url`/`cover_url`/`duration_ms`/`quality` 的镜像 —— 它们只是 `segments[0]` 的重复，留着只会让两边对不上。

### 2.4 `op` —— 一次变更

```jsonc
{ "type": "UPSERT", "favorite": { "id": "...", "url": "...", /* ... */ } }
{ "type": "DELETE", "favorite_id": "..." }
```

- `type` 只支持 `UPSERT` / `DELETE`，其它值 → 400。
- `UPSERT` 必须带完整 `favorite` 对象（整条覆盖，不是增量 patch）。
- `DELETE` 必须带非空 `favorite_id`。
- App 用 `explicitNulls=false` 序列化，所以 UPSERT 请求里**不会**出现 `favorite_id: null` 或 `media: null` 这种键。

### 2.5 只存在本地、不上传的东西

观看进度（段序号 + 逐段位置）只写在 App 本地的 Room（`segmentProgress` / `lastSegmentIndex`），协议里没有对应字段。原因：多设备同步进度要引入冲突裁决（谁的进度算数），而这条链路上唯一有价值的是「接着看」，把它做成服务端字段带来的复杂度和收益完全不匹配。换设备后从头一段开始看。

标签关系（哪个标签挂在哪条收藏上）本地维护，上传时以标签名数组呈现，服务端自己映射成 ID。

## 3. 接口清单

### 3.1 `POST /sync` —— 上传变更（App 唯一的写接口）

请求：

```json
{
  "device_id": "tab-3f2a9c1d7b40",
  "sent_at": 1763122500000,
  "ops": [
    {
      "type": "UPSERT",
      "favorite": {
        "id": "9f1c0a5e-2b7d-4c8a-9f3e-6d0a1b2c3d4e",
        "url": "https://www.bilibili.com/video/BV1xx411c7mD",
        "note": "周末看",
        "tags": ["待看", "算法"],
        "source_app": "chrome",
        "favorite_at": 1763122400000
      }
    }
  ]
}
```

成功响应（200）：

```json
{
  "ok": true,
  "server_time": 1763122500123,
  "applied": 1,
  "unknown_ops": [],
  "favorites": [{
    "id": "9f1c0a5e-2b7d-4c8a-9f3e-6d0a1b2c3d4e",
    "url": "https://www.bilibili.com/video/BV1xx411c7mD",
    "note": "周末看",
    "tags": ["待看", "算法"],
    "source_app": "chrome",
    "favorite_at": 1763122400000,
    "device_id": "tab-3f2a9c1d7b40",
    "updated_at": 1763122500100,
    "media": {
      "title": "哔哩哔哩视频 · a3f19c",
      "author": "阿测",
      "site": "哔哩哔哩",
      "summary": "UP 主实测 3 款降噪耳机，先看 8 分钟对比视频，再对照 4 张频谱图。",
      "segments": [
        { "index": 0, "kind": "video", "title": "哔哩哔哩视频 1", "cover_url": "https://picsum.photos/seed/a3f19c2d-v0/640/360", "url": "https://.../x36xhzz.m3u8", "duration_ms": 480000, "quality": "1080P" },
        { "index": 1, "kind": "video", "title": "哔哩哔哩视频 2", "cover_url": "https://picsum.photos/seed/a3f19c2d-v1/640/360", "url": "https://.../BigBuckBunny.mp4", "duration_ms": 660000, "quality": "720P" },
        { "index": 2, "kind": "image", "title": "图 1", "cover_url": "", "url": "https://picsum.photos/seed/a3f19c2d-i0/1280/720", "duration_ms": 0, "quality": "" }
      ],
      "failed_reason": "",
      "resolved_at": 1763122500120
    }
  }],
  "next_wait_ms": 3000,
  "error": ""
}
```

字段语义：

- `applied`：**服务端确实落库的条数**。UPSERT 成功计 1，删除已有条目计 1。
- `unknown_ops`：要删但服务端没有这个 ID 的 `favorite_id` 列表。**这不是错误**：多设备场景下别的设备已经删过，属正常收敛，App 一样会清掉本地数据。
- `favorites`：**本次涉及条目的最新状态，每条都已带 `media`**。App 直接落库并渲染，不会再回头问一次。所以解析失败就在 `failed_reason` 里写清楚，别为了「响应好看」编一段假内容出来。
- `next_wait_ms`：**服务端建议「下一条上传前等多久」**。App 每次请求只带一条 op，这个值因此精确对应单条的节奏。缺省（不下发该字段或为 null）时 App 退回设置页的「上传间隔」（默认 3000ms，填 0 表示不限速）。参考实现默认固定 3000ms，可用 `UPLOAD_WAIT_JITTER_MS` 按下发序号抖动，验证 App 是否真的读服务端的建议而不是只用自己的配置。
- `error`：失败原因（中文，会直接显示在 App 列表/设置里）。

失败响应示例（400，`Content-Type` 仍是 JSON）：

```json
{ "ok": false, "error": "第 1 条操作（UPSERT）缺少 favorite.id", "applied": 0, "unknown_ops": [] }
```

**服务端实现必须守住的不变式：`applied + len(unknown_ops) == len(ops)`。** App 的成功判据就是这个等式；不等时条目留在队列并标红（详见 §5）。参考实现在内部也做了同一断言，对不上宁可抛 500，也不回一个「看起来成功」的空响应。

### 3.2 `GET /favorites?limit=&cursor=` —— 分页拉取收藏

服务端是收藏的事实来源，App 本地那张表只是**分页缓存**：

- 冷启动发现本地缓存为空（换机、清数据）→ 自动取第一页，不用用户点；
- 视频墙滚到离底还有两屏 → 静默取下一页；
- 空列表/抽屉里的「从后台加载我的收藏」是同一件事的手动入口。

请求：`GET /favorites?limit=50`，续页时带上 `&cursor=<上一页返回的 next_cursor>`（App 会对游标做 URL 编码）。

响应：

```json
{
  "ok": true,
  "server_time": 1763122500123,
  "favorites": [ /* favorite 对象数组，每条都带 media，最多 limit 条 */ ],
  "total": 1280,
  "next_cursor": "1763120000000",
  "has_more": true
}
```

- 请按 `favorite_at` **倒序**返回，游标就用上一页最后一条的 `favorite_at`（键集分页）。用偏移量的话，翻页途中新收藏一条就会把下一页顶掉一条；键集不会，重复取到的那条 App 按 `id` 去掉。
- `total`：**这个账号下的收藏总数**（不含已删除），每页都带同一个值。App 拿它区分「一共就这些」和「本地只取回了前几页」：顶栏说「共 1280 条 · 已取回 50 条」，墙头说「已取回 50 / 1280 条」。不下发或为 0 时 App 退回只显示本地条数，不会编出一个总数。
- `next_cursor` 为空或 `has_more=false` 都表示到底了，App 就不再补页（列表尾部显示「到底了」）。
- `has_more=true` 却返回 0 条，App 按到底处理，避免无休止地滚动补页。
- 某条的 `media` 缺失时，该条在 App 里显示「内容信息还没取回来」，条目照常出现在墙上 —— 这不是错误状态，全局也没有对应的计数。
- 4xx → 手动入口提示「从后台加载失败：后台拒绝：HTTP xxx」；网络层失败 → 提示「从后台加载失败：<IO 原因>」。自动补页失败不弹提示，只把尾部的加载位收回去。这个接口只读，不会污染上传队列。

### 3.3 `POST /resolve` —— 强制重新解析

App 侧唯一入口：遮罩层里的「重新解析」按钮（每次只传 1 个 ID）。**App 不会自动重试解析** —— 同一条链接的解析结果由链接本身决定，再问一遍只会多占一个出站时隙。

请求：`{ "favorite_ids": ["9f1c0a5e-..."] }`

响应：`{ "ok": true, "server_time": 1763122500123, "favorites": [ /* 带新 media 的收藏 */ ], "unknown_ids": [ /* 后台没有这条收藏 */ ] }`

语义：

- 让服务端**丢弃旧结果重算**（例如换了解析器、之前解析失败）。ID 去重由服务端负责；参考实现会跳过空白与重复 ID，落库后再返回。
- **`favorite_at` 不能变**：重解析不该把这条顶到列表最前。参考实现只替换 `media` 和 `updated_at`。
- 后台没有的 ID 放进 `unknown_ids`，整体仍回 200。App 见到「全部未知」提示「后台没有这条收藏」。
- 响应里没有 favorites 也没有 unknown_ids 时，App 提示「后台没有返回解析结果」。

### 3.4 `GET /health` —— 免鉴权自查

```json
{ "ok": true, "server_time": 1763122500123, "host": "0.0.0.0", "port": 8787,
  "favorites": 20, "resolver": "mock" }
```

用途：平板浏览器先打这个，确认网络可达再调数据接口。App 不调用。

## 4. 上传节奏：一次一条

`SyncWorker` 是队列的执行体，行为如下（这些决定了服务端会看到什么样的流量）：

1. 每次 `nextDue(now)` 只取**一条**到期 op，`ops` 数组长度恒为 1（`OPS_PER_REQUEST = 1`）。串行是为了让 `next_wait_ms` 精确对应单条，失败时也能定位到具体条目。
2. 成功后：`wait = next_wait_ms ?? 设置里的上传间隔`，把队列里其余条目的 `nextRetryAt` 统一排到 `now + wait`，然后 `delay(wait)` 再取下一条。`wait <= 0` 时不等待。
3. 单次 `doWork()` 最多跑 3 分钟（`MAX_RUN_MS`）；时间片用完但队列非空 → `Result.retry()`，由 WorkManager 线性退避 4s 后继续。**无常驻定时器、不轮询**。
4. 载荷无法解析（极端情况，如升级后字段变更）→ 丢弃该 op 继续跑，避免整条队列被一条坏数据永久堵住。
5. 队列在 App 里**先落 Room 再入队**，所以「保存即生效」不依赖网络；同一条目短时间反复编辑只发最新版本（入队时会覆盖该条目尚未上传的旧载荷）。

取列表（`GET /favorites`）和重新解析（`POST /resolve`）走同一个 `SyncGate` 时隙，但**不入队** —— 它们是即发即收的读操作，失败了由 UI 提示，不产生待重试的 op。

## 5. 状态码 → App 行为对照表

| 服务端表现 | App 归类 | App 行为 |
|---|---|---|
| 2xx，`ok=true`，`applied + unknown_ops == 送出条数` | 成功 | 出队该条、标绿（SYNCED）、落库返回的 `favorites`（含 `media`）；`DELETE` 则物理删除本地条目；按 `next_wait_ms` 节奏继续 |
| 2xx，`ok=true`，但确认条数不足（典型：`applied=0`） | **假成功** | **条目留在队列**，`nextRetryAt` 排到遥远将来，标红 FAILED，原因写「后台确认条数不符（applied=0）」。需要用户在设置页「立即重试」。**这是最早那版静默丢数据的根因，绝不允许** |
| 2xx，`ok=false` | 拒绝 | 同上（标红、留在队列），显示服务端 `error` 文本 |
| 400 / 404 / 413 等 4xx | 拒绝 | 同上；优先展示响应体里的中文 `error`，没有则「后台拒绝：HTTP xxx」 |
| 401 | 拒绝 | 同上 —— 令牌不匹配不会自动重试，请让用户在设置页改令牌后点「立即重试」 |
| 429 | 可重试 | 按 `attempts × 8s` 退避（**App 读的是响应体 `next_wait_ms`，不看 `Retry-After` 头**，限速时请把等待时间放进 JSON） |
| 5xx | 可重试 | 按 `attempts × 8s` 退避 |
| 连接失败 / 超时 / 响应不是合法 JSON | 可重试 | 同上，原因显示「网络不可用」「后台响应格式不符：…」 |

重试上限 `MAX_ATTEMPTS = 3`。用尽后条目**仍留在队列**（`nextRetryAt=0`，随时可跑）并标红：联网回调、下次改动、或用户点「立即重试」都会自动补传 —— 与原始需求里「静默重试 3 次后转本地待上传队列，之后自动补传」一致。

WorkManager 侧另有约束：没有网络时任务不会被调度（`NetworkType.CONNECTED`），网络恢复由 `Connectivity` 回调触发一次 `flush()`。

**界面上因此只有三种状态词，全app统一：**「离线」（连不上后台）、「待同步 N」（队列里还有没上传完的）、「失败 N」（重试次数用尽或被拒绝）。解析失败不占任何全局计数 —— 它只是那条卡片上的一行文字。

## 6. 校验规则（参考实现逐条对应，真实后台建议照抄）

`POST /sync` 的校验是**全有或全无**：任何一条不合法就整批 400，绝不部分应用。错误消息都带「第 N 条操作」定位。

| 情况 | HTTP | `error` 文本 |
|---|---|---|
| 请求体不是 JSON | 400 | `请求体不是合法 JSON` |
| 请求体不是对象 | 400 | `请求体必须是 JSON 对象` |
| 缺 `device_id` 或为空白 | 400 | `缺少 device_id` |
| `ops` 不是数组 | 400 | `ops 必须是数组` |
| `ops` 里某项不是对象 | 400 | `第 N 条操作不是 JSON 对象` |
| `type` 不是 UPSERT/DELETE | 400 | `第 N 条操作的 type 只支持 UPSERT / DELETE` |
| UPSERT 缺 `favorite` | 400 | `第 N 条操作（UPSERT）缺少 favorite 对象` |
| UPSERT 缺/空 `favorite.id` | 400 | `第 N 条操作（UPSERT）缺少 favorite.id` |
| `favorite.url` 不是字符串 | 400 | `第 N 条操作（UPSERT）的 favorite.url 必须是字符串` |
| `favorite.tags` 不是字符串数组 | 400 | `第 N 条操作的 favorite.tags 必须是字符串数组` |
| `note`/`source_app` 类型不对 | 400 | `…的 favorite.xxx 必须是字符串` |
| `favorite_at` 不是有限数 | 400 | `…的 favorite.favorite_at 必须是数字` |
| DELETE 缺 `favorite_id` | 400 | `第 N 条操作（DELETE）缺少 favorite_id` |
| 请求体 > 4MB | 413 | `请求体超过 4MB 上限` |
| 路径不认识 | 404 | `not found` |
| 服务端内部异常 | 500 | `服务端内部错误` / `服务端处理失败：<原因>` |

`POST /resolve`：`favorite_ids` 不是字符串数组 → 400 `favorite_ids 必须是字符串数组`。

其它实现要求：

- **UPSERT 必须幂等**（按 `favorite.id` 覆盖）；App 会重发同一条，服务端不能产生副本。
- **删除不存在的 ID 要进 `unknown_ops`**，不能 404 也不能静默计成 `applied`。
- 解析结果一旦生成就应**随收藏那一行一起持久化**，别只在内存里 —— App 重启后靠 `GET /favorites` 补内容信息。
- 客户端传来的 `media`（如果有人手滑传了）一律忽略，以自己解析的为准。

## 7. App 侧的存储（改协议前先看清这里）

Room **v4，一张表**（`app/src/main/java/com/favkit/tablet/data/db/Rows.kt`）。以前收藏和内容信息分两张表、内容表还带一个 `status` 列，是异步解析假设的残留：每次渲染都要 join，计数要从两个源各数一遍，才导致「加了删了数字对不上」。现在合成一行：

| 列组 | 列 | 归属 |
|---|---|---|
| 上传的 | `id`、`url`、`note`、`sourceApp`、`favoriteAt` | App 产生，`POST /sync` 送出去 |
| 后台解析的 | `title`、`author`、`site`、`summary`、`segmentsJson`、`failedReason`、`resolvedAt` | 只从响应写回，App 不自造 |
| 本地状态 | `badge`（SYNCED/QUEUED/FAILED）、`locallyCached`、`updatedAt`、`deletedAt` | 只在 App |
| 本地进度 | `segmentProgress`、`lastSegmentIndex` | 只在 App，见 §2.5 |

标签是另外两张表（`TagRow` 标签库、`FavoriteTagRow` 多对多），待上传队列 `PendingOpRow` 一张。

因为开发阶段不留兼容包袱，`AppDatabase` 只挂 `fallbackToDestructiveMigration()`，v4 没写 Migration —— 升级会清本地缓存。清完不是丢数据：冷启动看见本地为空会自动去后台取第一页，收藏本身在后台。**联调时看到「收藏全没了」先确认是这个，别当成后台丢了数据。**

## 8. mock 参考实现：跑起来与可调项

```bash
node mock-server/server.mjs
```

只用 Node 内置模块，**不需要 `npm install`**。启动时会打印每个网卡的 IPv4 地址，形如 `平板可填: http://192.168.1.20:8787/api/v1`，直接抄进 App 设置页。

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `HOST` | `0.0.0.0` | 监听全部网卡，平板才能局域网直连；改成 `127.0.0.1` 只本机可访问 |
| `PORT` | `8787` | 端口 |
| `BASE_PATH` | `/api/v1` | 路由前缀，**必须与 App 里 base 地址的后缀一致** |
| `SYNC_TOKEN` | 空 | 非空则数据接口要求 `Authorization: Bearer <token>`，否则 401 |
| `DATA_FILE` | `mock-server/data.json` | 数据落盘位置（已在 `.gitignore` 里，不要提交） |
| `UPLOAD_WAIT_MS` | `3000` | `next_wait_ms` 基准值 |
| `UPLOAD_WAIT_JITTER_MS` | `0` | 正数则按请求序号抖动 `基准 + (序号 % 3) × 该值`，用来验证 App 真读了服务端建议 |

Windows 上真机直连还要放行防火墙（一次性，管理员执行）：

```
netsh advfirewall firewall add rule name="favkit-mock" dir=in action=allow protocol=TCP localport=8787 profile=private
```

假解析器：**同一个 url 永远得到同一份结果**（对 url 取 sha1，用 `hash[6:10]` 当槽位），存在的意义是把「一条链接 → 多个素材」的展示链路在本地完整跑一遍。`slot % 10` 决定素材构成，四类链接都会均匀出现：

| 桶 | 构成 | 段数 |
|---|---|---|
| 0–3 | 图 + 视频混合 | 1–2 段视频 + 1–4 张图 |
| 4–6 | 纯图集 | 1–12 张图 |
| 7–8 | 多段视频 | 2–4 段 |
| 9 | 单个视频（最贴近真实） | 1 段 |

`segments` 里视频段排在前面（卡片首图取 `segments[0]`，能播的先给封面）：视频段的 `cover_url` 是 `picsum.photos/seed/<hash8>-v<i>/640/360`、`duration_ms` 60s~30min、`quality` 从 720P/1080P/480P 取、播放地址从 4 个业界常用的公开测试流里选；图片段 `cover_url` 留空（它自己就是要看的那张图），`url` 是 `picsum.photos/seed/<hash8>-i<i>/1280/720`。`summary` 由同一份 `segments` 现场统计（`共 3 张图 + 2 段视频（合计约 9 分钟）：…`／`共 7 张图：…`／`1 段视频，约 6 分钟：…`），所以卡片上的文字永远不会和图对不上。`title` 为 `<站点>视频 · <hash6>`（纯图集是 `<站点>图集 · <hash6>`）。链接不是合法 http(s) 时回 `segments: []` + `failed_reason: "收藏链接不是合法的 http(s) 地址"`。

## 9. 手工联调脚本

把 `$BASE` 换成实际地址（例如 `http://127.0.0.1:8787/api/v1`），带令牌时再加 `-H "Authorization: Bearer $TOKEN"`。

```bash
BASE=http://127.0.0.1:8787/api/v1

# 1) 存活
curl -s "$BASE/health"

# 2) 上传一条收藏：期望 applied=1、favorites[0].media.segments 非空、next_wait_ms 有值
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' -d '{
  "device_id":"tab-debug","sent_at":1763122500000,
  "ops":[{"type":"UPSERT","favorite":{
    "id":"11111111-1111-1111-1111-111111111111",
    "url":"https://www.bilibili.com/video/BV1xx411c7mD",
    "note":"调试","tags":["算法"],"source_app":"manual",
    "favorite_at":1763122400000}}]}'

# 3) 分页拉取（第一页 / 续页）：每条都应自带 media，total 每页相同
curl -s "$BASE/favorites?limit=50"
curl -s "$BASE/favorites?limit=50&cursor=1763120000000"

# 4) 强制重算：favorites[0].favorite_at 应与第 2 步一致（重解析不置顶）
curl -s -X POST "$BASE/resolve" -H 'content-type: application/json' \
  -d '{"favorite_ids":["11111111-1111-1111-1111-111111111111"]}'

# 5) 删除已有 / 删除不存在：后者应进 unknown_ops，applied=0，但 ok 仍为 true
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' \
  -d '{"device_id":"tab-debug","sent_at":1763122501000,"ops":[{"type":"DELETE","favorite_id":"11111111-1111-1111-1111-111111111111"}]}'
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' \
  -d '{"device_id":"tab-debug","sent_at":1763122502000,"ops":[{"type":"DELETE","favorite_id":"nope"}]}'

# 6) 校验负例：应 400 且 error 指出「第 1 条操作（UPSERT）缺少 favorite.id」
curl -s -i -X POST "$BASE/sync" -H 'content-type: application/json' \
  -d '{"device_id":"tab-debug","sent_at":1763122503000,"ops":[{"type":"UPSERT","favorite":{"url":"x"}}]}'

# 7) 设了 SYNC_TOKEN 却带错令牌：应 401
curl -s -i -X POST "$BASE/sync" -H 'content-type: application/json' -H 'Authorization: Bearer wrong' \
  -d '{"device_id":"tab-debug","sent_at":1763122504000,"ops":[]}'
```

App 侧的对应验收：列表小圆点 黄(QUEUED) → 绿(SYNCED)；拔网线保存 → 黄/红且条目仍在；恢复网络后不点任何按钮应自动补传转绿；保存成功后**卡片应立即出现标题、说明和拼图封面**（同一次 `/sync` 回执带来的，不需要任何后续请求）。

## 10. 兼容与演进

- App 端配置项：接口地址与令牌在设置页可改，持久化在 DataStore；打包默认值来自 `gradle.properties` 的 `SYNC_ENDPOINT` 或 CI 的 `SYNC_ENDPOINT` 变量（缺省 `http://10.0.2.2:8787/api/v1`，即模拟器访问宿主机）。设备标识 `device_id` 形如 `tab-` + 12 位 UUID 片段，首次使用时生成并固定。
- 本协议没有版本号字段，版本靠 `BASE_PATH`（`/api/v1`）体现。
- **加字段安全**（App 忽略未知键），**改语义/删字段危险**：改任一边都要同时改 `Dto.kt`、`server.mjs` 与本文。
- 若后台真的改成异步解析，**不要**把 `status` 加回来。加一个 `media: null` 的语义（表示「还没算完」）就够了，App 已经按这条分支显示「内容信息还没取回来」；但那样就必须回头再取一次，而「回头取」正是这版协议删掉的东西 —— 请先确认收益再动。
- Room 已到 v4（单表 `favorites`；v4 把 `video_info` 并进来、删掉 `bucket` 与 `last_position_ms`）。开发阶段不写迁移，见 §7。
