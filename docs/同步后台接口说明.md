# 同步后台接口说明

本文是 App 与收藏后台之间**唯一**的协议文档，内容与两处实现一一对应：

- App 侧：[net/Dto.kt](../app/src/main/java/com/favkit/tablet/net/Dto.kt)（数据结构）、[net/SyncApi.kt](../app/src/main/java/com/favkit/tablet/net/SyncApi.kt)（收发与状态码判定）、[sync/SyncWorker.kt](../app/src/main/java/com/favkit/tablet/sync/SyncWorker.kt)（成功判据与节奏）
- 参考实现：[mock-server/server.mjs](../mock-server/server.mjs)（可直接跑起来当联调靶子）

**改任何一边都必须同步改另一边，并更新本文。**

协议只有一条主脑：**后台保存与解析在同一次调用里完成**。App 发一条链接回来就带着这条链接的内容信息，所以协议里没有「已上传、等内容」这种中间态，没有 `pending` 状态，也没有专门取解析结果的轮询接口。数据接口一共三个，加上一个免鉴权的 `GET /health`。

协议刻意是纯明文 JSON：出网的只有链接、备注、标签名和播放不了才需要解释的那点元信息，没有需要密文传输的数据。上一版加过 RSA+AES 信封，结果是「后台解不开却回 200」变成静默丢数据，排查代价远大于收益。传输加密交给部署环境的 TLS（后台换成 `https://` 即可，App 无需改动）。

## 1. 基础约定

| 项目 | 约定 |
|---|---|
| 传输 | HTTP/1.1 或 HTTP/2，`Content-Type: application/json; charset=utf-8` |
| 寻址 | App 把「设置页里的接口地址」当作 base，直接拼接 `/sync`、`/favorites`、`/resolve`、`/health`。因此地址要**填到包含前缀的完整 base**，例如 `http://192.168.1.20:8787/api/v1`；结尾多余的 `/` 会被去掉；不以 `http://`/`https://` 开头会被判为「同步地址无效」，请求根本不发 |
| 字段命名 | 全部 `snake_case`（`device_id`、`favorite_at`、`next_wait_ms`…） |
| 时间 | 一律 Unix 毫秒时间戳。`sent_at` 是客户端本地时间，**服务端不要拿它做排序或去重依据** |
| 认证 | 设置页填了令牌时，App 每个请求都带 `Authorization: Bearer <token>`；未填则不带该头。参考实现用环境变量 `SYNC_TOKEN` 控制：非空时数据接口校验，不匹配回 401（`/health` 不校验） |
| 附加请求头 | `X-Device-Platform: android-tablet`（服务端可忽略，仅便于排查） |
| 未知字段 | App 的 JSON 解析器 `ignoreUnknownKeys = true`：**服务端可以多返回字段**（如 `updated_at`、`rev`），App 会忽略，不会报错 |
| App 发出的字段 | `encodeDefaults = true`、`explicitNulls = false`：所有非空字段都会显式出现，值为 `null` 的字段会被整个省略 |
| 超时 | 连接 10s、读 20s、整次调用 40s；连接失败由 OkHttp 自行重试一次 |
| 体积 | 参考实现对请求体设 4MB 上限，超出回 413（App 视为永久失败，见 §5） |

`GET /health` 是给人在浏览器/curl 里自查用的，App 不会调用它。

**出站节奏只有一个闸门**（`net/SyncGate.kt`）。三个数据接口共用它：上一条请求完成后要等到下一个时隙才发下一条，等待时长由响应里的 `next_wait_ms` 决定。所以后台看到的是一个串行的、自己可以调速的流量，不会并发打过来。

## 2. 数据结构

### 2.1 `favorite` —— 一条收藏

用户产生的数据由客户端提供，内容信息由服务端解析。**同名字段客户端传了也不算数**，服务端一律以自己解析出来的为准。

| 字段 | 类型 | 谁写 | 说明 |
|---|---|---|---|
| `id` | string | 客户端 | 收藏的唯一标识，App 生成（UUID 字符串）。服务端以它为幂等键 |
| `url` | string | 客户端 | 用户收藏的**原始链接**。它不等于可播放地址：一条链接可能解析出多个素材，可播地址在 `media.segments[]` 的各段 `url` |
| `note` | string | 客户端 | 用户备注（含手写转成的文字），默认 `""` |
| `tags` | string[] | 客户端 | 标签**名称**数组，不带标签 ID；服务端自行维护名称→ID |
| `source_app` | string | 客户端 | 来源应用标识，如 `chrome`、`share`、`manual`，默认 `""` |
| `favorite_at` | number | 客户端 | 收藏时间（毫秒）。App 缺省时参考实现按 `Date.now()` 补；它是 `(favorite_at, id)` 复合分页游标的第一段（§3.2），所以范围夹紧会造出并列值、并列必须由 id 切开 |
| `media` | object 或 null | **服务端** | 这条链接的解析结果，见 §2.2。请求里永远是 `null`（App 直接省略这个键），只有响应里才带 |

上传一条收藏时要送的就是前六项；`media` 只出现在服务端 → App 的方向。

### 2.2 `media` —— 后台解析出来的内容信息

一条链接解析回来的**不一定是单个视频**：可能是「图＋视频」「纯图集（1~N 张）」或「多段视频」。所以内容清单在 `segments[]`，另有一句给人看的 `summary`。

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | string | 内容标题。App 不再用链接猜标题，标题**只能**来自这里 |
| `author` | string | 作者/UP 主 |
| `site` | string | 站点显示名 |
| `summary` | string | **一句话说明文案**：后台读懂内容后写给用户看的「这条链接里有什么、建议怎么看」。App 把它当内容主体 —— 卡片上两行，遮罩层里全文 |
| `segments` | object[] | 素材清单，见 §2.3。空数组 + 非空 `failed_reason` 表示解析失败 |
| `failed_reason` | string | 非空表示**解析失败**，此时 `segments` 必为空。App 把这句话原样显示在那条卡片上（卡片和遮罩层各一处），没有全局计数 |
| `resolved_at` | number | 解析完成时间（毫秒），遮罩层的元信息行展示 |

没有 `status` 字段。只有三种情况，各自都能从上面直接读出来：

- `media` 缺失（老数据或后台没解析）→ App 显示「内容信息还没取回来」，条目照常出现在墙上；
- `failed_reason` 非空 → 显示「解析失败」+ 原因；
- 其余 → 用 `summary` + `segments` 渲染。

### 2.3 `segments` 元素 —— 一个可独立浏览或播放的素材

| 字段 | 类型 | 说明 |
|---|---|---|
| `index` | number | 段序号。App 先按它排序，再重新编号成 `0..n-1`，所以**跳号或从 1 起算都不会打乱顺序** |
| `kind` | string | `image` / `video`。大小写不敏感；**其它值一律按 `video` 处理**（宁可给一个播不了的段，也不把图片当视频播） |
| `title` | string | 该段自己的标题，如 `图 2`、`哔哩哔哩视频 1` |
| `cover_url` | string | 视频段的封面图；图片段留空（它自己就是要看的那张图） |
| `url` | string | `video` 段是可播地址（mp4 或 m3u8），`image` 段就是图片本身。**同一个字段两种用途**，App 靠 `kind` 区分 |
| `duration_ms` | number | 视频段时长；图片段填 0。填 0 时 App 的进度条不可拖动 |
| `quality` | string | 视频段清晰度，如 `1080P`；图片段留空 |

顺序即展示顺序：App 的视频墙卡片拿 `segments[0]` 当首图，所以**有可播段时请把视频段排在前面**，纯图集按阅读动线排（第一张最抓人）。参考实现就是这么做的。

顶层不再有 `play_url`/`cover_url`/`duration_ms`/`quality` 的镜像 —— 它们只是 `segments[0]` 的重复，留着只会让两边对不上。

### 2.4 `op` —— 一次变更

```jsonc
{ "type": "UPSERT", "favorite": { "id": "...", "url": "...", /* ... */ } }
{ "type": "DELETE", "favorite_id": "..." }
```

- `type` 只支持 `UPSERT` / `DELETE`，其它值 → 400。
- `UPSERT` 必须带完整 `favorite` 对象（整条送上来，但服务端只写 `changed_fields` 列出的那几列，见下面那条）。
- `DELETE` 必须带非空 `favorite_id`。
- App 用 `explicitNulls=false` 序列化，所以 UPSERT 请求里**不会**出现 `favorite_id: null` 或 `media: null` 这种键。
- **`changed_fields`（参考实现已经读了）**：字符串数组，声明这一次真正改了哪些用户列。服务端按它写列，没列出的列保持行上现值 —— 整条 `favorite` 里 `url`、`source_app`、`favorite_at` 大多是从后台抄回来的旧值，全部当成「这次写的」就会把另一台设备刚改的列吞掉（设计稿 §3 R4）。**缺省、空数组、`["*"]` 三种都算全字段覆盖**，那是老客户端和手搓 curl 的兜底；App 自己每一次写都如实填（`create` → 五列全给，改备注 → `["note"]`，改标签 → `["tags"]`）。`tags` 算**一列**：并发加/删标签会丢一边，这是集合级决胜明写的代价，不是 bug。服务端自有列（`id`/`account_id`/`media`/`updated_at`/`rev`/`deleted_at`）永远不可写，客户端列了也**静默忽略**而不是拒 —— 拒一个本来就写不动的键只会让联调的人以为协议错了。数组里混进非字符串 → 400。
- **`write_hlc{wall_ms,seq}`（参考实现已经读了）**：写在 `favorite` 里，取这一行落库时存的那对戳，`updatedAt==0` 时不发。服务端拿它与行上的内部列 `field_hlc` **逐列**比（比较序 `wall_ms` → `seq` → 写者标识，写者取请求顶层的 `device_id`，见设计稿 §3），赢的那一列才落。`field_hlc` 本身**不上协议**：它是服务端内部列，响应发出前剥掉。
- **决胜戳只有三档，参考实现三档都已落地（`applySync` 的 UPSERT 分支，搜「三档兜底」）**：① `favorite.write_hlc` → `[wall_ms, seq, device_id]`；② 仅 `favorite.updated_at_ms` → `[updated_at_ms, 0, device_id]`；③ 两个都不带 → `[now, 0, device_id]`，也就是「按到达顺序整条写」的老语义。**两键同带按第一档，不混算**。超前全部**夹紧、不拒**（拒一个只是钟不准的写入等于惩罚时区没设对的设备）：第一档 `wall_ms > now+5min` 夹到 `now+5min`（`seq` 与档位都不变，夹紧后照旧走 `wall_ms→seq→写者`），第二档 `updated_at_ms > now+5min` **退回 `now`**（不是 `now+5min` —— 设计稿 §3 就这么写的，两档由此真的不同档），`updated_at_ms` 为负夹到 0。校验口径同 `write_hlc`：键存在却不是有限数字 → 400。
- **`favorite.updated_at_ms`（第二档的载体，§5 表格已登记）**：本 App **从不发它** —— 有戳就发 `write_hlc`，没戳就两个都不发，退回第三档。它是给「只知道行上次更新时间、没有 HLC 序列」的写入者（例如第三方接入面）用的兜底位，参考实现读它但不存它：`normalizeFavorite` 重建六个键时把它剥掉，落库列里没有这一位。
- **`favorite_at` 范围夹紧（同一分支，搜「favorite_at 夹紧」）**：合法区间 `[now−10年, now+5min]`，超出同样**夹成本值 + 记一行日志 + 不拒**。夹在**归并取较旧之前**做：先夹再用夹后的值参与「归并取较老的 `favorite_at`」，否则一个未来的垃圾值会把新收藏判成老收藏、把 keyset 游标顶跳条。这条对分页有连带后果 —— 所有早于 2016 的值会被压成同一个数，而单列游标在并列值上会漏条，所以复合 `(favorite_at, id)` 游标不是锦上添花 —— 它已落地，见 §3.2。
- **App 已经在发、参考实现只当情报的键**：`base_rev`（本次编辑基于哪一版，本机 `rev==0` 时不发）。参考实现从 ③-1a 起**已经发 `rev`**，所以 App 本地行拿到版本号之后现在是真的会送 `base_rev` 的 —— 但服务端**不做版本冲突判定，这是定下来的语义而不是没做完**：`base_rev` 落后于行上现值时照旧按上面的逐列 HLC 决胜落库，这个键只当排障线索（设计稿 §5 的裁决、§7 的 ③-2 那行）。联调时别把「发了 `base_rev` 却没被拒」当成漏实现。

### 2.5 只存在本地、不上传的东西

观看进度（段序号 + 逐段位置）只写在 App 本地的 Room（`segmentProgress` / `lastSegmentIndex`），协议里没有对应字段。原因：多设备同步进度要引入冲突裁决（谁的进度算数），而这条链路上唯一有价值的是「接着看」，把它做成服务端字段带来的复杂度和收益完全不匹配。换设备后从头一段开始看。

标签关系（哪个标签挂在哪条收藏上）本地维护，上传时以标签名数组呈现，服务端自己映射成 ID。

## 3. 接口清单

### 3.1 `POST /sync` —— 上传变更（App 唯一的写接口）

请求：

```json
{
  "device_id": "tab-3f2a9c1d7b40",
  "sent_at": 1763122500000,
  "ops": [
    {
      "type": "UPSERT",
      "favorite": {
        "id": "9f1c0a5e-2b7d-4c8a-9f3e-6d0a1b2c3d4e",
        "url": "https://www.bilibili.com/video/BV1xx411c7mD",
        "note": "周末看",
        "tags": ["待看", "算法"],
        "source_app": "chrome",
        "favorite_at": 1763122400000,
        "write_hlc": { "wall_ms": 1763122400000, "seq": 3 }
      },
      "changed_fields": ["note"]
    }
  ]
}
```

`write_hlc` **只在 `favorite` 里才有效**（设计稿 §5 的字段表把它登在 `op.favorite` 那一行，参考实现也只在这里读）。放在 `op` 顶层不会报错，但服务端当它不存在 —— 于是这一笔退回第三档（`server_time`，见 §2.4），逐字段决胜就地失效，两台设备的并发编辑重新变成「后到的全赢」；而第三档的戳比任何真实 HLC 都新，所以一笔**旧**改动反过来会吃掉别人刚写的那一列。这条区别在联调时只能靠「用一个明显很旧的 `wall_ms` 去写、看它赢不赢」验出来，响应里没有任何键会说。

`changed_fields` 里只声明这次真改过的列；`write_hlc` 与 `base_rev` 都取自这一行落库时存的那对戳，不是发送时现取的钟。本 App 只发 `write_hlc`（第一档）或不发（第三档），从不发 `updated_at_ms`。

成功响应（200）：

```json
{
  "ok": true,
  "server_time": 1763122500123,
  "applied": 1,
  "unknown_ops": [],
  "favorites": [{
    "id": "9f1c0a5e-2b7d-4c8a-9f3e-6d0a1b2c3d4e",
    "url": "https://www.bilibili.com/video/BV1xx411c7mD",
    "note": "周末看",
    "tags": ["待看", "算法"],
    "source_app": "chrome",
    "favorite_at": 1763122400000,
    "account_id": "acct-f010fc20222bf72d",
    "updated_at": 1763122500100,
    "rev": 7,
    "media": {
      "title": "哔哩哔哩视频 · a3f19c",
      "author": "阿测",
      "site": "哔哩哔哩",
      "summary": "UP 主实测 3 款降噪耳机，先看 8 分钟对比视频，再对照 4 张频谱图。",
      "segments": [
        { "index": 0, "kind": "video", "title": "哔哩哔哩视频 1", "cover_url": "https://picsum.photos/seed/a3f19c2d-v0/640/360", "url": "https://.../x36xhzz.m3u8", "duration_ms": 480000, "quality": "1080P" },
        { "index": 1, "kind": "video", "title": "哔哩哔哩视频 2", "cover_url": "https://picsum.photos/seed/a3f19c2d-v1/640/360", "url": "https://.../BigBuckBunny.mp4", "duration_ms": 660000, "quality": "720P" },
        { "index": 2, "kind": "image", "title": "图 1", "cover_url": "", "url": "https://picsum.photos/seed/a3f19c2d-i0/1280/720", "duration_ms": 0, "quality": "" }
      ],
      "failed_reason": "",
      "resolved_at": 1763122500120
    }
  }],
  "merged_into": [],
  "op_errors": [],
  "rev": 7,
  "next_wait_ms": 3000,
  "error": ""
}
```

字段语义：

- `applied`：**服务端确实落库的条数**。UPSERT 成功计 1，删除计 1 —— 删除现在是**墓碑化**（写 `deleted_at`、行保留），对同一个 id 重复删同样计 1，那是幂等而不是错误。
- `unknown_ops`：要删但服务端没有这个 ID 的 `favorite_id` 列表。**这不是错误**：多设备场景下别的设备已经删过，属正常收敛，App 一样会清掉本地数据。「这个 id 属于别人的账号」也走这里，**不回**「存在但无权限」那种说法，否则等于帮人枚举他人收藏。**这一档只服务删除**：写侧被拒的 op 不进这里，进下面的 `op_errors` —— 因为 App 把 `unknown_ops` 计入「已确认」，走到那儿的条目会**出队并标绿**，用它能表达「后台不需要再管这条」，表达不了「后台拒了这一笔、改动还压在本机」。
- 账号归属：每行落库时都盖服务端自己解出的 `account_id`（见 §3.5）。**已裁并已在参考实现落地（2026-11-19）：写侧也拦。** 拿别人的 `favorite_id` 发 UPSERT 属于该 op 被拒，进 `op_errors`（中性原因，例如「这一条不存在或不属于本账号」），**该行一个字都不改、不计 `applied`**；早前参考实现那句「写内容、不换主人」是当时的现状，已下线。删除侧维持「与不存在同一个出口」的 `unknown_ops`。
- `op_errors: [{op_index, id, reason}]`：**被拒的 op 与它的中文原因**，`op_index` 定位的是**这一次请求里的那一批**中的位置（与本地队列自增 id 无关）。不计入 `applied`，也不进 `unknown_ops`。App 判据：`applied + len(unknown_ops) + len(op_errors) == len(ops)` 先确认后台把每一条都答了，然后**被点名的那一条单独标红 FAILED、留在队列、把 `reason` 原样写进 `lastError`**（顶栏「失败 N」点开可见）—— 那是数据层面的拒绝，再发一次还是同样判据，不自动重试。不下发这个键的老后台，App 退回上一等式（`applied + unknown_ops`）。
- `merged_into: [{op_index, from_id, to_id}]`：这次写的 id 被 url 判重归进另一行时下发，`from_id` 是调用方发出的那个、`to_id` 是后台留下的那个。App 在回填前先按它改本机主键，再拿 `to_id` 翻 badge —— 少这一步，卡片上那个「待同步」点会永远留着而队列里对应的 op 早被删掉。**它只在真有列落下时才发**：url 命中了别人的行但这次写每一列都判输（`applied` 仍计 1、`favorites` 为空）时，后台什么都没并，`merged_into` 也就是空的（钉在 `mock-server/test/legacy-field-stamp.test.mjs` 的 M4-b）。这一笔的后果要说死：本机那个 `from_id` 在后台根本不存在，而 op 已按等式确认出队 —— 撞上它要求本机这一笔的戳确实判输（HLC 的 `wall_ms` 取的是各自设备的物理时间，§3 的超前夹紧只管走得快的、不管走得慢的；慢的那台同毫秒时还要比写者串），正常同毫秒以外的收藏动作总是赢列、总带回执。
- 顶层 `rev`：这个账号当前的最新号（`favorites` 里每项各自带自己那行的 `rev`）。App 存下来当 `base_rev` 与对账起点参考，**不参与落库判据**（§3 那条裁决）。
- 解析缓存：同一 `url` 只解析一次，改 `note`/`tags` 重传**不会重爬**，回来的 `media` 与 `resolved_at` 与上次逐字节相同（缓存对象在多条同 url 的行之间是同一个只读引用）。
- `favorites`：**本次涉及条目的最新状态，每条都已带 `media`**。App 直接落库并渲染，不会再回头问一次。所以解析失败就在 `failed_reason` 里写清楚，别为了「响应好看」编一段假内容出来。
- `next_wait_ms`：**服务端建议「下一条上传前等多久」**。App 每次请求只带一条 op，这个值因此精确对应单条的节奏。缺省（不下发该字段或为 null）时 App 退回设置页的「上传间隔」（默认 3000ms，填 0 表示不限速）。参考实现默认固定 3000ms，可用 `UPLOAD_WAIT_JITTER_MS` 按下发序号抖动，验证 App 是否真的读服务端的建议而不是只用自己的配置。
- `error`：失败原因（中文，会直接显示在 App 列表/设置里）。

失败响应示例（400，`Content-Type` 仍是 JSON）：

```json
{ "ok": false, "error": "第 1 条操作（UPSERT）缺少 favorite.id", "applied": 0, "unknown_ops": [] }
```

**服务端实现必须守住的不变式：`applied + len(unknown_ops) + len(op_errors) == len(ops)`**（没有 `op_errors` 这个键的老后台是它的退化形 `applied + len(unknown_ops) == len(ops)`）。App 的成功判据就是这个等式；不等时条目留在队列并标红（详见 §5）。**被拒不算确认**：一个 op 进了 `op_errors` 就绝不能再计进 `applied`，否则拒绝会被判成假成功。参考实现在内部也做了同一断言，对不上宁可抛 500，也不回一个「看起来成功」的空响应。

### 3.2 `GET /favorites?limit=&cursor=` —— 分页拉取收藏

服务端是收藏的事实来源，App 本地那张表只是**分页缓存**：

- 冷启动发现本地缓存为空（换机、清数据）→ 自动取第一页，不用用户点；
- 视频墙滚到离底还有两屏 → 静默取下一页；
- 空列表/抽屉里的「从后台加载我的收藏」是同一件事的手动入口。

请求：`GET /favorites?limit=50`，续页时带上 `&cursor=<上一页返回的 next_cursor>`（App 会对游标做 URL 编码）。

响应：

```json
{
  "ok": true,
  "server_time": 1763122500123,
  "favorites": [ /* favorite 对象数组，每条都带 media，最多 limit 条 */ ],
  "total": 1280,
  "next_cursor": "1763120000000.11111111-1111-1111-1111-111111111111",
  "has_more": true
}
```

- 这个接口是**按账号读**的：只返回 `account_id` 等于本次请求解出的那个账号的行，别的账号的行连数量都不透露（`total` 也只数自己的）。没有 `account_id` 的行一律不可见 —— 参考实现不模拟升级前的老数据，每行写侧都会盖归属。墓碑（`deleted_at` 非空）对外的可见性等同已物理删除，一律过滤。
- 排序与游标是一件事，请**按 `(favorite_at 倒序, id 升序)` 这个复合键**返回并翻页：`next_cursor` 是上一页最后一条的 `(favorite_at, id)` 拼成的**不透明串** `<favorite_at>.<id 的 URL 编码>`（并列时按 id 字典序切），App 只把它原样回传、不解析。为什么不能用单列 `favorite_at`：`favorite_at` 会被夹紧（§2.4 搜「favorite_at 夹紧」），夹完必然出现同一个值，单列游标在并列值上要么漏条要么重复。为什么不能用偏移量：翻页途中新收藏一条就会把下一页顶掉一条。复合键切得干净，边界上不重不漏；万一后台把边界那条重复发了一次，App 导入按 `id` 命中、命不中再按 `url` 命中（`FavoritesRepository.importRemote`），只会刷新成同一行而不会变两行 —— 那是兜底，不该被触发。
- 游标**不合法就明确回 400，不要退回第一页**：退第一页会让 App 陷入「拉到同一页 → 游标不变 → 再拉同一页」的死循环，400 才会把这次翻页失败暴露成一次可见的失败。参考实现现在对纯数字（旧单列格式）就是 400，原文：`cursor 不是合法的复合游标，请把上一次响应里的 next_cursor 原样回传`。
- `total`：**这个账号下的收藏总数**（不含已删除），每页都带同一个值。App 只在 `has_more=true` 时用它：顶栏说「共 1280 条 · 已取回 50 条」，墙头说「已取回 50 / 1280 条」。**页取全了就不再看这个数** —— 它只在翻页时刷新，本地那时已经是后台的镜像，还拿它跟本地条数比，删掉一条会说出「共 20 条 · 已取回 19 条」这种把刚删的那条说成还没取回的话，所以取全后一律只报本地条数。不下发或为 0 时同样退回只显示本地条数，不会编出一个总数。
- `next_cursor` 为空或 `has_more=false` 都表示到底了，App 就不再补页（列表尾部显示「到底了」）。
- `has_more=true` 却返回 0 条，App 按到底处理，避免无休止地滚动补页。
- 某条的 `media` 缺失时，该条在 App 里显示「内容信息还没取回来」，条目照常出现在墙上 —— 这不是错误状态，全局也没有对应的计数。
- 4xx → 手动入口提示「从后台加载失败：后台拒绝：HTTP xxx」；网络层失败 → 提示「从后台加载失败：<IO 原因>」。自动补页失败不弹提示，只把尾部的加载位收回去。这个接口只读，不会污染上传队列。

### 3.3 `POST /resolve` —— 强制重新解析

App 侧唯一入口：遮罩层里的「重新解析」按钮（每次只传 1 个 ID）。**App 不会自动重试解析** —— 同一条链接的解析结果由链接本身决定，再问一遍只会多占一个出站时隙。

请求：`{ "favorite_ids": ["9f1c0a5e-..."] }`

响应：`{ "ok": true, "server_time": 1763122500123, "favorites": [ /* 带新 media 的收藏 */ ], "unknown_ids": [ /* 后台没有这条收藏 */ ] }`

语义：

- 让服务端**丢弃旧结果重算**（例如换了解析器、之前解析失败）。ID 去重由服务端负责；参考实现会跳过空白与重复 ID，落库后再返回。
- **`favorite_at` 不能变**：重解析不该把这条顶到列表最前。参考实现只替换 `media` 和 `updated_at`。
- 后台没有的 ID 放进 `unknown_ids`，整体仍回 200。App 见到「全部未知」提示「后台没有这条收藏」。**墓碑与别人的账号也走这一条**：参考实现里「不存在 / 已删 / 不归你」三种情况共用同一个出口，不额外区分 —— 区分就是泄露。
- 响应里没有 favorites 也没有 unknown_ids 时，App 提示「后台没有返回解析结果」。

### 3.4 `GET /health` —— 免鉴权自查

```json
{ "ok": true, "server_time": 1763122500123, "host": "0.0.0.0", "port": 8787,
  "favorites": 20, "tombstones": 3, "accounts": 1, "account_isolation": true, "resolver": "mock",
  "clock_skew": { "ahead": 1, "behind": 1, "max_abs_ms": 2592001377 } }
```

`favorites` 只数活条目，`tombstones` 单独数「已删但还在保留窗口里」的行数 —— 分开报才看得出磁盘上的字节是活数据占的还是没 GC 掉的删除标记占的。`accounts` 只报数量，不露 `account_id`、不露 token 哈希。

`clock_skew` 是**运维观察指标，不下发**：按账号累计「客户端声称的写时刻」与「服务端接收时刻」的差，超前 = 比 `now+5min` 还靠前、滞后 = 落后超过 24 小时（正常离线写作在小时量级，超过一天更像时钟坏了），`max_abs_ms` 取账号内最大绝对偏移。上面这份是实测：一笔 `write_hlc` 报未来 10 天记 `ahead`，一笔 `updated_at_ms` 报 30 天前记 `behind`，同一实例上合法戳与「两把都不带」的第三档各一笔都不计数 —— 第三档的戳就是服务端 `now`，偏移恒为 0，记进去只会稀释。它记的是**夹紧前**客户端自己声称的戳，否则夹紧会把问题本身抹掉。计数只在进程内（不落盘，重启清零），且**只进 `/health` 与日志**：`/meta`、`/favorites`、`/favorites/changes` 都不带这个键，App 也不得据它改判据 —— 客户端拿它做决定就等于把一个观察指标变成协议。

用途：平板浏览器先打这个，确认网络可达再调数据接口。App 不调用。

### 3.5 `GET /meta` —— 免鉴权自述能力

```json
{ "ok": true, "server_time": 1763122500123, "cursor_style": "keyset:favorite_at_desc,id_asc",
  "cursor_note": "复合 keyset 分页：favorite_at 降序、并列时 id 字典序升序；游标是不透明串（favorite_at.id），原样回传",
  "changes_retention_days": 30, "tombstones": 0,
  "resolve_requires_auth": false,
  "account_isolation": true,
  "account_note": "设 SYNC_TOKEN 时令牌对应一个账号；未设时整实例共享一个匿名账号，多设备互相可见",
  "next_wait_ms": 3000, "next_wait_jitter_ms": 0,
  "resolver": { "name": "mock", "deterministic_by_url": true, "note": "同一 url 永远得到同一份结果；保存与解析同一次调用完成，不联网" } }
```

- 定位是**联调第一步**：先打 `/meta` 看这个后台到底怎么分页、解析是否按 url 确定性、墓碑留几天、账号怎么分，再去搓数据接口。App 不调用它，App 的节奏仍然只读响应里的 `next_wait_ms`。
- `SYNC_TOKEN` 设了值它也回 200 —— 免鉴权是这条接口的定义，不是漏配。
- 参考实现**故意不下发** `max_ops_per_request`：App 每次一条是客户端自己的策略（§4），不是服务端限制，编一个限制出来只会让人去凑一个不存在的数。
- 手动清墓碑：`POST /gc`（要鉴权），配合 `CHANGES_RETENTION_DAYS=0` 的实例可以在测试里当场验证保留窗口真的生效。同一次 GC 里 `revision_log` 也按**同一个窗口**一起清，并把该账号被清掉的最大 rev 记进 truncated 的水位线 —— 墓碑清了而日志留着，`/changes` 就会发出一条指向已经不存在的那行的 `deleted` 假消息。

### 3.6 `GET /favorites/changes?since_rev=&limit=` —— 增量对账

真实形状（一笔改动 + 一笔删除）：

```json
{ "ok": true, "server_time": 1763122500500,
  "items": [
    { "rev": 7, "favorite_id": "9f1c0a5e-2b7d-4c8a-9f3e-6d0a1b2c3d4e", "deleted": false,
      "favorite": { "id": "9f1c0a5e-2b7d-4c8a-9f3e-6d0a1b2c3d4e", "url": "https://www.bilibili.com/video/BV1xx411c7mD",
                    "note": "周末看", "tags": ["待看"], "source_app": "chrome", "favorite_at": 1763122400000,
                    "account_id": "acct-f010fc20222bf72d", "rev": 7,
                    "media": { "title": "…", "segments": [] }, "updated_at": 1763122500300 } },
    { "rev": 8, "favorite_id": "11111111-1111-1111-1111-111111111111", "deleted": true }
  ],
  "next_rev": 8, "truncated": false }
```

- 唯一来源是服务端的 `revision_log`：每次真实落库在**发号的同一步**追加一条，条目写下去就不再改。同一条收藏连改两次，这里能看到两笔，第一笔的 `favorite` 仍是它当时那份快照（不是最终值）。
- `favorite` 里除协议字段外还带 `account_id` 与 `updated_at` 两个服务端自有列（实测就在这条通道上，`GET /favorites` 与上传回执同一份形状）：App 的 `FavoriteDto` 两个都没声明，靠上面那张表的 `ignoreUnknownKeys` 吸收，本机没有读它们的判据。但**别把这句说成「这两列不参与任何判据」**：`account_id` 是行归属，跨账号 id 撞车时它在**判据**里出现 —— 落库前先比归属，不等于本账号就整 op 拒掉（`server.mjs` 的归属校验在 UPSERT 分支最前面，[server.mjs:624-634](../mock-server/server.mjs#L624-L634)），比完之后新行与目标行的 `account_id` 一律写成本次解出的账号，没有任何「照抄别人归属」的分支。**已裁并落地（2026-11-19）：写侧拦，进 `op_errors`、原因用中性文案**（口径见 §2 那两条 bullet，常驻断言见 `mock-server/test/cross-account.test.mjs` 的 M1-c 与 `mock-server/test/server.test.mjs` 的「跨账号 id 撞车的 UPSERT 被拦」）；早前这里的「写内容、不换主人」现状描述、以及它与设计稿 §2 R1 相互矛盾的那段登记，随这次落地一并消掉了。`updated_at` 是服务端自己写的时刻（跟客户端声称的 `favorite.updated_at_ms` 不是一回事），在行缺 `field_hlc` 时会被拿去派生旧决胜戳 —— 只有没被新写盖过的历史行走那条兜底，新写一律比 `field_hlc`；这条兜底的两个后果（平局比的是账号串、以及一列真落库后其余无戳列继承新的 `updated_at`）钉在 `mock-server/test/legacy-field-stamp.test.mjs`。
- `since_rev` 是**严格大于**。本机存的 `next_rev` 就是上一批最后一条的 rev，服务端要是取 `>=` 就每批重复回同一条。
- **`since_rev` 不是合法数字时静默按 0 处理，这里刻意不给 400**（实测：`since_rev=abc` 与 `since_rev=-5` 都回 200，两条响应除 `server_time` 外内容一致 —— 都按「从头起」走）。**归 0 ≠ 空响应**，这一句要说死：判据是 `rev > sinceRev`，所以账号里没日志时才是 `items: []` + `next_rev: 0`（空批回送起点），日志还在窗口里就变成**整段从头重放**、`next_rev` = 这批最后一条的 rev。跟 §3.2 那条「游标不合法必须 400」不是自相矛盾，是两个键的性质不同：`cursor` 是**不透明串**，客户端猜不出来、退第一页会让翻页陷在「同一页 → 游标不变 → 同一页」的死循环；`since_rev` 是本机自己从 DataStore 读出来再写回去的**数字**，没有格式可猜错，退 0 的后果是把保留窗口内的日志从头重对一遍 —— 每批游标严格前进，因而**必然收敛**，且重放的是幂等写入（活条目走 `importRemote`；已删那一笔若本机早已没有这行就是空转，但**会连带清掉同 id 未上传的 op**，见下面「先删后活」那条）。同一判据还带着 `truncated`：归 0 之后 `since_rev > 0` 不成立，所以永远不会把「从头起」误报成「中间缺了一段」。真后台若要收严，收严成「非数字 400、负数夹 0」都可以，但**别改成退第一页且不给信号**那种半态。
- **翻页判据只有两条，契约里没有 `has_more`**：`items` 为空 = 这一段对完了，停在 `next_rev`；`items` 满一页才继续拉下一批。少一个键是有意为之 —— 它和「整页长度」说的是同一件事，两处给就有一处会说不清。
- **一轮对账是有界的**：App 侧 `MAX_PAGES = 3`、`CHANGE_PAGE = 200`，一轮最多 600 笔，跑满返回 `PAGE_CAP`。落库与推游标是**逐批**做的（每批 `applyChanges` 成功才 `setSinceRev(next_rev)`），所以停在「本机落完的最后一批末尾」，绝不越过没落库的那一段，下一轮从这里接着对、不会跳条。跑满这件事**现在有一个消费者**（`SyncWorker.reconcileQuietly`）：同一次 worker 运行里，若 `reconcile()` 回 `PAGE_CAP` 且 drain 那条 `startedAt + MAX_RUN_MS`（3 分钟）的时间窗还没用完，就**再调一次**、次数写死 1，第二次还是 `PAGE_CAP` 就算了，剩下的留给下一次触发（用户动作或联网回调把 worker 拉起来）。这不是定时循环：续跑的前提是「这一轮已经落定了」，没有 `delay`、没有 `Timer`、没有周期任务，判据用的还是 worker 已有的那把表。要知道的边界：deadline 只决定**要不要**续跑，不约束续跑本身，所以第二轮内部仍是最坏 3 页 × `callTimeout`，可能越过 `MAX_RUN_MS` —— 被 WorkManager 停也安全，因为游标只在每批落库成功后才推。另外：**把 `CHANGE_PAGE` 改大是无效的** —— 参考实现在服务端夹（`clampLimit` 的 `Math.min(Math.floor(value), 200)`，`/favorites` 与 `/changes` 同一条），App 侧出站不夹、原样发，超出的部分由后台砍掉。真后台换实现要记得这条砍幅，否则同一份客户端行为会漂。
- `deleted: true` 那笔**不带 `favorite`**，App 收到即物理删除本地行、连播放进度一起删，并且**在同一条 Room 事务里清掉这条收藏在本机还没上传的 op**（`FavoritesRepository.applyChanges` 的删除档 + `clearSameFavorite`）。不清就是复活：`pending_ops` 对 `favorites` 没有外键，行没了那笔 op 还留着，下一轮 `SyncWorker` 把它当新 UPSERT 发上去，而后台在同一次调用里保存+解析 —— 删除只写 `deleted_at`、不发字段戳，决胜里根本没有"删过"这件事，于是已删的收藏带着旧内容回来了。后果是**本机那份没传出去的编辑丢**（这台设备接受账号已经把它删了），设置页「立即重试」也救不回它 —— 队列里没有了，正是想要的，否则那颗按钮就是复活入口。**同一批里先删后活**（`since_rev` 归 0 从头重放时真会遇到，实测一页四笔就是 `1:alive 2:alive 3:DELETE 4:alive`，同一个 `favorite_id`）是同一类结局：删除那步清掉 op，复活那步按后台快照新建行并标 SYNCED，本机最终拿到的是后台那一版。**这条是四条数据接口里唯一能把本机行删掉的路**：`GET /favorites` 和上传回执都是按 `deleted_at` 过滤过才发的，永远不会带删除信息进来。
- `next_rev` 在空批时回送本机这次的起点而不是 0；App 侧也做了同一半兜底（后台漏发这个键时保住游标），否则下一轮会从头重对一整段。
- `truncated: true` 表示 `since_rev` 掉出了 `CHANGES_RETENTION_DAYS` 窗口、这批不完整：App 丢弃游标改走全量翻页。判据是服务端内部的**水位线**（账号 → 被清掉的最大 rev），水位线本身不上协议，响应里只有 `truncated` 这个本来就在契约里的键。`since_rev=0`（从没对过）永远不算 truncated —— 那是从头起，不是中间缺了一段。
- 账号隔离与 `GET /favorites` 一致：别的账号写过什么，在这一行的 `/changes` 里一条都不出现。第三方经 ingest 面写入的改动也走同一份日志，所以 App 看见别人的录入**不需要任何新接口或新字段**。
- App 侧现状：**出站、落库与游标持久化都已实现**（`SyncApi.fetchChanges` + `FavoritesRepository.applyChanges` 逐条按后台给的顺序应用、不开整批事务；`AppSettings.setSinceRev` 按账号指纹存 `since_rev`，`SyncManager.reconcile()` 每批落完才推进）。触发时机接了两条：`SyncWorker` 把队列跑到 `nextDue == null`（干净）时顺手对一次（4b-2a）；`MainActivity.onResume` 里用 `window.decorView.post { … }` 挂一次进前台对账（4b-2b-i）—— 挂在这条 Runnable 上而不是直接 `lifecycleScope.launch`，因为后者是 `Main.immediate`，冷启动时会在首帧之前就把请求发出去。它前面有两道退让：`_state.value.online` 为假直接返回（离线不占出站时隙），`cachedCount() == 0` 也返回（表空 = 换机或清了数据，`seedRemoteCache` 已经去取第一页，再来一次全量日志重放等于把同一件事做两遍）。这条退让有边界，得说死：**「换机首装」与「清过数据」的设备，第一次进前台不对账**，要等表里落进第一条（第一次上传或第一次补页）之后的下一次进前台才对得上；空表时翻页本来就是正解，`since_rev` 那段日志缺的也只是「别人删过的行本机根本没有」，翻页落库时不需要它。落删除时同事务清队列 op（上一条）已接（4b-2c）。`truncated` 的善后也已接：游标退回第一页、把 `remoteHasMore` 扶正再走既有的 `loadRemotePage`，不新写第二份翻页。**跑满一轮 600 笔（`PAGE_CAP`）后的「落定即续一次」也已接**（4b-2b-ii，落在 worker 那一档，判据见上一条）。至此 `Reconcile` 七个值里被消费的只有两个：`TRUNCATED`（界面退回全量翻页）与 `PAGE_CAP`（worker 同一次运行内续跑一次）；`CONVERGED / UNSUPPORTED / FAILED / BUSY / RETRY_LATER` 仍只是返回值、不驱动任何行为。设计稿里列的第三个触发点「联网回调」**已裁（2026-11-19）：不加对账，只补传**（`SyncManager.init` 里 `connectivity.onlineTransitions().collect { flush() }`，到此为止）。理由说死：对账已经有 worker 排空与进前台两档接着，本机什么都不写的纯接收设备等到下一次进前台收敛，代价只是晚一点；而联网跳变那一刻往往正有攒下的改动要发，再插一档对账会抢出站时隙，对账结果还会被自己的在途改动盖住 —— 这正是当初把它放在 worker 排空之后而不是开头的原因。

## 4. 上传节奏：一次一条

`SyncWorker` 是队列的执行体，行为如下（这些决定了服务端会看到什么样的流量）：

1. 每次 `nextDue(now)` 只取**一条**到期 op，`ops` 数组长度恒为 1（`OPS_PER_REQUEST = 1`）。串行是为了让 `next_wait_ms` 精确对应单条，失败时也能定位到具体条目。
2. 成功后：`wait = next_wait_ms ?? 设置里的上传间隔`，把队列里其余条目的 `nextRetryAt` 统一排到 `now + wait`，然后 `delay(wait)` 再取下一条。`wait <= 0` 时不等待。
3. 单次 `doWork()` 最多跑 3 分钟（`MAX_RUN_MS`）；时间片用完但队列非空 → `Result.retry()`，由 WorkManager 线性退避 4s 后继续。**无常驻定时器、不轮询**。
4. 载荷无法解析（极端情况，如升级后字段变更）→ 丢弃该 op 继续跑，避免整条队列被一条坏数据永久堵住。
5. 队列在 App 里**先落 Room 再入队**，所以「保存即生效」不依赖网络；同一条目短时间反复编辑只发最新版本 —— 入队时「清掉该条目尚未上传的旧载荷」和「插新载荷」落在**同一笔 Room 事务**里，分开跑的话 `SyncWorker` 能插在两步中间看到「旧的已删、新的未入」而白跑一轮。入队还跑在一条串行线程上，两次连续编辑不会并发各插一笔。
6. 有一档兜底扫尾：进程正好在「写完用户字段」与「入队」这两笔事务之间被杀，那一行会一直显示待同步、队列里却没有可传的东西，它不会自己复活。`SyncWorker.drain()` 开头扫一次「badge 是 QUEUED 但 `pending_ops` 里没有 op」的行，活行补一条 UPSERT（**不带 `changed_fields`**，也就是 §2.4 的「全字段覆盖」那一档 —— 本机已经不知道用户那一次改的是哪一列，宁可少声明不可误声明）、墓碑补 DELETE。扫尾只在 worker 被拉起时跑，**不在冷启动路径上、也没有定时器**，这两条是硬约束。
7. 后台确认收了这一条，**不等于本机接住了**：`importRemote` 是逐条 try 的（脏载荷只进 `skipped`/`broken` 计数，不抛），所以 worker 先落库、再看那两个计数 —— 非零就**不销账**，沿用后台拒绝那一档形状（留在队列、`nextRetryAt` 排到遥远将来、标 FAILED、`lastError` 写清是哪个计数没对上）。不这样就会出现「后台已有、队列已清、卡片标 SYNCED 而行还停在旧内容」那格没人负责的账。销账本身（`ops.delete`）与 badge 翻转还共用一个判据：**这一笔得还在队列里**（受影响行数 > 0）才允许翻 —— 在途时用户又动了同一条收藏的话，`queue()` 早已把它换成新载荷，旧回执没有资格替新那笔定成败。

取列表（`GET /favorites`）和重新解析（`POST /resolve`）走同一个 `SyncGate` 时隙，但**不入队** —— 它们是即发即收的读操作，失败了由 UI 提示，不产生待重试的 op。

## 5. 状态码 → App 行为对照表

| 服务端表现 | App 归类 | App 行为 |
|---|---|---|
| 2xx，`ok=true`，`applied + unknown_ops + op_errors == 送出条数` | 成功 | 出队该条、标绿（SYNCED）、落库返回的 `favorites`（含 `media`）；`DELETE` 则物理删除本地条目；按 `next_wait_ms` 节奏继续 |
| 2xx，`ok=true`，但这一条被 `op_errors` 点名（典型：同 id 换 url、拿别人的 id 写） | 拒绝 | **留在队列**、标红 FAILED，`lastError` 写后台给的那句中文原因，顶栏「失败 N」点开可见；不自动重试（判据是数据层面的，重发还是同一结果） |
| 2xx，`ok=true`，但确认条数不足（典型：`applied=0`） | **假成功** | **条目留在队列**，`nextRetryAt` 排到遥远将来，标红 FAILED，原因写「后台确认条数不符（applied=0）」。需要用户在设置页「立即重试」。**这是最早那版静默丢数据的根因，绝不允许** |
| 2xx，`ok=false` | 拒绝 | 同上（标红、留在队列），显示服务端 `error` 文本 |
| 400 / 404 / 413 等 4xx | 拒绝 | 同上；优先展示响应体里的中文 `error`，没有则「后台拒绝：HTTP xxx」 |
| 401 | 拒绝 | 同上 —— 令牌不匹配不会自动重试，请让用户在设置页改令牌后点「立即重试」 |
| 429 | 可重试 | 按 `attempts × 8s` 退避（**App 读的是响应体 `next_wait_ms`，不看 `Retry-After` 头**，限速时请把等待时间放进 JSON） |
| 5xx | 可重试 | 按 `attempts × 8s` 退避 |
| 连接失败 / 超时 / 响应不是合法 JSON | 可重试 | 同上，原因显示「网络不可用」「后台响应格式不符：…」 |

重试上限 `MAX_ATTEMPTS = 3`。用尽后条目**仍留在队列**（`nextRetryAt=0`，随时可跑）并标红：联网回调、下次改动、或用户点「立即重试」都会自动补传 —— 与原始需求里「静默重试 3 次后转本地待上传队列，之后自动补传」一致。

WorkManager 侧另有约束：没有网络时任务不会被调度（`NetworkType.CONNECTED`），网络恢复由 `Connectivity` 回调触发一次 `flush()`。

**界面上因此只有三种状态词，全app统一：**「离线」（连不上后台）、「待同步 N」（队列里还有没上传完的）、「失败 N」（重试次数用尽或被拒绝）。解析失败不占任何全局计数 —— 它只是那条卡片上的一行文字。

## 6. 校验规则（参考实现逐条对应，真实后台建议照抄）

`POST /sync` 的校验是**全有或全无**：任何一条不合法就整批 400，绝不部分应用。错误消息都带「第 N 条操作」定位。

> 这条口径**只适用于 App 面**。第三方走的 ingest 面是**逐条独立应用**（一条脏 url 只拒那一条，其余照常落库），批量场景整批回滚会逼调用方二分重发。见 [第三方采集服务接入接口.md](第三方采集服务接入接口.md) §0/§4。

| 情况 | HTTP | `error` 文本 |
|---|---|---|
| 请求体不是 JSON | 400 | `请求体不是合法 JSON` |
| 请求体不是对象 | 400 | `请求体必须是 JSON 对象` |
| 缺 `device_id` 或为空白 | 400 | `缺少 device_id` |
| `ops` 不是数组 | 400 | `ops 必须是数组` |
| `ops` 里某项不是对象 | 400 | `第 N 条操作不是 JSON 对象` |
| `type` 不是 UPSERT/DELETE | 400 | `第 N 条操作的 type 只支持 UPSERT / DELETE` |
| UPSERT 缺 `favorite` | 400 | `第 N 条操作（UPSERT）缺少 favorite 对象` |
| UPSERT 缺/空 `favorite.id` | 400 | `第 N 条操作（UPSERT）缺少 favorite.id` |
| `favorite.url` 不是字符串 | 400 | `第 N 条操作（UPSERT）的 favorite.url 必须是字符串` |
| `favorite.tags` 不是字符串数组 | 400 | `第 N 条操作的 favorite.tags 必须是字符串数组` |
| `note`/`source_app` 类型不对 | 400 | `…的 favorite.xxx 必须是字符串` |
| `favorite_at` 不是有限数 | 400 | `…的 favorite.favorite_at 必须是数字` |
| `favorite.write_hlc` 结构不对（缺 `wall_ms`/`seq` 或不是数字） | 400 | `…的 favorite.write_hlc 必须是 {wall_ms, seq} 两个数字` |
| `favorite.updated_at_ms` 存在但不是有限数字 | 400 | `…的 favorite.updated_at_ms 必须是数字` |
| `changed_fields` 不是字符串数组 | 400 | `…的 changed_fields 必须是字符串数组` |
| DELETE 缺 `favorite_id` | 400 | `第 N 条操作（DELETE）缺少 favorite_id` |
| 读路径另有一条：`GET /favorites` 的 `cursor` 不是复合串（旧的单列纯数字就落这里） | 400 | `cursor 不是合法的复合游标，请把上一次响应里的 next_cursor 原样回传` |
| 请求体 > 4MB | 413 | `请求体超过 4MB 上限` |
| 路径不认识 | 404 | `not found` |
| 服务端内部异常 | 500 | `服务端内部错误` / `服务端处理失败：<原因>` |

`POST /resolve`：`favorite_ids` 不是字符串数组 → 400 `favorite_ids 必须是字符串数组`。

其它实现要求：

- **UPSERT 必须幂等**（**本账号内**按 `favorite.id` 覆盖）；App 会重发同一条，服务端不能产生副本。跨账号的 id 不算「同一条」：见下面那条写侧校验，别拿这句去解释「别人的 id 也能覆盖」。
- **删除不存在的 ID 要进 `unknown_ops`**，不能 404 也不能静默计成 `applied`。
- **写侧也要校验归属**（2026-11-19 裁决，参考实现同日落地）：`id` 命中的行不属于本账号 → 该 op 进 `op_errors`、中性原因、原行不动、不计 `applied`。这条与删除侧的区别只在桶：删除走 `unknown_ops` 是因为「后台已经没有了」本来就是确认；写侧若也塞那里，App 会把被拒的改动出队标绿。校验的是**撞上的那一行**：`id` 在库里根本不存在时按新行收下并盖本次账号的归属，这一步拦不了「拿旧账号的 id 在新账号里新建一行」。
- 解析结果一旦生成就应**随收藏那一行一起持久化**，别只在内存里 —— App 重启后靠 `GET /favorites` 补内容信息。
- 客户端传来的 `media`（如果有人手滑传了）一律忽略，以自己解析的为准。

## 7. App 侧的存储（改协议前先看清这里）

Room **v5，收藏与内容信息同一行**（`app/src/main/java/com/favkit/tablet/data/db/Rows.kt`）。以前收藏和内容信息分两张表、内容表还带一个 `status` 列，是异步解析假设的残留：每次渲染都要 join，计数要从两个源各数一遍，才导致「加了删了数字对不上」。现在合成一行。整个库四张实体：这一行 + `tags`/`favorite_tags` 两张标签表 + `pending_ops` 待上传队列；**`pending_ops` 对 `favorites` 没有外键**，所以删行不会带走它排着的那笔 op（这条在增量对账启用之后是会撞到的，见 §3.6）。

| 列组 | 列 | 归属 |
|---|---|---|
| 上传的 | `id`、`url`、`note`、`sourceApp`、`favoriteAt` | App 产生，`POST /sync` 送出去 |
| 后台解析的 | `title`、`author`、`site`、`summary`、`segmentsJson`、`failedReason`、`resolvedAt` | 只从响应写回，App 不自造 |
| 本地状态 | `badge`（SYNCED/QUEUED/FAILED）、`locallyCached`、`updatedAt` + `hlcSeq`（本机这次写入的 HLC 读数，成对写）、`deletedAt`（软删＝墓碑，行留在表里等 DELETE op 被后台确认） | 只在 App |
| 后台发号存下来的 | `rev` | 只读：来自响应，本机下次编辑拿它当 `base_rev`；App 不自增、不自己编 |
| 本地进度 | `segmentProgress`、`lastSegmentIndex` | 只在 App，见 §2.5 |

**删掉之后重新收藏同一个链接不会新建一行**：面板按 url 判重时，活行算「已收藏过」，墓碑行算「恢复」—— 复用原来那个 id、清掉 `deletedAt`、写这次的备注/来源/标签整套覆盖、badge 回 QUEUED，队列里那条还没上传的 DELETE 由 `SyncManager.queue()` 那一步就地换成 UPSERT —— 清掉该条目尚未上传的旧载荷与插新载荷在**同一笔 Room 事务**里，两步不分开。`favoriteAt` 取两边较旧的那个，所以这条**不会回到列表顶部**，而是回到它上次的排序位置（排序稳定是键集游标不跳条的代价）。id 之所以必须复用：后台那边这一行本来就还在，本机换个新 id 就要等 `merged_into` 回执才对得上，中间这段时间本机看不见自己刚收藏的东西。

**换账号（设置页存了一串不同的 Bearer 令牌）时，本机会在同一条 Room 事务里做三件事**：`pending_ops` 整表清空、还挂着 `QUEUED`/`FAILED` 的行一次性归到 `SYNCED`、墓碑行物理删掉（`FavoritesRepository.dropUnsentEdits`，`MainViewModel.setSyncToken` 只在 trim 后的值真的变了才触发 —— 同一份配置重复保存不该把用户刚攒的改动清掉）。三件必须同事务：扫尾补投挑的正是「badge 是 QUEUED 而队列里没有 op」，光清 op 下一轮 worker 就把这些行重新铸成 op，等于没清；终值取 SYNCED 而不是 FAILED，因为三个 badge 里没有「不属于本账号」这一档，而 FAILED 会挂成一个没有 op、没有 `lastError`、也没有重试对象的假失败。**不清的三样**也各有理由：活行留着（`favorites` 没有账号列是既定口径，抹掉它等于把这台设备自己的收藏史删了；反过来说，换过账号之后本面墙上会短暂混着旧账号的行，直到用户手动清数据或新账号里同 url 那条被翻回来覆盖）、HLC 不动（它是本机自己的发号器，跨账号继续单调才是对的）、游标不手动归零（`AppSettings.sinceRev()` 的**游标戳 = 账号指纹 + 端点**，两者任一变了读数就是 0，新那台第一次对账自动从头对；只绑 token 的话，把同一串令牌指到另一台后台时旧游标照样成立，而那台的 rev 从自己的计数器起，`rev ≤ 旧游标` 的写入会被整段藏掉，里面可能正好有唯一能物理删本机行的墓碑）。**只改端点不清队列**：账号身份只由 bearer 算，同一串令牌换后台还是同一个账号，把待发队列清了等于替用户否定他刚换上的那台后台。剩下的一个窗口写在 KDoc 里，是明知的代价：令牌写 DataStore 与这笔库写在两个存储上做不到一次原子，选的顺序是「先落令牌、再清这里」——崩在中间的话旧账号的 op 还留着、重启后可能顶着新令牌发出去；反过来清在先，一次没保存成功的改令牌就把用户还没传出去的改动清没了，那是本机自己就能确认的丢数据。（发出去之后会怎样，§2 那条写侧校验已经落地（2026-11-19）：旧账号的 id 若在这台后台上就是一行别人归属的存量，进 `op_errors` 标红、原行不动；若那台后台压根没有这个 id（换端点或旧账号从没传上来），它会当成新账号的新行收下 —— 这一半拦不住，是明知留下的。）

因为开发阶段不留兼容包袱，`AppDatabase` 只挂 `fallbackToDestructiveMigration()`，v4→v5 没写 Migration —— 升级会清本地缓存。清完不是丢数据：冷启动看见本地为空会自动去后台取第一页，收藏本身在后台。**联调时看到「收藏全没了」先确认是这个，别当成后台丢了数据。**

假解析器：**同一个 url 永远得到同一份结果**（对 url 取 sha1，用 `hash[6:10]` 当槽位），存在的意义是把「一条链接 → 多个素材」的展示链路在本地完整跑一遍。`slot % 10` 决定素材构成，四类链接都会均匀出现：

| 桶 | 构成 | 段数 |
|---|---|---|
| 0–3 | 图 + 视频混合 | 1–2 段视频 + 1–4 张图 |
| 4–6 | 纯图集 | 1–12 张图 |
| 7–8 | 多段视频 | 2–4 段 |
| 9 | 单个视频（最贴近真实） | 1 段 |

`segments` 里视频段排在前面（卡片首图取 `segments[0]`，能播的先给封面）：视频段的 `cover_url` 是 `picsum.photos/seed/<hash8>-v<i>/640/360`、`duration_ms` 60s~30min、`quality` 从 720P/1080P/480P 取、播放地址从 4 个业界常用的公开测试流里选；图片段 `cover_url` 留空（它自己就是要看的那张图），`url` 是 `picsum.photos/seed/<hash8>-i<i>/1280/720`。`summary` 由同一份 `segments` 现场统计（`共 3 张图 + 2 段视频（合计约 9 分钟）：…`／`共 7 张图：…`／`1 段视频，约 6 分钟：…`），所以卡片上的文字永远不会和图对不上。`title` 为 `<站点>视频 · <hash6>`（纯图集是 `<站点>图集 · <hash6>`）。链接不是合法 http(s) 时回 `segments: []` + `failed_reason: "收藏链接不是合法的 http(s) 地址"`。

## 9. 手工联调脚本

把 `$BASE` 换成实际地址（例如 `http://127.0.0.1:8787/api/v1`），带令牌时再加 `-H "Authorization: Bearer $TOKEN"`。

```bash
BASE=http://127.0.0.1:8787/api/v1

# 1) 存活 + 能力自述（都免鉴权；先看 /meta 确认分页样式、保留窗口与账号口径）
curl -s "$BASE/health"
curl -s "$BASE/meta"

# 2) 上传一条收藏：期望 applied=1、favorites[0].media.segments 非空、next_wait_ms 有值
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' -d '{
  "device_id":"tab-debug","sent_at":1763122500000,
  "ops":[{"type":"UPSERT","favorite":{
    "id":"11111111-1111-1111-1111-111111111111",
    "url":"https://www.bilibili.com/video/BV1xx411c7mD",
    "note":"调试","tags":["算法"],"source_app":"manual",
    "favorite_at":1763122400000}}]}'

# 3) 分页拉取（第一页 / 续页）：每条都应自带 media，total 每页相同
curl -s "$BASE/favorites?limit=50"
curl -s "$BASE/favorites?limit=50&cursor=1763120000000.11111111-1111-1111-1111-111111111111"

# 4) 强制重算：favorites[0].favorite_at 应与第 2 步一致（重解析不置顶）
curl -s -X POST "$BASE/resolve" -H 'content-type: application/json' \
  -d '{"favorite_ids":["11111111-1111-1111-1111-111111111111"]}'

# 5) 删除已有 / 删除不存在：后者应进 unknown_ops，applied=0，但 ok 仍为 true
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' \
  -d '{"device_id":"tab-debug","sent_at":1763122501000,"ops":[{"type":"DELETE","favorite_id":"11111111-1111-1111-1111-111111111111"}]}'
curl -s -X POST "$BASE/sync" -H 'content-type: application/json' \
  -d '{"device_id":"tab-debug","sent_at":1763122502000,"ops":[{"type":"DELETE","favorite_id":"nope"}]}'

# 6) 校验负例：应 400 且 error 指出「第 1 条操作（UPSERT）缺少 favorite.id」
curl -s -i -X POST "$BASE/sync" -H 'content-type: application/json' \
  -d '{"device_id":"tab-debug","sent_at":1763122503000,"ops":[{"type":"UPSERT","favorite":{"url":"x"}}]}'

# 7) 设了 SYNC_TOKEN 却带错令牌：应 401
curl -s -i -X POST "$BASE/sync" -H 'content-type: application/json' -H 'Authorization: Bearer wrong' \
  -d '{"device_id":"tab-debug","sent_at":1763122504000,"ops":[]}'
```

App 侧的对应验收：列表小圆点 黄(QUEUED) → 绿(SYNCED)；拔网线保存 → 黄/红且条目仍在；恢复网络后不点任何按钮应自动补传转绿；保存成功后**卡片应立即出现标题、说明和拼图封面**（同一次 `/sync` 回执带来的，不需要任何后续请求）。

## 10. 兼容与演进

- App 端配置项：接口地址与令牌在设置页可改，持久化在 DataStore；打包默认值来自 `gradle.properties` 的 `SYNC_ENDPOINT` 或 CI 的 `SYNC_ENDPOINT` 变量（缺省 `http://10.0.2.2:8787/api/v1`，即模拟器访问宿主机）。设备标识 `device_id` 形如 `tab-` + 12 位 UUID 片段，首次使用时生成并固定。
- 本协议没有版本号字段，版本靠 `BASE_PATH`（`/api/v1`）体现。
- **加字段安全**（App 忽略未知键），**改语义/删字段危险**：改任一边都要同时改 `Dto.kt`、`server.mjs` 与本文。
- 若后台真的改成异步解析，**不要**把 `status` 加回来。加一个 `media: null` 的语义（表示「还没算完」）就够了，App 已经按这条分支显示「内容信息还没取回来」；但那样就必须回头再取一次，而「回头取」正是这版协议删掉的东西 —— 请先确认收益再动。
- Room 工作树已到 **v5**（提交在 HEAD 的还是 v4）。v4 把 `video_info` 并进来、删掉 `bucket` 与 `last_position_ms`；v5 加 `rev`（后台发号，本地只读）与 `hlcSeq`（本机 HLC 的 seq，与 `updatedAt` 成对），并把 `updatedAt` 的默认值从「建表就取本机墙钟」改成 **0** —— 0 的意思是「这一行本机没写过」，也就是**不发 `write_hlc`**。默认值取墙钟是错的：那样每一行都会带着一个凭空出现的戳参与决胜。开发阶段不写迁移，见 §7。
- **多设备与多写入者的目标协议**见 [多设备与多写入者同步设计.md](多设备与多写入者同步设计.md)。本文只描述**现在真在跑的东西**：参考实现已经有账号维度（`account_id` 由凭证解出，无凭证时整实例共享一个匿名账号）、墓碑化 DELETE + 保留窗口、按 url 的解析缓存、`GET /meta`、按账号发号的 `rev`、`changed_fields` 字段白名单与逐字段 `(wall_ms, seq, 写者)` 决胜、**三档时钟兜底与超前夹紧（③-3a，见 §2.4）**、**`(favorite_at, id)` 复合分页游标与 `clock_skew` 账号级计数（③-3b，见 §3.2、§3.4）**；App 侧的**文案收尾**同样已落地（占位句「内容信息还在后台解析」卡片与遮罩层同词，`VideoCard.kt:389`、`FocusOverlay.kt:1123`；失败那句两处不同词，是界面自己的口径，不影响协议）；对账的触发与善后已全部落地 —— `since_rev` 持久化、「队列跑干净时对一次」、「进前台对一次 + `truncated` 退回全量翻页」与「跑满一轮后在同一次 worker 运行里续跑一次」。`GET /favorites/changes` 对账通道（④）**参考实现已经上线**（§3.6：`revision_log` + `truncated` 水位线 + 与墓碑同窗口 GC），App 侧出站与落库也已实现；`base_rev` 的版本冲突判定（③-2）**已定为不做**，是裁决不是待办（见 §2.4 与设计稿 §5）。读本文按现状读，别把设计稿里的字段当成已存在。
- **第三方采集服务不走本文这套接口**。后台给它单独一个 ingest 面（`POST /ingest/favorites` 批量逐条应用、异步解析），契约见 [第三方采集服务接入接口.md](第三方采集服务接入接口.md)。两个面共用同一套数据与同一个 `rev` 序列，所以 §0 那条「保存与解析在同一次调用里完成」的主脑**只约束 App 面**：第三方写进来的内容信息会晚于数据到达，App 靠对账补上，界面上仍然只有卡片占位那一行字，不进任何计数。
