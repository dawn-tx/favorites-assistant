# 第三方采集服务接入接口（待实施）

> **状态：设计稿，后台与 mock 参考实现里都还没有这个接口。**
> 本文只描述**面向第三方服务的 ingest 面**。App 现在真在跑的那份协议见 [同步后台接口说明.md](同步后台接口说明.md)；多设备合并与对账的目标协议见 [多设备与多写入者同步设计.md](多设备与多写入者同步设计.md)。
> 三者关系：**两个 API 面，一套数据**。Ingest 面写进去的每一条，都走同一个 `account_id`、同一个 `rev` 序列、同一张 `revision_log`，所以 App 靠 `GET /favorites/changes` 就能看到服务方写的内容，**App 协议与 App 代码都不为此改动任何接口形状**。

---

## 0. 为什么单独开一个面

让第三方直接调用 App 的 `POST /sync` 也能跑，但那要求它理解一堆只属于「有本地队列的重客户端」的概念：客户端自生成 id、整条覆盖、`applied + unknown_ops == len(ops)`、`next_wait_ms` 驱动的节奏、字段级 `changed_fields`、HLC、以及 id 被归并后要读 `merged_into`。这些每一个都会让一个「只想把采集结果推给你」的服务出错。

| | App 面 | Ingest 面（本文） |
|---|---|---|
| 面向 | 有状态重客户端：本地队列、离线编辑、翻页缓存、要续传 | 无状态一次性写入方 |
| 幂等键 | `favorite.id` | `(provider, external_id)`，其次 `(account, url)` |
| 批量 | 一次 1 条（内部实现约定，不是公开契约） | **一次最多 N 条**，逐条独立应用 |
| 失败粒度 | 整条 op 留在本地队列重试 | 逐 item 结果，请求本身不重发 |
| 校验回滚 | **全有或全无**：任一条不合法整批 400（接口说明 §6） | **逐条独立应用**：一条脏数据只影响那一条 |
| 节奏 | `next_wait_ms` 驱动客户端队列 | 没有队列要推，只有 `retry_after_ms`（429） |
| 内容信息 | 与保存同一次调用返回（本面的主脑） | **异步解析**，见 §9 |
| 时钟 | 客户端 HLC | 服务端代发，调用方不碰，见 §7 |

**「全有或全无 → 逐条独立应用」是本面与现有协议最大的语义差别**，也是接入方最容易猜错的一条，所以放在第一页。

## 1. 身份、授权与凭证

```
provider_credentials(
  token_hash,            -- 只存哈希，不存明文
  provider_id, name,
  writable_fields[],     -- 见 §6；默认 [url, tags, favorited_at, metadata]
  default_source_app,    -- 强制写进落库行，请求里传了也忽略
  max_items, rate_limit_per_min, daily_item_quota,
  tier[standard|media_override],
  created_at, revoked_at
)

provider_accounts(provider_id, account_id, bound_at, bound_by)   -- 授权白名单
```

四条硬性规则：

1. **`account_id` 永远不来自请求体本身**，来自 `provider_accounts` 查询：请求带 `account`（服务方自己的用户键或后台发放的绑定码），后台查「这个 provider 被允许写这个账号吗」，不在白名单 → 整请求 `403 account_not_bound`。一个服务代多个用户写是常态，所以「一凭证一账号」这种简化模型不成立。
2. **`source_app` 由凭证给出**。否则任何服务都能伪装成 `chrome`，而 App 卡片上那行来源（`VideoCard` 已在展示 `sourceApp`）就成了谎话。
3. 匿名账号（无 token 的单设备）与 provider 写的行落在同一 `account_id` 时，用户看得见、管得了（删除走 App 面正常 tombstone）。这就是「同一账号、可见可合并」的实现形态。
4. 凭证吊销 = `revoked_at` 置位，已写入的数据**不回滚**（用户的所有物）。运维要清理来源，走单独的「按 provider 批量 tombstone」内部脚本，不做成公开接口。

## 3. `POST /api/v1/ingest/favorites`

```jsonc
{
  "account": "u-8f2c1d",                  // 必填，经 §1 白名单校验
  "items": [                              // 必填，1..max_items（默认 200）
    {
      "external_id": "srv:9f1c0a5e",      // 必填，provider 内唯一，幂等键
      "url": "https://www.bilibili.com/video/BV1xx411c7mD",  // 必填，合法 http(s) 绝对地址
      "tags": ["待看", "算法"],            // 可选
      "favorited_at": "2026-11-19T03:10:00+08:00",            // 可选，见 §7
      "action": "upsert",                 // 可选，upsert | delete，默认 upsert
      "metadata": {                       // 可选，规则见 §8 —— 提示，不是权威
        "title": "实测 3 款降噪耳机",
        "duration_ms": 480000,
        "cover_url": "https://…"
      }
    }
  ]
}
```

响应 200（**逐条结果，不用 HTTP 状态码表达单条失败**，与 App 面同一读法）：

```jsonc
{
  "ok": true,
  "server_time": 1763122500123,
  "account_rev": 1284,                    // 这批写完之后账号的最新 rev
  "results": [
    { "index": 0,
      "external_id": "srv:9f1c0a5e",
      "status": "created",                // 见 §4 全表
      "favorite_id": "b7d4c3f2-…",        // 后台真实 id；服务方通常用不到（§5）
      "reason": "", "reason_code": "" }
  ],
  "retry_after_ms": 0,                    // 仅限流时 > 0
  "error": ""                             // 仅整请求级错误时非空
}
```

**本面的不变式：`len(results) == len(items)`，且每个 index 恰好一个结果。**
App 面靠 `applied + unknown_ops + op_errors == len(ops)` 防假成功（`op_errors` 非空时那几条绝不计进 `applied`；不下发该键的老后台退回 `applied + unknown_ops == len(ops)`），本面靠这条等价但不依赖计数的形式。对不上就是后台 bug，宁可 500 也不回一个「看起来成功」的响应——沿用接口说明 §3.1 同一条立场。

请求内多个 item 命中同一行时，**按数组顺序逐条应用**（顺序是契约的一部分，因为本面是同步逐条落库，不存在「合并窗口」）。同一请求内出现两个 `external_id` 指向同一 url：第一个建/改行，第二个 `merged` 并把它的 alias 指到同一个 `favorite_id`。

## 4. `status` 与 `reason_code` 全表

| `status` | 含义 | 会 bump `rev` 吗 | 写 `revision_log` 吗 |
|---|---|---|---|
| `created` | 新行 | 是 | 是 |
| `updated` | 命中已有行且有字段实际变化 | 是 | 是 |
| `merged` | 命中的是**别人创建**的行（url 撞车），只写入了自己有写权的字段 | 是（若有变化） | 是 |
| `unchanged` | 内容重放，或目标状态已达成（删已删的） | **否** | **否** |
| `deleted` | 按 `external_id` 墓碑化成功 | 是 | 是 |
| `rejected` | 本 item 被拒，其余照常应用 | 否 | 否 |

| `reason_code` | HTTP | 伴随 status | 该重试吗 |
|---|---|---|---|
| `missing_external_id` | 200 | rejected | 否 |
| `url_not_absolute` | 200 | rejected | 否（不是合法 http(s) 绝对地址） |
| `field_not_writable` | 200 | rejected | 否（**reason 里点名哪个字段**，见 §6） |
| `ambiguous_datetime` | 200 | rejected | 否（见 §7） |
| `url_immutable` | 200 | rejected | 否（同 `external_id` 换了 `url`） |
| `owned_by_other_source` | 200 | rejected | 否（本凭证对该行无任何可写字段） |
| `unknown_external_id` | 200 | rejected | 否（`action: delete` 指向从未见过的 id） |
| `quota_exceeded` | 200 | rejected | 否（日配额；整请求已应用的条目不回滚） |
| `account_not_bound` | 403 | — 整请求 | 否 |
| `too_many_items` | 413 | — 整请求 | 是，拆批 |
| `rate_limited` | 429 | — 整请求 | 是，按 `retry_after_ms` |
| `resolver_unavailable` | 200 | updated/created | 无需重试（§9：解析自己会补投） |

`unknown_external_id` 不复用 App 面 `unknown_ops` 那个「不算错误」的口径。语义不同：App 面删不到东西是**多设备正常收敛**，ingest 面删不到东西是**它以为存在过的记录不存在** —— 必须报拒绝，否则服务方的本地状态机和后台悄悄错位。

## 5. 幂等与重放

`favorite_aliases.payload_hash = sha256(该 item 归一化后的可写字段)`。

- 同 `external_id` + 同 hash 重放 → `unchanged`，**不 bump `rev`、不写 `revision_log`**。
- 同 `external_id` + 不同 hash → 正常合并，`updated`/`merged`。

少了 hash 判定这条，服务方的每一次网络重试都会给所有设备产生一条空对账变更，`/changes` 的流量等于重试次数。这也是 §11 里 `unchanged` 率的用途：**偏高就是在盲目重放**，运维可以直接找服务方要说法。

`favorite_id` 每步都返回，但**服务方不需要存它**：后续所有操作都能用 `external_id` 表达，别名解析在后台完成。服务方要展示或跳转再用它。这是分接口最直接的减负 —— 上一版为「第三方直接调 `/sync`」设计的 `merged_into` 回执，在 ingest 面根本不需要暴露给服务方（App 面仍然保留，因为 App 自生成的 id 也可能撞上 ingest 先建的行）。

## 6. 字段归属与合并

`favorite_fields(favorite_id, field, value, hlc_wall, hlc_seq, owner)`，其中 `owner` 是 `device_id`（App 面）或 `provider_id`（本面）。

合并一个字段时两道判定：

1. **写权**：该 owner 的 `writable_fields` 含这个字段吗？不含 → 整个 item `rejected / field_not_writable`。
   *为什么是整条拒而不是静默丢弃那一个字段*：静默会让服务方以为写成了。宁可它改一次调用就对了。
   默认**不含 `note`**：备注是用户自己的文字，服务方不该往里写；也不含 `media`（内容信息只认解析器，§8）。要 `note` 写权得单独申请凭证（运维级 `tier`）。
2. **胜负**：有写权再看 HLC，按设计稿 §3 的比较序取新值。所以服务方反复重传同一批标签，一旦用户在 App 里删掉某个标签，用户那次写入赢。

url 撞车的三种落点：

| 命中情况 | 结果 |
|---|---|
| 同一 `external_id` | 正常更新 |
| 别的 provider 或用户建的行，且本凭证有 ≥1 个可写字段落在**该字段归属为空或 owner = 本 provider** 的列上 | `merged`：只写有写权的字段，其余一律不动。**不会把用户的备注洗掉** |
| 本凭证对这个行一个字段都写不了 | `rejected / owned_by_other_source` |

## 7. 时间与格式纪律

时区影响显示、偏移与漂移影响决胜 —— 处置不同，别混。本面对时间字符串比 App 面宽容，因为服务方数据源里常是 ISO 串，而且**带偏移的 ISO-8601 是无歧义的**：

| 输入 | 处理 |
|---|---|
| 整数 epoch 毫秒 `1763122400000` | 原样采用 |
| 带偏移 ISO-8601 `2026-11-19T03:10:00+08:00` / `...Z` | 服务端换算成 epoch 毫秒 |
| **无偏移** `2026-11-19 03:10:00` / `2026-11-19T03:10:00` | 拒绝 `ambiguous_datetime`（不猜时区） |
| 落在 `[1e8, 1e11)` 的整数 | 拒绝 `ambiguous_datetime`（看着是秒，**不自动 ×1000**） |
| 浮点、字符串数字、布尔 | 拒绝 `ambiguous_datetime` |

范围判据优先于位数判据；自动 ×1000 会把「填错字段」变成「静默错位十年」，这是最难查的一类事故。

超出范围的物理时间不拒绝，**夹紧**到 `[now − 10 年, now + 5 分钟]` 并计数。

**决胜时间戳不由调用方给**：本面的每次写入由服务端生成 HLC `(wall_ms = server_time, seq = 0, owner = provider_id)`。服务方完全不用实现时钟逻辑，但它的写入在因果上必然排在「它收到上一个响应之后」——这正是我们想要的性质。

App 面**不收** ISO 字符串：客户端只发毫秒（`SyncApi.kt:52`），给它加一条解析分支是纯死代码。

## 8. `metadata` 与 `media_hint`：内容信息谁说了算

现状是硬的：客户端传的 `media` 一律忽略，内容信息只认后台解析器（接口说明 §6）。本面把服务方已有的标题/时长/封面收进 `media_hint`，规则：

1. `metadata` **不覆盖** `media`。落 `media_hint` 列，仅参与 §5 的 hash 与 §6 的写权判定。
2. **仅当解析器返回 `failed_reason` 非空**时，用 `media_hint.title` / `cover_url` 兜底填空缺，卡片仍显示「解析失败」及原因。这样用户看得见「这句标题是别人给的，不是抓的」。
3. 时长/清晰度一律不采信 `metadata`（播放链路只认段上的真实值，`duration_ms` 为 0 时进度条不可拖）。
4. 要权威覆盖解析结果，凭证 `tier = media_override`，运维级。默认凭证享受不到，因为「服务方报的标题」压过「后台实际抓到的」会让墙上的内容不可信。
5. `metadata` 里出现 `url`/`play_url`/`segments` 一律拒绝（素材清单只能由解析器产生，这是播放器安全边界）。

## 9. 异步解析：本面不再「保存与解析同一次完成」

接口说明 §0 那条主脑（保存与解析在同一次调用完成）**只约束 App 面**。本面：

- 请求内只做数据落库 + 别名维护，**不同步解析**。返回 `created` 时就意味着「数据已经安全落地」，不意味着「内容信息已经就绪」。
- 解析进后台队列（按凭证并发上限与优先级），结果写入后 bump `rev`、写 `revision_log`。App 靠 `/changes` 在既有事件上看到它。
- **不需要新字段表达「解析中」**：`media` 缺失 = 还没解析出来，`failed_reason` 非空 = 终态失败，`media` 有值 = 完成。这正是接口说明 §10 预言过的那条「不要把 `status` 加回来，用 `media: null` 的语义就够了」。
- 成本控制（App 面同样受益）：按 `hash(url)` 建 `media_cache`，**重传同一 url 不重爬**；改 `note`/`tags` 永不触发解析。现状 mock 每次 UPSERT 无条件 `resolveMedia`（`server.mjs:369`）必须先改掉，否则批量回灌直接把解析层打爆。

服务方需要「这批到底解析完没有」的可观测出口时，用 `GET /ingest/status?external_ids=…` 只读查询（返回 `{external_id, favorite_id, media_state: pending|ready|failed}`），**不要**为它设计回调推送 —— 回调会引入重试、签名、顺序三个新问题，收益只有「省一次轮询」。

## 10. 配额、限流与批量

| 项 | 默认 | 载体 |
|---|---|---|
| `max_items` | 200（超出 413 `too_many_items`） | 凭证级可调，`GET /ingest/meta` 公布 |
| 请求体 | 4MB（沿用 App 面同一条，超出 413） | 全局 |
| 速率 | `rate_limit_per_min`，429 + `retry_after_ms` | 凭证级 |
| 日量 | `daily_item_quota`，超出逐 item `rejected / quota_exceeded` | 凭证级 |
| 解析队列 | 每凭证并发上限 + 优先级 | 运维参数，`ingest/meta` 只读展示 |

日配额用尽时**已应用的条目不回滚**（回滚会产生一批无意义的 tombstone，把 App 的对账流量打满）。`retry_after_ms` 是本面唯一的等待提示，没有 `next_wait_ms` —— 本面没有待推的客户端队列。

## 11. 观测与隐私

按 provider 维度出指标：item 数、`status` 分布、`reason_code` 分布、**`merged` 率**（偏高 = 服务方的唯一键管理有问题，在靠 url 撞车续命）、**`unchanged` 率**（偏高 = 在盲目重放）、解析队列积压与延迟分位。

日志隐私约束：url **只记 `host` + `sha1(url)` 前 8 位**，不记全串。收藏链接常带一次性 token / 签名参数，把全串写进运维可查的日志等于长期留存用户凭证。完整 url 仅在单请求 debug 开关下打印，且开关默认关闭、变更要审计。

`token` 只存哈希；日志与指标里都不出现明文凭证；`Idempotency-Key` 若启用则只存哈希与时间。

## 12. App 侧对应口径（明确不做什么）

1. **`SyncBadge` 保持 `SYNCED / QUEUED / FAILED` 三值**（`Models.kt:10`），**不新增「待解析」**。同步状态描述的是「本机改动有没有传到后台」，解析是后台的进度，两者不能混进同一个枚举——那是最早那版 `status` 列被删掉的同一个错误。
2. **界面上的状态词仍然只有三枚**：`离线 / 待同步 N / 失败 N`，且全部只数上传队列。解析中多少条**不进任何全局计数**（顶栏、筛选抽屉、悬浮球角标都不进）。这条写成测试用例：库里 50 条全在解析中，顶栏不得出现「待同步 50」。
3. 「解析中」只出现在两个位置：卡片封面占位块（`VideoCard.kt:388` 那条分支）与遮罩层详情里的那一行。文案统一改成**「内容信息还在后台解析」**——现有文案「内容信息还没取回来」在异步解析下会让人以为是自己没同步到。这一句对两种缺失原因（后台还在解析 / 老后台没返回）都成立，所以不需要为区分它们新增字段。
4. 占位块**不给转圈**、不给进度条。转圈是轮询的心智承诺，而本条链路根本没有轮询。
5. 解析结果到达走的是**已有落库路径**：`importRemote` 对已有行「只写 media，用户数据/上传状态/播放进度一概不动」（`FavoritesRepository.kt:177`）。这段代码的形状本来就是为这一刻准备的，零改动。
6. 不需要任何新的取数时机：补投靠 `/changes`，触发仍是**进前台 / 联网回调 / 一次上传成功之后**这三类既有事件（原始需求的「零轮询、零定时器、后台静默同步不吃电量」一条不动）。
7. 手动出口不变：遮罩层「重新解析」按钮走 `POST /resolve`（App 面仍同步返回，见接口说明 §3.3），筛选抽屉「从后台加载」走全量翻页。
8. 服务方写进来的行在界面上就是普通收藏：来源显示凭证的 `source_app`，用户可以改备注、加删标签、删除、缓存。用户一旦改过某字段，该字段的归属与 HLC 让用户赢（§6）。

## 13. 联调脚本

```bash
BASE=http://127.0.0.1:8787/api/v1
TOK=<service token>

# 1) 能力与限制
curl -s "$BASE/ingest/meta" -H "authorization: Bearer $TOK"

# 2) 两条：期望 results 两条、status 分别 created / created，account_rev 递增 2
curl -s -X POST "$BASE/ingest/favorites" -H "authorization: Bearer $TOK" \
  -H 'content-type: application/json' -d '{
  "account":"u-debug","items":[
    {"external_id":"srv:1","url":"https://www.bilibili.com/video/BV1xx411c7mD",
     "tags":["待看"],"favorited_at":"2026-11-19T03:10:00+08:00",
     "metadata":{"title":"服务方给的标题"}},
    {"external_id":"srv:2","url":"https://example.com/a"}]}'

# 3) 幂等重放第 2 步同一批：期望两条都 unchanged，account_rev 不变
# 4) 同 url 换 external_id：期望 merged，favorite_id 与 srv:1 相同
# 5) 无偏移时间：期望 rejected + ambiguous_datetime，其余 item 照常 applied
curl -s -X POST "$BASE/ingest/favorites" -H "authorization: Bearer $TOK" \
  -H 'content-type: application/json' \
  -d '{"account":"u-debug","items":[{"external_id":"srv:3","url":"https://example.com/b","favorited_at":"2026-11-19 03:10:00"}]}'

# 6) 传不可写字段（默认凭证不含 note）：期望 rejected + field_not_writable 且点名 note
# 7) 删除：{"account":"u-debug","items":[{"external_id":"srv:2","action":"delete"}]}
#    再删一次 → unchanged；删从未见过的 external_id → rejected + unknown_external_id

# 8) 从 App 面确认服务方写的东西真的可见
curl -s "$BASE/favorites?limit=5" -H "authorization: Bearer $USER_TOKEN"
```

验收口径：第 2 步之后，用户设备上「进前台」应看到两张新卡（内容信息可能仍是「还在后台解析」，属正常），顶栏计数只反映本机上传队列，**不因为服务方写了 2 条而出现任何新的状态词**。

## 14. 接入方自查清单

1. `external_id` 在你自己库里唯一且**永不复用**（换内容请用新 `external_id`，同 `external_id` 换 url 会被拒）。
2. 时间只传 epoch 毫秒或带偏移 ISO-8601，**别传裸本地时间**。
3. 不要传 `note`、不要指望 `metadata` 覆盖标题（默认凭证；§8）。
4. 不要假设「`created` = 内容信息已就绪」，见 §9。
5. 逐 item 读 `status`/`reason_code`，只看 HTTP 200 会把被拒的 item 当成成功。
6. 重放安全，但别把重放当常规手段——`unchanged` 率是你的运维指标之一。
7. 429/413 按 `retry_after_ms` 退避、拆批，不要多开连接绕配额。
8. 不要缓存 `favorite_id` 当唯一键；一切用 `external_id` 表达。
9. 一个服务代多个用户时，绑定关系要经 §1 的白名单流程，别把 `account` 当自由字符串填。
10. 需要内容信息就绪的强信号时，用 `GET /ingest/status` 自己低频查，不要要求后台回调。

## 15. 红线（评审时逐条对照）

- 不给 App 面加「批量 ops 的顺序无关性」承诺——第三方约束已经迁到本面，`/sync` 的单 op 只是内部实现事实。
- 不引入 `status` / `pending` 字段，不用 `media: null` 之外的方式表达解析中。
- 不把解析中计入任何全局状态计数（§12 第 2 条）。
- 不接受调用方提供的可播地址、段清单、时长。
- 不在日志里留存完整收藏 url、明文 token。
- 不为 ingest 设计回调推送。
